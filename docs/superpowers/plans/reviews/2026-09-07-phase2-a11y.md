# A11y Lens Review

**Reviewer lens:** accessibility (visual, auditory, motor, cognitive)
**Plan:** `/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase2.md` (Phase 2 — Swift)
**Spec:** `docs/superpowers/specs/2026-09-07-crackerjack-multi-language-design.md` Rev 2
**Primary user:** LLM-driven workflows (Mahavishnu/Akosha dispatch, humans via CLI). Screen-reader / keyboard-only / non-expert users must not be silently excluded.

## Findings (most-severe first)

### F1 (CRITICAL) — Tool descriptions are dense with internal jargon that screen readers will read aloud as gibberish

The three registered MCP tool descriptions embed opaque spec IDs:

- `swift_bump_version`: `"Bump the Swift project's version (via git tags, no Package.swift mutation). Per spec Swift F1: tag is the version. Per spec MCP F5: requires auth."`
- `swift_run_hooks`: `"Run the configured Swift hooks against project_root..."`
- `detect_languages`: `"Return which language adapters detect the project at project_root. Phase 2: returns {'python': bool, 'swift': bool}. Phase 3+ adds Kotlin, Phase 4+ adds Web."`

Screen readers will read `F1`, `F5`, `Swift F1`, `MCP F5` as letter-then-number sequences with no context. For a user exploring `discover_tools()` output, those internal anchors communicate nothing about behavior, prerequisites, or failure modes. **Better:** rephrase as actionable language — "Bumps the version by creating a new `vX.Y.Z` git tag (Package.swift is not modified). Requires authentication." Drop the spec IDs entirely from docstrings; keep them in plan/spec/code comments where humans navigate by structure.

### F2 (CRITICAL) — Error messages fail the WHAT/WHY test for non-expert users

`_require_auth()` raises two variants:

```python
raise PermissionError(
    "MAHAVISHNU_AUTH_ENABLED=true required for mutation tools. "
    "See .claude/decisions/mcp-backend-wiring-discipline.md.",
)
raise PermissionError(
    "MAHAVISHNU_JWT_SECRET unset. Mutation tools require auth.",
)
```

- **WHAT**: env-var names are present — good.
- **WHY**: "required for mutation tools" is a tautology. It does not explain the security model (unauthorized bump/release would push tags and create GitHub releases). A user encountering this in CI without context will assume it's a typo, not a deliberate gate.
- **Link target**: the path `.claude/decisions/mcp-backend-wiring-discipline.md` is opaque to anyone not on the maintainer team, and unreachable from the MCP client surface that surfaced the error.

**Better:** "Mutation tools require authentication. Set `MAHAVISHNU_AUTH_ENABLED=true` and `MAHAVISHNU_JWT_SECRET` (min 32 chars) in the environment, or contact your crackerjack administrator to obtain credentials. Without auth, lifecycle operations that push tags and create GitHub releases are blocked."

### F3 (HIGH) — CHANGELOG entry contains a typo that breaks text-to-speech intelligibility

Step 8.6 of the plan writes:

```
`crackageck.language_adapters` entry-point group now registers both
```

That is `crackageck`, not `crackerjack`. A screen reader will read it as a nonsense word. Even sighted users searching the docs for the entry-point group name will not find it. This needs to be fixed before Step 8.6 commits. The error is in the plan text — implementers will copy-paste it.

### F4 (HIGH) — Missing tests for several documented error paths

The plan's test coverage is good for the happy path + auth gate, but leaves gaps that matter for accessibility of failure feedback:

- **No test for `FileNotFoundError` on missing `project_root`.** If a user passes a path that doesn't exist, what does `swift_bump_version` return? The lifecycle calls `GitTagVersionSource.read()` which will raise `VersionNotFoundError`, but the MCP wrapper has no try/except and no friendly error mapping. The user gets a raw stack trace in MCP `CallToolResult.content[0].text`.
- **No test for non-auth subprocess failures** (network drop on `git push`, missing `swift` binary, missing `gh` CLI). `_push` is mocked to raise `RuntimeError("network")` in one test, but real git failures raise `subprocess.CalledProcessError` — a different exception class with no message. The rollback will still fire, but the user-facing message will be unhelpful.
- **No test for rollback failure.** If `_delete_tag` itself raises during rollback (e.g., tag already pushed elsewhere), the original `RuntimeError` from `_push` is the only exception surfaced; the secondary failure is swallowed. This is a discoverability bug for operators diagnosing stuck releases.
- **No test for invalid `level` values.** `LifecycleOptions.level` is typed `Literal["major", "minor", "patch"]`, so the type system rejects most cases — but at runtime the helper `_bump()` raises `ValueError(f"Unknown level: {level!r}")`. That message is jargon-heavy ("major", "minor" are not defined inline).
- **No test for `swift_run_hooks` when `Package.swift` doesn't exist.** `adapter.capabilities(root)` calls `parse_platforms()` which raises `FileNotFoundError("Package.swift not found: {path}")`. That message is fine, but it's untested, and the MCP layer doesn't catch it.

Add at least: `test_swift_bump_version_missing_project_root`, `test_swift_run_hooks_missing_package_swift`, `test_swift_lifecycle_rollback_handles_delete_tag_failure`, `test_swift_bump_version_invalid_level`.

### F5 (MEDIUM) — `detect_languages` breaks the naming convention, harming screen-reader navigation

Phase 2 registers three tools:

| Tool name | Pattern |
|---|---|
| `swift_bump_version` | `<language>_<verb>_<noun>` |
| `swift_run_hooks` | `<language>_<verb>_<noun>` |
| `detect_languages` | `<verb>_<noun>` (no language) |

When clients list these alphabetically (`detect_languages`, `swift_bump_version`, `swift_run_hooks`), a screen-reader user browsing for a Swift operation hears `detect_languages` first, then has to skip it. As Phase 3+ adds Kotlin and Web tools, the convention breaks further.

**Better:** rename to `languages_detect` (verb-first, consistent sort), OR add a `crosscutting_*` prefix group. At minimum, document the convention in the spec so Phase 3+ implementers extend it instead of fragmenting it.

### F6 (MEDIUM) — `_run_swift_lifecycle` swallows subprocess errors into the generic `Exception` rollback path

The catch block:

```python
try:
    self._push(commit_sha, tag_name)
except Exception:
    logger.exception("push failed; rolling back tag %s", tag_name)
    self._delete_tag(tag_name)
    self._reset(commit_sha)
    raise
```

`except Exception` will catch `KeyboardInterrupt` and `SystemExit` (linter enforcement aside — Ruff B902 will probably flag this). For accessibility of error reports, narrower `except` clauses (`subprocess.CalledProcessError`, `OSError`) let the caller distinguish a transient network issue from a programming error, which matters for users triaging failures via screen reader.

### F7 (LOW) — Underscore-separated tool names are read awkwardly by some screen readers

`swift_bump_version` is pronounced by some TTS engines as "swift underscore bump underscore version" or "swift bump version" depending on punctuation-handling rules. NVDA and JAWS typically pronounce as a single phrase; VoiceOver may split on underscores. Mitigation: rely on the docstring (which the same screen reader will announce) to reinforce meaning. The chosen names are fine; this is a documented limitation, not a plan defect.

### F8 (LOW) — Output structure for screen-reader parsing is good but could include a human summary

`_run_swift_lifecycle` returns:

```python
{
    "new_version": str | None,
    "commit_sha": str | None,
    "tag_name": str | None,
    "release_url": str | None,
}
```

- Keys are descriptive snake_case — good.
- Types are clear (`str | None`) — good.
- Insertion order is preserved (Python 3.7+) — good.
- **Missing**: a one-line `summary` field that a non-technical user could read aloud directly, e.g., `"summary": "Released v1.1.0 (commit abc123) — https://github.com/.../releases/tag/v1.1.0"`. Screen readers reading the raw dict will say "key new version value 1.1.0, key commit sha value abc123..." — functional but verbose.

### F9 (LOW) — Plan length and heading structure are screen-reader-friendly

The plan is ~1900 lines with clear `## Task N` and `## File Structure` headings, checkbox steps for navigation by `skip-heading` users, and consistent code-block formatting. This is better than most plans in the repo. No changes needed; flagging as positive observation.

### F10 (LOW) — Doc references to internal `.claude/decisions/*.md` paths are not navigable from outside the repo

The plan and the error message both reference `.claude/decisions/mcp-backend-wiring-discipline.md`. This is fine for in-repo reading, but the error message will be the only thing a user sees from a remote MCP client. Add a one-sentence summary of the policy in the error message itself (see F2) so the user does not need to leave the tool surface to understand the rule.
