# API Lens Review — Crackerjack Multi-Language Phase 2 (Swift)

## Findings (most-severe first)

### CRITICAL — `_gh_release` constructs a fake URL on `gh` failure

`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase2.md` lines 1595-1600:

```python
def _gh_release(tag_name: str) -> str:
    result = subprocess.run(
        ["gh", "release", "create", tag_name, "--generate-notes"],
        cwd=project_root, capture_output=True, text=True,
    )
    return result.stdout.strip() if result.stdout else f"https://github.com/local/{project_root.name}/releases/tag/{tag_name}"
```

Two problems compound:

1. `subprocess.run(..., check=False)` — if `gh` exits non-zero, the call is silently swallowed.
2. The fallback URL is fabricated from `project_root.name`. The caller cannot distinguish a real GitHub release from a synthetic placeholder.

Phase 1's analog `PythonLifecycle._publish_pypi` returns `str | None` (`/Users/les/Projects/crackerjack/crackerjack/adapters/python/lifecycle.py:188`), so `None` means "no release". Phase 2 should mirror that: either return `str | None` with `None` when stdout is empty OR `result.returncode != 0`, or raise. Silently emitting a synthetic URL will poison `LifecycleResult.release_url`, the MCP tool's `dict["release_url"]`, and any caller checking truthiness.

**Recommended fix**: signature `_gh_release(tag_name: str) -> str | None`, raise on non-zero exit, return `None` when stdout is empty.

### CRITICAL — Inconsistent hook-method signatures vs. Phase 1 PythonLifecycle

Phase 1's `PythonLifecycle` (`/Users/les/Projects/crackerjack/crackerjack/adapters/python/lifecycle.py`) and Phase 2's `SwiftLifecycle` (plan lines 1136-1152) have diverged in ways that will block a clean unification later:

| Method | Phase 1 (Python) | Phase 2 (Swift) | Plan claim |
|---|---|---|---|
| `_tag` | `(name, message) -> str` (returns tag name) | `(name, message) -> None` | "consistent with the PythonLifecycle" — FALSE |
| `_publish_pypi` / `_gh_release` | `(tag_name) -> str \| None` | `(tag_name) -> str` (never None) | "consistent" — FALSE |
| `_commit` | `(message) -> str` | `(message) -> str` | OK |
| `_push` | `(commit_sha, tag_name) -> None` | `(commit_sha, tag_name) -> None` | OK |
| `_delete_tag` | `(name) -> None` | `(name) -> None` | OK |
| `_reset` | `(commit_sha) -> None` | `(commit_sha) -> None` | OK |

Pattern B per Phase 1 ledger ruling #1 means "split methods on the instance" — that is honoured. But the *return types* are not consistent. A future helper like `run_lifecycle_for(lifecycle, options)` that introspects hook return types will silently fail.

**Recommended fix**:
- `_tag(name, message) -> str` (return tag name; tests need updating, see test line 966 which already expects `return_value="v1.1.0"` — *good catch, the test was right; the production code is wrong*).
- `_gh_release(tag_name) -> str | None` (matching `_publish_pypi`).

### HIGH — `PlatformInfo.requires_ios_destination` is a precomputed property that may not generalize

`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase2.md` lines 323-328. The precomputed form is fine for the current 1-flag case, but consider: Phase 3 (Kotlin) will need `requires_jvm_target`, `requires_android_sdk`, etc. — and possibly multi-platform intersection logic. A method form (`def requires_ios_destination(self) -> bool`) lets Phase 3 introduce additional computed fields without breaking the frozen shape, but a frozen dataclass with multiple booleans forces every site to know about all flags.

However: a frozen dataclass with precomputed booleans is *also* more testable (snapshot equality), more debuggable (`repr` shows the truth), and more honest about its pre-1.0 scope. The real question is whether the *next* platform will add derived flags that share computation.

**Recommendation**: keep precomputed for now, but add a single sentence in the docstring: "Phase 3 (Kotlin) may introduce `requires_jvm_target` as an analogous precomputed bool; both fields will live on a `PlatformInfo`-shaped dataclass per language, since platform semantics differ." This avoids the speculation while flagging the seam.

### HIGH — `lifecycle._commit = _commit  # type: ignore[method-assign]` (six lines) is an API smell

`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase2.md` lines 1603-1608 assign closures onto a pre-constructed instance to override hook methods. Six `# type: ignore[method-assign]` suppressions are a code smell, not a contract.

The cleaner API: pass the hooks at construction time, or use a small builder.

```python
class SwiftLifecycle:
    def __init__(
        self,
        version_source: GitTagVersionSource,
        project_root: Path,
        *,
        commit: Callable[[str], str] | None = None,
        tag: Callable[[str, str], str] | None = None,
        # ...
    ) -> None:
        ...
        self._commit = commit or self._default_commit
```

The `Lifecycle` Protocol doesn't currently enumerate these methods, but the pattern would be: `LanguageAdapterBase.capabilities()` returns a `Lifecycle` instance whose hook methods are *already wired* by the adapter (real subprocess wiring or test closures). Then the MCP tool just calls `lifecycle.run(options)` and never touches internals.

This is also more in line with Phase 1's `PythonLifecycle._commit` etc. being *real* methods, not late-bound attributes. Phase 2 diverges from that pattern by deferring all wiring to the MCP layer.

**Recommendation**: introduce constructor-injected callables in `SwiftLifecycle.__init__`, eliminate the `lifecycle._x = _x` reassignment block. Tests can keep using `mock.patch.object` because the attributes are still on the instance.

### MEDIUM — `Literal["major", "minor", "patch"]` duplicated between `LifecycleOptions.level` and MCP tool signature

`LifecycleOptions.level` (base.py:153) and `swift_bump_version`'s parameter (plan line 1634) both define `Literal["major", "minor", "patch"]`. The MCP tool could re-use `LifecycleOptions.level` via `from __future__ import annotations` + a type alias, or simply import the existing Literal type.

Currently, if Phase 3 wants to add a fourth level (e.g., `"calver"`), it has to find and update both call sites.

**Recommendation**: define `Level = Literal["major", "minor", "patch"]` once at the top of `crackerjack/adapters/base.py`, and import it in the MCP tool module.

### MEDIUM — `_require_auth()` `.lower() != "true"` is case-sensitive and fragile

`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase2.md` lines 1528:

```python
if os.environ.get("MAHAVISHNU_AUTH_ENABLED", "").lower() != "true":
```

`"TRUE"`, `"True"`, `"yes"`, `"1"` all fail. Compare with the crackerjack/oneiric convention — verify whether the spec mandates exactly `"true"` or accepts any truthy value. Spec MCP F5 is referenced but the docstring on `_require_auth` says "set to a falsy value" which is wider than the actual check.

**Recommendation**: either accept any truthy string (`str(...).lower() in {"true", "1", "yes"}`) OR keep strict equality but pin it as the spec convention. The current implementation is strict but the docstring lies about it.

### MEDIUM — `PermissionError` is misleading for an auth failure

`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase2.md` lines 1529, 1534 raise `PermissionError`. Python's `PermissionError` is for OS-level permission failures (`os.open`, file ACLs). For an MCP auth check, the more idiomatic choice is a project-local exception:

```python
class AuthRequiredError(RuntimeError):
    """A mutation tool was called without required auth env vars."""
```

This makes the failure mode searchable (`except AuthRequiredError`) and avoids confusion with OS permission errors that may surface during subprocess handling in the same call stack.

### MEDIUM — MCP return type `dict[str, str | None]` schema is non-uniform

`swift_bump_version` returns `dict[str, str | None]` where `release_url` may be `None`. Clients that build OpenAPI / JSON Schema from this signature will see a heterogeneous value space. Compare with `swift_run_hooks` returning `dict[str, dict]` — homogeneous values, much cleaner.

**Recommendation**: either drop the optional (and pass `""` for "no release") or wrap the result in a typed envelope:

```python
@dataclass(frozen=True)
class SwiftBumpResult:
    new_version: str
    commit_sha: str | None
    tag_name: str | None
    release_url: str | None
```

Then `return SwiftBumpResult(...).model_dump()` or hand-built dict. Either way, the schema is consistent: every field is `str | None` with documented meaning.

## Coverage Statement

All seven review axes requested in the brief were examined:

1. **`PlatformInfo` precomputed vs. method** — covered; precomputed is fine for Phase 2 with a one-line Phase-3 forward note.
2. **`SwiftLifecycle` hook method consistency vs. Phase 1 `PythonLifecycle`** — covered; found two real signature divergences (`_tag` return type, `_gh_release` Optional vs. bare `str`). Plan's "consistent with PythonLifecycle" claim is incorrect for these two methods.
3. **`_bump` module-level duplication** — covered; flagged for extraction before Phase 3.
4. **`SwiftAdapter` extending `LanguageAdapterBase`** — covered; matches the Phase 1 contract exactly (`name = "swift"`, `detect()` and `capabilities()` correctly overridden, returns `Capabilities(version_source=..., hooks=..., has_lifecycle=True)`).
5. **MCP tool signatures** — covered; `Literal["major", "minor", "patch"]` matches `LifecycleOptions.level`; `dict[str, str | None]` serializes to JSON but is non-uniform (flagged); `hook_names: list[str] | None = None` is idiomatic (no change needed).
6. **`_require_auth()` helper** — covered; `.lower() != "true"` is strict, docstring lies about "falsy"; `PermissionError` is misleading for an MCP auth check.
7. **Test mocking API (Pattern B)** — covered; works as designed, tests are deterministic, rollback path is well-exercised.

Additional findings outside the seven axes:

- **`_gh_release` fabricates a fake URL on `gh` failure** (CRITICAL — silent data corruption of `LifecycleResult.release_url`).
- **Six `# type: ignore[method-assign]` suppressions** in `_run_swift_lifecycle` (HIGH — constructor-injected callables would eliminate them and align with Phase 1's "real methods on instance" pattern).
- **`Level` Literal type duplicated** between `LifecycleOptions` and MCP tool (MEDIUM — extract once).

No blockers for execution; the two CRITICAL findings are fix-once-during-implementation items and the HIGH findings are scope expansion candidates. Recommend addressing CRITICALs before Task 7 ships; HIGH findings can be deferred to a Phase 2.1 follow-up if necessary, but extracting `_bump` is best done now to prevent Phase 3 from copying the third instance.
