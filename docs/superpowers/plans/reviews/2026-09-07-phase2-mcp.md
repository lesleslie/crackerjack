# MCP Lens Review — Phase 2 Swift

## Findings (most-severe first)

### BLOCKER 1 — Registration map lives in `crackerjack/mcp/tools/profiles.py`, NOT `crackerjack/mcp/server_core.py`

The plan (Task 7 Step 7.5, lines 1684-1701) instructs the implementer to modify `crackerjack/mcp/server_core.py` and add `"language_tools": language_tools.register_language_tools` to `_build_registration_map()` in that file. This is wrong on both the file and the structure:

- `_build_registration_map()` actually lives in `crackerjack/mcp/tools/profiles.py` (lines 93-129), not `server_core.py`. `server_core.py` only contains a comment block (lines 196-218) describing the pipeline contract.
- `server_core.py` does NOT call `register_language_tools` or any per-group registrar directly. Instead, line 228-248 calls `mcp_common.tools.dispatch._apply_tool_profile(...)` which routes via `REGISTRATION_MAP` (built from `_build_registration_map()` in `profiles.py`) and `PROFILE_REGISTRATIONS` (the `FULL_REGISTRATIONS` / `STANDARD_REGISTRATIONS` / `MINIMAL_REGISTRATIONS` lists in the same file).
- The plan also claims `FULL_REGISTRATIONS` is a `set` (`FULL_REGISTRATIONS = {"language_tools", ...}`). The actual type is `list[str | Callable[[FastMCP], Awaitable[None] | None]]` (line 61). The Python literal the plan shows would fail at runtime.

If the implementer follows the plan literally, they will edit `server_core.py` and end up with either no-op changes (function still in `profiles.py`) or a syntax error (set literal where list is expected). Either outcome means language_tools stay invisible — exactly the silent-invisibility failure mode the 4-step pipeline was designed to prevent.

**Required fix:** Task 7 Step 7.5 must point to `crackerjack/mcp/tools/profiles.py::_build_registration_map()` and the import line 99-114; Step 7.6 must show `FULL_REGISTRATIONS` as a `list` literal with `"language_tools"` appended after `"semantic_tools"`. Cross-reference the W2a migration note (comment lines 84-91 in profiles.py) which states "adding a new group in `_build_registration_map` is enough — no separate edit here" for `register_all_tool_groups`, but a separate edit IS still needed in `FULL_REGISTRATIONS`.

### BLOCKER 2 — Spec MCP F1 step 4 (TEST) is satisfied at the unit level but NOT at the MCP server integration level

Task 7 Step 7.2 / 7.8 unit-tests `register_language_tools` against a local `FastMCP("test")` instance and inspects `mcp_app._tool_manager._tools`. This validates the registration callable, but FastMCP's per-instance tool manager is separate from the running server's manager — a passing unit test does not prove that `create_mcp_server()` actually wires `language_tools` into the profile-dispatched server. The plan's only end-to-end check is Task 8 Step 8.4:

```bash
curl -s http://127.0.0.1:8676/mcp 2>&1 | head -5
```

This is a 5-line dump of the HTTP root. It does NOT verify:

1. That `language_tools` appears in the `discover_tools()` output.
2. That `swift_bump_version` / `swift_run_hooks` / `detect_languages` are reachable via `tools/list`.
3. That `MAHAVISHNU_AUTH_ENABLED=false` correctly refuses `swift_bump_version`.
4. That the FULL profile includes `language_tools` and STANDARD profile does NOT.

Per the spec quote (lines 211-215): "TEST the new tool by: (a) starting the MCP server: `mahavishnu mcp start` (b) calling `discover_tools()` to confirm registration (c) exercising the tool end-to-end via the FastMCP client". The plan only does (a).

**Required fix:** Add a Task 8 Step 8.4b that starts the server with `CRACKERJACK_TOOL_PROFILE=full`, calls `discover_tools(query="swift")` via the FastMCP client transport, and asserts the three tool names appear. Add a second check with `CRACKERJACK_TOOL_PROFILE=standard` and assert NONE of the three appear (mutation tools belong in FULL only). Add a third check: invoke `swift_bump_version` with auth unset and assert `PermissionError` matches `"MAHAVISHNU_AUTH_ENABLED"`.

### HIGH 1 — `_run_swift_lifecycle` is sync but called from an async handler — event loop blocked for 5-30s on push

Task 7 `_run_swift_lifecycle` (lines 1539-1616) calls `subprocess.run(...)` synchronously for `_commit`, `_tag`, `_push`, `_gh_release`. The wrapping tool `swift_bump_version` is `async def` (line 1632) and calls `_run_swift_lifecycle(...)` directly without `await asyncio.to_thread(...)` or `loop.run_in_executor(...)`.

`git push origin <tag>` to a real remote can take 5-30 seconds; `gh release create` can take 10-20 seconds. While these run, the FastMCP event loop is blocked. Any concurrent MCP client (e.g., a Claude session calling `discover_tools()` or `swift_run_hooks`) will stall until the push completes. FastMCP's default concurrency model is single-threaded async — blocking it means the entire MCP server is unresponsive for the duration.

Per spec MCP F7 (quoted line 517-525): "The Jinja formatter runs inside `asyncio.to_thread` so it doesn't block the event loop on multi-file passes". The same rule applies to lifecycle subprocess calls. The plan only applies `asyncio.to_thread` to the Jinja formatter in spec prose; Task 7 forgets to apply it to the Swift lifecycle.

**Required fix:** In `swift_bump_version`, wrap `_run_swift_lifecycle` with `await asyncio.to_thread(_run_swift_lifecycle, Path(project_root), level, release)`. Add `import asyncio` at the top of the module. The existing crackerjack tools do not wrap subprocess in `to_thread` either (per `grep -n "asyncio.to_thread\|run_in_executor"` returning empty), so this is a fresh convention — Phase 2 is a good place to set it.

### HIGH 2 — Auth posture checks env vars at invocation, not at startup; diverges from spec language

Spec MCP F5 (line 482): "until that's done, mutation tools must check for env vars at startup and refuse to operate if absent". The plan's `_require_auth()` (Task 7, lines 1523-1536) is called from inside `swift_bump_version` (line 1641), so the check happens at every invocation, not at startup.

This is a meaningful divergence:

- **Spec intent:** start-up check surfaces the configuration gap to the operator when the server boots, before any client requests are processed. Operator sees a clear "mutation tools disabled — set MAHAVISHNU_AUTH_ENABLED=true and MAHAVISHNU_JWT_SECRET" message and can fix before clients start hitting the server.
- **Plan behavior:** server boots fine; every `swift_bump_version` call raises `PermissionError` until env vars are set. Each client receives a confusing error instead of a server-startup log.

The current `_require_auth()` design does have one advantage: it does not require the operator to know in advance which tool groups include mutation tools. But it loses the startup-time visibility the spec was after.

**Required fix options (pick one):**

1. Honor the spec literally: at module import time (top of `language_tools.py`), call `_require_auth()` and `logger.info(...)` / `logger.warning(...)` accordingly. The per-invocation check stays as a defensive belt-and-suspenders guard but is not the primary failure surface.
2. Document the divergence as an intentional improvement and amend spec MCP F5 in a Phase 2 spec follow-up.

Either way, the plan's Step 7.2 test (lines 1420-1434) only validates the invocation-time check; it does not test startup behavior. Add a startup-time test: import the module with auth unset and assert `PermissionError` (or at least a clear `logger.warning` call captured via caplog).

### HIGH 3 — `swift_run_hooks` does not actually run hooks; it returns metadata

The tool's docstring says "Run the configured Swift hooks against project_root" (line 1649). The implementation (lines 1655-1670) only returns `cli_command`, `autofix`, `timeout_seconds` per hook — it does NOT execute any subprocess. The tool name is `swift_run_hooks`, not `swift_list_hooks` or `swift_describe_hooks`.

An LLM client invoking `swift_run_hooks(project_root="/path")` and expecting "the configured Swift hooks ran" will receive `{hook_name: {cli_command: [...], autofix: bool, timeout_seconds: int}}` and assume the work was done. This is a wire-protocol-vs-name mismatch that will silently produce incorrect outcomes (the LLM thinks hooks passed; the actual code is un-tested).

The plan's CLI counterpart `crackerjack run` actually runs hooks. The MCP surface should match.

**Required fix options:**

1. Rename the tool to `swift_describe_hooks` (or `swift_list_hooks`) and update the docstring to say "Return the configured Swift hooks and their metadata". The MCP surface is then a "describe" tool, distinct from "run".
2. Make the tool actually run the hooks (wrap each `Hook.cli_command` in `asyncio.to_thread(subprocess.run, ...)`) and return per-hook exit codes. This is a more invasive change but matches the name.

The spec (line 39) explicitly says the tool is `swift_run_hooks` — the name is correct per spec, but the implementation does not match the name. Recommend option 2 if Phase 2 has the bandwidth; otherwise option 1 + a spec amendment naming the tool `swift_describe_hooks`.

### MEDIUM 1 — `_run_swift_lifecycle` monkey-patches instance methods after construction, breaking type guarantees

Task 7 Step 7.4 (lines 1602-1608) assigns to `lifecycle._commit = _commit`, etc. on a freshly constructed `SwiftLifecycle` instance. `SwiftLifecycle.__init__` declares `self._version_source` and `self._project_root`, but the methods `_commit`/`_tag`/`_push`/`_delete_tag`/`_reset`/`_gh_release` are declared on the class (Task 5, lines 1136-1152) and raise `NotImplementedError`.

This is technically fine at runtime (Python allows monkey-patching), but it has three problems:

1. **Test surface drift.** The test in Task 7 Step 7.2 line 1449 mocks `_run_swift_lifecycle` directly rather than going through `SwiftLifecycle`. The contract between the MCP tool and the lifecycle is now a closed implementation detail, not the `Lifecycle` Protocol.
2. **Type checker warning.** The `# type: ignore[method-assign]` on every assignment signals mypy knows this is wrong. Crackerjack's CLAUDE.md says "no Any in production code" — method-assign on a non-protocol class is the next-worst thing.
3. **Spec mismatch.** Spec API F9 defines `Lifecycle.run()` as the single public method; instance methods like `_commit` are internal seams for testing. The MCP tool should not be patching them.

**Required fix:** Move the subprocess delegations into `SwiftLifecycle`'s class body (replacing the `raise NotImplementedError` stubs) or into a `_GitService` collaborator passed via `__init__`. The MCP tool then constructs `SwiftLifecycle(version_source, project_root, git_service=GitService())` and calls `lifecycle.run(options)`. Test mocking happens against `GitService.commit` etc., not against the lifecycle's private methods.

### MEDIUM 2 — `swift_run_hooks` return type `dict[str, dict]` is opaque; client can't distinguish "no hooks matched filter" from "all hooks succeeded"

`swift_run_hooks` returns `{hook_name: {"cli_command": [...], "autofix": bool, "timeout_seconds": int}}`. When the caller passes `hook_names=["swift.test"]`, the result is `{"swift.test": {...}}`. When the caller passes `hook_names=["nonexistent.hook"]`, the result is `{}` — empty dict. The MCP client cannot tell whether:

- The filter matched zero hooks (caller bug).
- The hooks ran but all reported empty metadata.
- The project has no Swift capabilities (`detect()` returned False).

Per CLAUDE.md "no Any in production code" and the spec's general JSON-serializability requirement, an envelope pattern would be safer:

```python
{
    "project_root": "/path",
    "detected": True,
    "hooks": {"swift.test": {...}, ...},
    "matched_count": 4,
    "filtered_count": 1,
    "skipped": ["nonexistent.hook"],
}
```

**Required fix:** Add envelope fields. Even minimal: `"project_root": str`, `"detected": bool`, `"hooks": dict`, `"filtered": list[str]` (the names the caller asked for that didn't match any hook).

### MEDIUM 3 — `detect_languages` returns `dict[str, bool]` but the spec says the dict maps "adapter names to detection results" — the bool semantic is overloaded

The plan's `detect_languages` (lines 1672-1681) returns `{name: adapter.detect(root) for name, adapter in adapters.items()}`. With Python and Swift registered, this is `{"python": bool, "swift": bool}`. Two ambiguities:

1. **Missing adapter = not detected = absent from dict.** A third-party adapter not installed via entry points does not appear in the dict. The caller cannot distinguish "not detected" from "not installed".
2. **Detect semantics differ per adapter.** `PythonAdapter.detect()` checks for `pyproject.toml`; `SwiftAdapter.detect()` checks for `Package.swift`. A `True` for both is meaningful, but a `False` for Swift just means "no Package.swift" — it does NOT mean "Swift not used in this project" (Swift source files might still be present).

**Required fix:** Return an envelope:

```python
{
    "project_root": "/path",
    "adapters": {
        "python": {"detected": True, "marker": "pyproject.toml"},
        "swift": {"detected": False, "marker": "Package.swift"},
    },
    "available_adapters": ["python", "swift"],  # entry-point resolved
}
```

This makes the API self-documenting and avoids the bool-only ambiguity.

### LOW 1 — `project_root: str` parameter type

The plan uses `project_root: str` for all three tools (lines 1632, 1645, 1672). FastMCP serializes parameters via Pydantic by default; `Path` is supported as a parameter type via Pydantic's coercion but `str` is the more portable choice across MCP clients (some clients serialize Path poorly). Crackerjack's existing tools (e.g., `pycharm_tools.py` line 53) use `str` for paths. The plan's choice is consistent.

However, internally the tools do `Path(project_root)` immediately — consider validating non-empty up front and raising `ValueError("project_root must be a non-empty string")` for clarity.

### LOW 2 — `_require_auth` matches string `"true"` (case-sensitive in spec, lowercased in plan)

Spec (line 487): `if not os.environ.get("MAHAVISHNU_AUTH_ENABLED") == "true":`. Plan (line 1528): `if os.environ.get("MAHAVISHNU_AUTH_ENABLED", "").lower() != "true":`. The plan's version is more permissive (accepts `True`, `TRUE`, `tRuE`). This is fine but should be a deliberate choice — either both should accept case-insensitive, or neither. Currently the plan improves on the spec without justification.

**Required fix:** Either match the spec verbatim (`== "true"`) or document the case-insensitive rationale in a code comment. Inconsistency between spec and impl is a future reviewer hazard.

### LOW 3 — `swift_bump_version` result dict has no `"dry_run"` field for the dry_run case

`_run_swift_lifecycle` always returns the same dict shape regardless of `LifecycleOptions.dry_run`. When dry_run is True, `result.commit_sha`, `result.tag_name`, `result.release_url` are all `None` — the caller cannot distinguish "dry_run completed successfully" from "real run that failed mid-flow". Spec MCP F2 mentions `LifecycleResult.skipped_steps` for this purpose; the plan's dict drops it.

**Required fix:** Include `skipped_steps` in the returned dict:

```python
return {
    "new_version": result.new_version,
    "commit_sha": result.commit_sha,
    "tag_name": result.tag_name,
    "release_url": result.release_url,
    "skipped_steps": list(result.skipped_steps),  # e.g., ("dry_run",)
}
```

## Coverage Statement

All seven review areas in the brief were examined:

1. **4-step registration pipeline** — covered. Two BLOCKER findings: file location wrong (`profiles.py`, not `server_core.py`); FULL_REGISTRATIONS is a `list`, not a `set`.
2. **Tool signatures** — covered. `swift_bump_version`, `swift_run_hooks`, `detect_languages` types reviewed; `detect_languages` `dict[str, bool]` flagged as ambiguous (MEDIUM 3).
3. **Async/sync split** — covered. HIGH 1: `_run_swift_lifecycle` blocks the event loop on push.
4. **Auth posture** — covered. HIGH 2: plan checks at invocation, spec says startup; LOW 2 case-sensitivity drift; LOW 5 missing startup test.
5. **Tool description strings** — covered. HIGH 3: `swift_run_hooks` docstring says "run" but implementation only describes; major wire-protocol mismatch.
6. **Rollback contract** — covered. MEDIUM 1: monkey-patching instance methods after construction; LOW 3: `skipped_steps` dropped from output dict.
7. **Lifecycle run output** — covered. JSON-serializable as `dict[str, str | None]`; LOW 3 envelope improvements.

The plan is structurally sound but has a registration pipeline location error that will silently produce invisible tools. Spec MCP F1 was added precisely to prevent this class of bug. Fix BLOCKER 1 and BLOCKER 2 before implementation; the rest are quality improvements that can land in the same Task 7 or as follow-ups.
