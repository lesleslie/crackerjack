## BLOCKER-1 — The Jinja formatter silently destroys whitespace around `{%-` / `-%}` markers

**Severity:** BLOCKER · **Confidence:** Certain (verified by execution)
**Location:** Task 4, Step 4 — `format_template`, the line `reconstructed = "".join(value for _, _, value in tokens)`

**What's wrong.** `Environment.lex()` does *not* return a lossless token stream. Jinja's `tokeniter` **applies whitespace-control stripping while tokenizing**, so the data token adjacent to a `{%-` has already had its whitespace removed, and the `-%}` token value has *absorbed* the following space. Joining token values therefore does not reconstruct the source.

Verified against `jinja2` in this repo's venv:

```
source:  'A {%- if x -%} B'
tokens:  [(1,'data','A'), (1,'block_begin','{%-'), ..., (1,'block_end','-%} '), (1,'data','B')]
rejoin:  'A{%- if x -%} B'          <-- the space before {%- is GONE
```

Running the plan's full `format_template` end-to-end:

```
'A {%- if x -%} B\n'  ->  'A{%- if x -%} B\n'     CHANGED
```

**Why it matters.** This is the exact failure mode Tier 1 rule 3 exists to prevent ("preserve `{%-` / `-%}` / `{{-` / `-}}`"). The plan preserves the *marker glyphs* while deleting the whitespace the markers were controlling — the worst of both worlds. `format_jinja_templates` writes files in place (Task 6), with no diff, no dry-run, and no backup, so this corrupts real templates on first run. Spec Jinja F1 lists the `lex()` caveats but the plan implements none of the compensations.

The plan's own test does not catch it: `test_format_preserves_whitespace_control_markers` asserts only `"{%- if x -%}" in result`, which is **true** for the corrupted output. See HIGH-6.

**How to fix.** Do not reconstruct from token values. Either:
1. **Recommended for Phase 4 Tier 1:** drop `lex()` from the Tier-1 path entirely. Tier 1's three rules (trailing newline, strip trailing whitespace, preserve markers) are pure text operations that require no tokenization — operate on the raw string and you get preservation for free. Use `lex()` only as a *validation* pass (catch `TemplateSyntaxError`, bail out unchanged) and later as the Tier-2 span locator.
2. If token-driven rewriting is required, use `env.lexer.tokeniter(source, ...)` positions to slice the **original source** rather than emitting token values, so untouched regions are byte-identical.

Either way, add a test asserting `format_template(s) == s` for `'A {%- if x -%} B\n'`.

## BLOCKER-2 — Tier 2 normalization regex deletes characters from every tag

**Severity:** BLOCKER · **Confidence:** Certain (verified by execution)
**Location:** Task 4, Step 4 — `_normalize_one_space_inside_delimiters`

**What's wrong.** The pattern is `{% (\S)(.*?)(\S) %}` and the replacement is `f"{open_d} {m.group(2)} {close_d}"` — groups 1 and 3 are captured and then **thrown away**.

Verified, running the plan's own Tier-2 test input:

```
'{%if x%}A{%endif%}\n'  --normalize=True-->  '{% f  %}A{% ndi %}\n'
```

`if` lost its `i`, `x` vanished entirely, `endif` became `ndi`. Three additional defects in the same six lines:

- `{{x}}` and `{#c#}` are **unchanged** — the pattern needs ≥2 non-space characters, so single-token expressions never match.
- `re.DOTALL` + non-greedy `.*?` can still span from one tag's opener to a *later* tag's closer when the first tag is short, because there is no "no closing delimiter in between" guard.
- The nested `def repl` inside a `for` loop closes over the loop variables `open_d`/`close_d` — correct here only because `re.sub` is called inside the same iteration; it is a latent late-binding trap.

**Why it matters.** Tier 2 is the opt-in tier the spec names as writing to user files (`[tool.crackerjack.jinja] normalize = true`). This is unambiguous data destruction. The plan's own `test_tier2_when_normalize_true` (`assert "{% if x %}" in result`) **will fail at Task 4 Step 5**, so the plan is internally inconsistent — an implementer following it verbatim will be stuck.

**How to fix.** Match the delimiters and capture the *entire* body:

```python
pattern = re.escape(open_d) + r"(-?)\s*(.*?)\s*(-?)" + re.escape(close_d)
# replacement: f"{open_d}{m['1']} {m['2'].strip()} {m['3']}{close_d}"
```
Preserve the `-`/`+` whitespace-control sigils explicitly (they sit *inside* the delimiter), skip bodies that are already canonical (idempotence), and add tests for `{{x}}`, `{#c#}`, `{%- if x -%}`, and two adjacent tags on one line.

## BLOCKER-3 — The hybrid fallback is unreachable for all three hooks

**Severity:** BLOCKER · **Confidence:** Certain
**Location:** Task 3, Step 5 — `run_hook_with_fallback` + `_npx_command`

**What's wrong.** The gate is:

```python
cli_name = hook.cli_command[0]
if cli_name != "npx" and shutil.which(cli_name) is None:
    ... invoke fallback ...
```

All three hooks default to the `_npx_command(...)` branch, so `cli_name == "npx"` and the fallback branch is **skipped unconditionally**. The Python fallback only becomes reachable in the `package.json`-pinned branch — and that branch is itself inverted (see BLOCKER-4). Net effect: in the default path (`package.json` present but tools not installed), no fallback ever runs.

Compounding:
- `shutil.which("npx")` is never checked. If Node isn't installed at all, `subprocess.run(["npx", ...])` raises an uncaught `FileNotFoundError` — the hook crashes rather than falling back or emitting install instructions.
- `npx --no-install` exits non-zero when the package isn't locally present; the code logs a warning and returns `[]` (see HIGH-1), so "tool not installed" is reported as **clean**, not as "fallback engaged".

**Why it matters.** Spec Writing F2 mandates one canonical interpretation: *CLI missing AND fallback set → invoke fallback; fallback also fails → fail with install instructions*. The plan states this correctly in Global Constraints (line 40) and in the `run_hook_with_fallback` docstring, then implements the opposite. This is the single most load-bearing behavior of Phase 4's hook design.

**How to fix.** Decide missing-ness on the **underlying tool**, not the launcher:

```python
tool = hook.cli_command[2] if hook.cli_command[0] == "npx" else hook.cli_command[0]
launcher_present = shutil.which("npx") is not None if hook.cli_command[0] == "npx" else True
tool_present = launcher_present and _npx_can_resolve(project_root, tool)  # `npx --no -- <tool> --version`, rc==0
```
Then apply the three-way F2 decision. Add the mandatory two-path test pair per hook (see HIGH-5).

## BLOCKER-4 — `npx` / pinned-dependency logic is inverted; bare CLI names are not on `PATH`

**Severity:** BLOCKER · **Confidence:** High
**Location:** Task 3, Step 5 — `_css_hook`, `_eslt_hook`, `_html_hook`

**What's wrong.** The plan does:

- pinned in `devDependencies` → invoke **bare** `("stylelint", "**/*.css")`
- not pinned → invoke **`npx`**

This is backwards. A package pinned in `devDependencies` lives in `node_modules/.bin/`, which is **not on `PATH`** — `shutil.which("stylelint")` returns `None`, and `subprocess.run(["stylelint", ...])` raises `FileNotFoundError`. `npx` exists precisely to resolve `node_modules/.bin` first. Conversely, for an *unpinned* tool, `npx --no-install` cannot resolve anything and will fail.

Spec line 365 says it the right way round: "Commands run via `npx` unless `package.json` pins them" — but that sentence is about *version selection*, and the only correct mechanism for the pinned case is still `npx` (or an explicit `node_modules/.bin/<tool>` path).

**Why it matters.** Both branches are broken: the pinned branch raises, the unpinned branch cannot resolve. Neither reaches the fallback (BLOCKER-3). Every Web hook is non-functional on every project.

**How to fix.** Always route through `npx --no-install` (or resolve `project_root / "node_modules/.bin" / tool` directly and fall back to `npx`). Use `_has_pinned_version` only to record the expected version in the hook's metadata / warning text, not to switch invocation strategy.

## BLOCKER-5 — `web.eslint_tsc` never runs `tsc`; `";"` is passed as a literal argv token

**Severity:** BLOCKER · **Confidence:** Certain
**Location:** Task 3, Step 5 — `_eslt_hook`

**What's wrong.** The command is built as:

```python
cmd = _npx_command("eslint", ".", "--ext", ".ts,.tsx,.js,.jsx") + (";", "tsc", "--noEmit")
```

With `shell=False` (correctly mandated by Global Constraints line 30), `;` is **not a separator** — it is an argument. eslint receives `;`, `tsc`, and `--noEmit` as *file paths to lint*, then `run_hook_with_fallback` appends `str(project_root)` as a fourth. eslint errors on the nonexistent paths; `tsc --noEmit` never executes. The plan's own comment ("the runner treats as sequential") describes a runner that does not exist.

The plan's test `test_eslint_tsc_hook_combines_eslint_and_tsc` asserts only that both substrings appear in the joined argv — it passes on broken input.

**Why it matters.** Spec line 47 lists `eslint` **and** `tsc --noEmit` as the JS/TS hook. TypeScript type checking — arguably the highest-value Web check — silently never runs, while the hook reports itself present in `check_web_lint`.

**How to fix.** `Hook.cli_command` is a single argv tuple; it cannot express two commands. Either:
1. Split into two hooks: `web.eslint` and `web.tsc`. Simplest, matches the `Hook` dataclass, and gives independent timeouts and independent fallbacks. Update the three name-set assertions accordingly.
2. Or extend `Hook` (in `adapters/base.py`) with `cli_commands: tuple[tuple[str, ...], ...]` — but that is a Phase-1 contract change and out of Phase 4's stated scope.

Recommend option 1.

## BLOCKER-6 — MCP tools are added at module top level; `mcp_app` is undefined

**Severity:** BLOCKER · **Confidence:** Certain
**Location:** Task 6, Step 3 — "Append to `crackerjack/mcp/tools/language_tools.py`"

**What's wrong.** In the existing file, `mcp_app` is a **parameter** of `register_language_tools(mcp_app: FastMCP) -> None` (line 176), and every tool is a nested `async def` inside it. The plan's snippet places `@mcp_app.tool()` at module scope. That is a `NameError` at import time — the entire `language_tools` module fails to import, taking Swift's three tools down with it.

**How to fix.** Indent both tool definitions one level, inside `register_language_tools`, alongside `swift_bump_version` / `swift_list_hooks` / `detect_languages`. Update the docstring header at line 177 ("Phase 2: Swift") to mention Phase 4.

## BLOCKER-7 — Every new MCP test calls `asyncio.run()` from inside a running loop

**Severity:** BLOCKER · **Confidence:** Certain
**Location:** Task 6, Step 1 — all four new tests

**What's wrong.** The new tests are declared `async def test_...`. With `asyncio_mode = "auto"`, pytest already runs them inside an event loop. Their bodies then call `asyncio.run(_register())` and `asyncio.run(tool.fn(...))` → `RuntimeError: asyncio.run() cannot be called from a running event loop`.

The existing tests in that file avoid this by being **sync** `def test_...` that wrap an inner coroutine in `asyncio.run` (verified at `tests/mcp/tools/test_language_tools.py:24-32`). The plan mixed the two idioms.

**Why it matters.** All four tests error at collection/run. Task 6 Step 4's stated "17 passed" is unreachable.

**How to fix.** Match the file's existing style: either make the tests sync and keep `asyncio.run`, or keep them `async def` and `await` directly (`_, tools = await _register()`; `result = await tool.fn(...)`; `with pytest.raises(...): await tool.fn(...)`). The latter is cleaner. Also note `test_check_web_lint_rejects_python_project_no_opt_in` never creates `package.json` **and** never writes `pyproject.toml`, so `_validate_project_root` runs first — confirm the env var is set before the `ValueError` is expected, or the test fails with `PermissionError` instead.

## HIGH-1 — Hooks always report clean; `check_web_lint` is a wire-up illusion

**Severity:** HIGH · **Confidence:** Certain
**Location:** Task 3, Step 5 — `run_hook_with_fallback` CLI path, `return []` at the end

**What's wrong.** On the CLI path, a non-zero exit is logged at WARNING and the function returns `[]`. The plan labels output parsing "a Phase 4.5 concern." So `web.stylelint` / `web.eslint_tsc` / `web.html_validate` can never surface a single issue.

**Why it matters.** This is exactly the `mcp-surface-health-illusion` pattern already recorded for this ecosystem: 3 registered hooks, a green `check_web_lint`, tests passing — and zero findings, ever. **How to fix.** Minimum viable for Phase 4: parse the JSON formatters all three tools ship (`stylelint -f json`, `eslint -f json`, `html-validate -f json`, and `tsc`'s line-oriented `file(line,col): error TSxxxx:` output) into the `(path, line, message)` shape the fallbacks already return. This is ~40 lines, not a phase. If it genuinely must be deferred, `check_web_lint` must report `status: "degraded"` and the hooks must be excluded from any pass/fail gate — do not ship a green surface over a dead feed.

## HIGH-2 — Fallbacks are handed a directory and silently return clean

**Severity:** HIGH · **Confidence:** Certain
**Location:** Task 3, Step 5 — `paths = file_paths or [project_root]`

**What's wrong.** When `file_paths` is `None` (the default, and what the MCP tool would pass), the fallback receives `project_root` — a directory. `css_fallback` immediately does `path.read_text()` → `IsADirectoryError`, which is an `OSError`, which is caught by `except (OSError, UnicodeDecodeError): return []`.

## HIGH-3 — `eslint --ext` and `.eslintrc.json` are removed in ESLint 9+

**Severity:** HIGH · **Confidence:** High
**Location:** Task 3 `_eslt_hook`; Task 7 fixture `.eslintrc.json`

**What's wrong.** `npx` with no pin resolves the **latest** eslint. In ESLint 9, flat config (`eslint.config.js`) is the default and `--ext` was removed — it is an unrecognized option, a hard failure, not a warning. Legacy `.eslintrc.json` is likewise not read without `ESLINT_USE_FLAT_CONFIG=false` (itself removed in 10). The plan's fixture pins `eslint: ^8.0.0` in `package.json`, so the *fixture* is self-consistent — but the unpinned `npx` path (the default for real projects, per BLOCKER-4) targets 9/10.

The plan's Step 1 pre-flight only runs `npx eslint --version`; it never validates the **flags**. Note also that in this environment `npx <tool> --version` for an uninstalled tool would attempt a download without `--no-install` — the pre-flight commands as written are not `--no-install`-guarded.

**Why it matters.** The JS/TS hook fails on any project using a modern eslint, which is now the majority.

**How to fix.** Drop `--ext` (flat config derives extensions from the config's `files` globs). Detect config flavor: if `eslint.config.{js,mjs,cjs,ts}` exists use flat; if only `.eslintrc*` exists, warn that eslint ≥9 requires migration. Update the fixture to flat config, or keep `^8` and add a second fixture on `^9` to pin the difference. Extend Step 1's pre-flight to exercise the **exact argv** each hook will emit, with `--no-install`.

## HIGH-4 — Tier 2 is unreachable from any user-facing surface; no CLI subcommand at all

**Severity:** HIGH · **Confidence:** Certain
**Location:** Task 6 `format_jinja_templates`; absence of a CLI task

**What's wrong.** Two wiring gaps:

1. **No config read.** Spec Jinja F3 names the switch `[tool.crackerjack.jinja] normalize = true`; spec Data Flow step 3 requires loading **all 6 delimiter keys** from `[tool.crackerjack.jinja]`. `format_jinja_templates` calls `format_template(path.read_text())` with neither `delimiters=` nor `normalize=`. So Tier 2 can only be reached from Python, and **custom delimiters — the entire motivating use case (fastblocks' `[%`, `[[`, `[#`)** — are never applied by the shipped tool. The delimiter support is implemented and then not connected.
2. **No CLI.** Spec line 55 requires "CLI + MCP mirror for every new feature"; Data Flow line 572 names `crackerjack web jinja format src/templates/`. The plan's Tech Stack line mentions "typer 0.26+ for CLI surface" but no task creates any command.

**Why it matters.** Directly violates crackerjack's own wire-up contract (`.claude/decisions/wire-up-contract.md`): a feature that is built but not reachable is not done. A Jinja formatter that cannot read fastblocks' delimiters cannot format fastblocks — the named Phase 4 target (spec line 713).

**How to fix.** Add a `_load_jinja_config(project_root) -> tuple[Mapping[str,str], bool]` reading `[tool.crackerjack.jinja]` (6 delimiter keys + `normalize`, each defaulting), call it in the MCP tool, and add Task 6b for the `crackerjack web jinja format` typer command. Add an Integration Contract block per `docs/plans/TEMPLATE.md`.

**Severity:** HIGH · **Confidence:** Certain (verified)
**Location:** Task 4, Step 2 — five of the nine tests

Specific blind spots, each verified against the plan's own implementation:

Task 7's `test_web_vanilla_fixture.py` only checks detection and hook names.

**How to fix.** Add `.expected` files beside each input; parametrize over the corpus asserting `format_template(input) == expected` **and** `format_template(expected) == expected`. Add explicit cases: leading whitespace before `{%-`, trailing whitespace after `-%}`, a template already ending in `\n\n`, a CRLF template, `{% raw %}` containing `{{ }}`, and a nested-quote expression `{{ "}}" }}`.

## HIGH-7 — Python fallbacks will produce false positives on real files

**Severity:** HIGH · **Confidence:** High
**Location:** Task 3, Step 4 — all three fallbacks

All three are naive character/regex scanners with no string, comment, or context awareness:

- **`js_ts_fallback`** counts braces with no awareness of string literals, template literals, regex literals, or comments. `const s = "}";` reports *"Unbalanced closing brace."* On any real TS file this is close to guaranteed. Its docstring also claims it catches "unclosed strings" — it never inspects strings at all.
- **`css_fallback`** same brace problem: `content: "}"` and `/* } */` both misfire. The empty-rule regex `[^{}]+\{\s*\}` also flags legitimately empty `@media`/`@supports` blocks.
- **`html_fallback`** has four distinct defects: (a) `[a-zA-Z][a-zA-Z0-9]*` excludes `-`, so every custom element (`<my-widget>`) and every Angular/Vue-style tag mis-parses; (b) `[^>]*?>` breaks on `>` inside attribute values (`<input value="a>b">`); (c) HTML5 **optional end tags** (`<li>`, `<p>`, `<tr>`, `<td>`) are treated as unclosed → dozens of false errors per real page; (d) `<script>` bodies containing `a < b` generate phantom tags.

**Why it matters.** A fallback that fires spuriously is worse than no fallback — it trains users to ignore the hook. And because the fallback is what runs when the CLI is absent, the *unconfigured* project (the common case) gets the noisiest experience.

**How to fix.** Two options, both better than the current code:
1. Use stdlib/available parsers: `html.parser.HTMLParser` (handles void + optional-end elements, attribute quoting) for HTML; `tinycss2` (pure-Python, small) for CSS. For JS/TS there is no reasonable pure-Python parser — make `web.eslint_tsc` `cli_required=True` with **no** fallback and rely on spec's third F2 row ("fail with installation instructions"). Spec permits this; `Hook.fallback` defaults to `None`.
2. If the naive scanners are kept, restrict them to a single check each with near-zero false-positive rate (e.g. HTML: unclosed `<!-- -->` only) and document the narrowness in the docstring. Do not claim checks the code does not perform.

Either way, add negative tests: a valid file containing `"}"` in a string must yield zero issues. The plan's current tests only assert `isinstance(issues, list)`, which passes for any behavior.

## MEDIUM-3 — `subprocess.run` is blocking and has no timeout

**Severity:** MEDIUM · **Confidence:** Certain
**Location:** Task 3, Step 5 — `run_hook_with_fallback`

Two constraint violations in one call:
- Global Constraints line 29: "All I/O async. Subprocess via `asyncio.to_thread`." `run_hook_with_fallback` is a plain `def` doing blocking `subprocess.run`. If the MCP handler ever calls it, the event loop stalls for up to the hook's duration. (The existing Swift tool does this correctly — `await asyncio.to_thread(_run_swift_lifecycle_sync, ...)` — so the pattern to copy is right there.)
- `Hook.timeout_seconds` is set (300/300/600) and then never passed to `subprocess.run(timeout=...)`. Spec's error table requires "Fail hook; report timeout duration." A hung `npx` blocks indefinitely.

Also missing: the `--` separator before user-influenced positionals (Global Constraints line 30), and `check=False` is implicit but should be explicit.

## MEDIUM-4 — `npx --no-install` is a legacy alias; and it does not by itself close the network question

**Severity:** MEDIUM · **Confidence:** High (verified)
**Location:** Task 3, Step 5 — `_npx_command`

Verified on this machine (`npm 12.0.2`, `node v26.8.1`): `npx --no-install --version` exits 0, so the flag is still accepted — but it is **not listed in `npx --help`**. The documented modern spelling is `npx --no` (or `npm exec --no --`). Relying on an undocumented back-compat alias in a pinned toolchain is a slow-motion break.

On the review question "does `--no-install` prevent silent network calls": yes for the *package fetch* — npx errors instead of downloading. But (a) it does not protect against a locally-installed package's own network activity, and (b) as written the non-zero exit is swallowed (HIGH-1), so the protection produces a false-green rather than a fallback. Fix the flag spelling *and* the error handling together.

## MEDIUM-5 — `WebAdapter.name` annotated as instance variable, overriding a `ClassVar`

**Severity:** MEDIUM · **Confidence:** High
**Location:** Task 5, Step 3 — `name: str = "web"`

`LanguageAdapter` / `LanguageAdapterBase` declare `name: ClassVar[str]` (`adapters/base.py:113, 129`). `name: str = "web"` re-annotates it as an instance variable; mypy strict reports *"Cannot override class variable with instance variable."* The existing Swift adapter uses bare `name = "swift"` (no annotation), which inherits the `ClassVar`. ## MEDIUM-7 — CRLF and multi-trailing-newline handling absent

**Severity:** MEDIUM · **Confidence:** Certain (verified)
**Location:** Task 4, Step 4

Spec Jinja F1 lists two `lex()` caveats explicitly: it strips a missing trailing newline (*"restore from raw input"*) and it **normalizes CRLF → LF** (*"preserve CRLF flag from raw input if needed"*). The plan implements neither properly:

- Trailing newline: the code unconditionally appends exactly one `\n`. Verified: `'end\n\n\n'` → `'end\n\n'` → `'end\n'`. Files lose trailing blank lines, one per run, which is also why the round-trip invariant is false (HIGH-6).
- CRLF: not mentioned anywhere in the plan. A CRLF template silently becomes LF on the first `format_jinja_templates` run — a whole-file diff on a Windows-authored template.

Fix: capture the source's line ending and trailing-newline count before lexing; restore both after. Add tests for `\r\n` input and for `'x\n\n'`.

## LOW-1 — Dead `tomli` fallback in `detection.py`

## Plan quality verdict

**Not ready for execution.** Seven BLOCKERs, of which four (1, 2, 5, 7) were reproduced by running the plan's own code and tests rather than inferred from reading. Two of the plan's own tests (`test_tier2_when_normalize_true`, and all four MCP tests) will fail at their designated verification steps, so an implementer following the plan verbatim gets stuck at Task 4 Step 5 and Task 6 Step 4 — the plan cannot be executed end to end as written.

**What the plan gets right, and should be preserved unchanged.** The detection guard (Task 2) is the best-specified piece of work here: correct semantics, fail-closed on malformed TOML, both-signals precedence handled, and eight tests that map one-to-one onto the spec's stated risk. Task 5's `WebAdapter` correctly honors the no-lifecycle constraint rather than inventing a version story. Task 1's entry-point form matches the repo's actual `module:Class` convention (the spec's module-only form at line 96-101 is stale — worth a spec amendment note). And the choice of `lex()` over `parse()` is right; only the reconstruction is wrong.

**The structural problem.** In four separate places the plan states a constraint correctly in prose and then contradicts it in the adjacent code block: Writing F2 (line 40 vs. the `cli_name != "npx"` guard), Jinja F1 marker preservation (line 47 vs. `"".join`), argv-no-shell (line 30 vs. the literal `";"`), and MCP nested-registration (line 35 vs. top-level `@mcp_app.tool()`). The prose was written from the spec; the code was written from intuition, and the two were never reconciled. That pattern also explains the vacuous tests — they were written to match the prose, so they pass against code that violates it. Any revision should treat "does the code block actually do what the sentence above it says" as the primary review question, per test.

**A second structural concern:** three independent paths all terminate in a false-green — CLI success unparsed (HIGH-1), fallback handed a directory (HIGH-2), fallback unreachable (BLOCKER-3). Fixing any one still leaves a green surface over a dead feed. This is the `mcp-surface-health-illusion` pattern verbatim, and crackerjack's own `mcp-backend-wiring-discipline.md` prohibits shipping it. Whatever else changes, Phase 4 must not register `check_web_lint` as healthy until at least one hook can return a real finding from a real file.

**Recommended path forward.** Rather than patching, I'd restructure the two weakest tasks:

- **Task 3 → split.** `web.stylelint`, `web.eslint`, `web.tsc`, `web.html_validate` as four single-argv hooks. One shared `run_hook` with correct `npx` resolution, per-hook timeout, `asyncio.to_thread`, JSON output parsing, and the F2 three-way decision. Drop the JS/TS Python fallback (`cli_required=True`, no fallback) — spec permits it and the alternative is a false-positive machine. Keep narrow, honest fallbacks for CSS and HTML using `tinycss2` and `html.parser`.
- **Task 4 → rewrite Tier 1 as pure text.** Tier 1's three rules need no tokenizer; doing them on the raw string makes marker preservation automatic and the round-trip invariant true by construction. Use `lex()` for syntax validation and, later, for Tier-2 span location. Then build the golden-master corpus first and let it drive the implementation.

Estimated rework: Tasks 3 and 4 substantially rewritten, Task 6 restructured (nesting + config wiring + `dry_run`), Task 7 extended (`.expected` files, `mixed` fixture, registry-fixture rebuild), plus a new Task 6b for the CLI mirror. Tasks 1, 2, and 5 can ship as written with the one-line `name = "web"` change from MEDIUM-5.
