## Findings (most-severe first)

### F1 (CRITICAL) — MCP tool docstrings are terse and screen-reader-unfriendly

The two new `@mcp_app.tool()` docstrings (Task 7, Step 3) are nearly content-free:

```python
@mcp_app.tool()
async def kotlin_bump_version(
    level: str,
    project_root: str,
    dry_run: bool = False,
    release: bool = False,
) -> dict:
    """Bump Kotlin/Gradle project version (mutation; auth required)."""

@mcp_app.tool()
async def kotlin_list_hooks(project_root: str) -> dict:
    """Return Kotlin/Gradle hook metadata (read-only; no auth)."""
```

Screen readers will announce `kotlin_bump_version` and read aloud exactly: *"Bump Kotlin/Gradle project version (mutation; auth required)."* — then the user has no way to learn:

- What values `level` accepts (`"major"`, `"minor"`, `"patch"`).
- What `dry_run` does (skips commit/tag/push).
- What `release` does (creates a GitHub release via `gh`).
- What `project_root` must contain (`build.gradle.kts` or `build.gradle`).
- **Where the version is written** (gradle.properties, NOT build.gradle.kts) — this is non-obvious and easy to confuse.
- What the return dict shape is (`new_version`, `commit_sha`, `tag_name`, `release_url`, `skipped_steps`).

For `kotlin_list_hooks` the user gets no hint that the return shape is a `dict[str, dict[str, Any]]` keyed by hook name.

**Better** (mirroring Phase 2 F1):

```python
@mcp_app.tool()
async def kotlin_bump_version(
    level: Literal["major", "minor", "patch"],
    project_root: str,
    dry_run: bool = False,
    release: bool = False,
) -> dict:
    """Bump a Kotlin/Gradle project version and create a git tag.

    Reads the current version from gradle.properties (probing keys
    `pluginVersion`, `projectVersion`, then `version`; falling back to
    `build.gradle.kts` and finally `./gradlew properties`). Bumps per the
    requested level using real semver (major bumps major, minor bumps minor,
    patch bumps patch — same as PythonLifecycle). Writes the new version to
    gradle.properties (NOT build.gradle.kts), commits, tags `vX.Y.Z`, and
    pushes the tag. When `release=True`, creates a GitHub release via `gh`.

    Args:
        level: One of `"major"`, `"minor"`, `"patch"`.
        project_root: Absolute path to a directory containing build.gradle.kts
            (or build.gradle). The path must be in MAHAVISHNU_PROJECT_ROOTS.
        dry_run: If True, compute the new version but skip commit/tag/push/release.
        release: If True, also create a GitHub release via `gh release create`.

    Returns:
        dict with keys: `new_version`, `commit_sha`, `tag_name`, `release_url`,
        `skipped_steps` (tuple of step names that were not executed, e.g.
        `("dry_run",)` or `("release",)`).

    Raises:
        PermissionError: MAHAVISHNU_AUTH_ENABLED and MAHAVISHNU_JWT_SECRET unset.
        ValueError: project_root does not contain build.gradle(.kts).
        RuntimeError: git/gh subprocess failed; rollback best-effort.
    """
```

### F2 (CRITICAL) — Spec/Plan MCP tool name drift will silently register the wrong tool

The spec (Rev 2, line 44) defines the Kotlin MCP tools as:

> **MCP tools**: `kotlin_bump_version` (mutation; auth required), `kotlin_run_hooks`.

The plan (Task 7, Step 3; line 988) defines:

> Two new `@mcp_app.tool()` async functions:
> - `kotlin_bump_version(level: Literal["major", "minor", "patch"], project_root: str, dry_run: bool = False, release: bool = False) -> dict` (mutation; auth required per spec MCP F5)
> - `kotlin_list_hooks(project_root: str) -> dict` (read-only; returns 3 hook names + gradle task probe results)

The spec calls the second tool `kotlin_run_hooks`; the plan calls it `kotlin_list_hooks`. **Phase 2 established `swift_run_hooks` for Swift** (F4 Phase 2 finding), so the spec is consistent with its own Phase 2 precedent — but the plan breaks that naming. Either:

- **Spec is correct, plan is wrong**: rename to `kotlin_run_hooks` and actually run the hooks (which contradicts the current plan, which only returns hook *metadata*).
- **Plan is correct, spec is wrong**: rename to `kotlin_list_hooks` everywhere (the spec must be amended).

This is a contract drift between spec and plan. Whichever name wins, the other document must be updated. **Why it matters:** an MCP client written against the spec will call `kotlin_run_hooks()` and get a tool-not-found error. Worse, screen-reader navigation depends on stable tool names; if the same conceptual tool has two different names across docs, the discoverability for non-sighted users collapses.

**Fix:** update the spec line 44 to say `kotlin_list_hooks`, OR update the plan to define `kotlin_run_hooks` (and have it actually invoke the hooks). Pick one. Mirror Phase 2's `swift_run_hooks` for consistency: call it `kotlin_run_hooks` and have it run the hooks.

### F3 (CRITICAL) — `_require_auth_config()` error messages inherit Phase 2 F2 verbatim

The plan inherits the auth check from Phase 2 (Task 7, Step 3 calls `_require_auth_config()`). Phase 2's a11y review (F2) called out:

### F4 (HIGH) — Spec Kotlin F2 "skip-with-warning" is documented in a comment but not implemented in code

The plan (Task 3, Step 3) explicitly states:

```python
def hook_with_probe(name: str, *cli_command: str) -> Hook:
    # If probe fails (task absent), the hook still emits; CLI invocation
    # will skip-with-warning at execution time. This matches spec Kotlin F2.
    return Hook(name=name, cli_command=(*gradlew, *cli_command))
```

The comment promises a warning emission. But:

- `GradleTaskProbe.has_task()` is defined but is **never called** anywhere in `hooks.py`.
- The `Hook` dataclass (Phase 1, frozen) has no `cli_required` / `on_missing_task` field shown in the plan.
- The plan has no code path that emits a warning, logs a `WARNING` line, or surfaces a "this hook was skipped because ktlintCheck task is not registered" message to the user.
- The spec (line 355–357) says: *"if absent, skip-with-warning"* — the implementation gap is in the plan, not the spec.

**Why this matters for a11y:** a Gradle project that doesn't apply the ktlint plugin will run `./gradlew ktlintCheck` (because `hook_with_probe` returned a Hook unconditionally), get a non-zero exit ("task 'ktlintCheck' not found in root project"), and the user will see a stack trace with no actionable hint that they need to apply the `org.jlleitschuh.gradle.ktlint` plugin to `build.gradle.kts`. **A screen reader reading the stack trace gets zero remediation.**

**Better:** wire the probe into the hook metadata so that the hook runner (Phase 1) can detect the absent-task case before subprocess invocation and emit a structured warning. At minimum, add a `test_kotlin_ktlint_skips_with_warning_when_task_absent` test that asserts a `WARNING` log line containing "ktlintCheck task not found; skipping. Apply the org.jlleitschuh.gradle.ktlint plugin to your build.gradle.kts." A non-sighted user running this test gets both the missing-task condition AND the remediation hint in one assertion.

### F5 (HIGH) — `VersionNotFoundError` messages lack remediation hints

Two error paths in `GradlePropertiesVersionSource`:

```python
if result.returncode != 0:
    raise VersionNotFoundError(f"`gradlew properties` failed: {result.stderr}")

m = re.search(r"^version:\s*(\S+)", result.stdout, re.MULTILINE)
if not m:
    raise VersionNotFoundError("`gradlew properties` did not emit a `version:` line")
```

Neither message tells the user **how to fix it**. The first dumps raw stderr (helpful for experts, hostile for novices — a Gradle stack trace dumps 30+ lines of JVM noise). The second says "did not emit" but not "add `version = \"X.Y.Z\"` to your `build.gradle.kts` or `gradle.properties`".

**Better:**

```python
raise VersionNotFoundError(
    f"`gradlew properties` failed at {self._project_root}. "
    f"Run `./gradlew properties --no-daemon --no-configuration-cache` manually "
    f"to see the underlying error. Common causes: Java not on PATH, "
    f"unsupported Gradle version, or build script syntax error."
)

raise VersionNotFoundError(
    "`gradlew properties` succeeded but no `version:` line was emitted. "
    "Add `version = \"X.Y.Z\"` to your build.gradle.kts or gradle.properties "
    "to make the project versionable."
)
```

The same critique applies to the file-probe tier — if `gradle.properties` and `build.gradle.kts` are both present but neither contains a version key, the user gets no hint. Add: *"Add a line like `version=0.1.0` to gradle.properties, or `version = \"0.1.0\"` to build.gradle.kts."*

### F7 (HIGH) — Missing tests for documented error paths

The plan's test coverage is **good for the happy path + auth gate + probe presence/absence** but leaves error paths untested:

- **No test for `FileNotFoundError` when `gradle.properties` is missing at `write()` time.** A user who deletes `gradle.properties` between `read()` and `write()` gets an uncaught `FileNotFoundError` raised by the open()-on-write path.
- **No test for the `gradle.properties` empty/no-key case** for `read()`. The test list in Task 2, Step 1 has `test_read_raises_version_not_found_when_nothing_matches` — but it tests the case where the file is *missing* (which falls through to `_read_via_gradle()`); it does NOT test the case where `gradle.properties` exists but is empty. These are different code paths once the plan ships the F5 fix.
- **No test for `kotlin_bump_version` when `gradle.properties` doesn't exist**. The MCP wrapper currently passes the path through; if `gradle.properties` doesn't exist, `version_source.write()` raises `FileNotFoundError`, but the MCP layer has no try/except, so the user gets a raw stack trace.
- **No test for `_read_via_gradle` failure when gradlew is missing**. `subprocess.run(["./gradlew", ...])` raises `FileNotFoundError` (not `VersionNotFoundError`) when the binary is missing. The MCP layer doesn't catch this either.
- **No test for rollback when `VersionWriteError` is raised** (per plan Task 5 Step 3, write happens before commit, so write failure shouldn't trigger rollback — but this invariant is not asserted).

Add at least:
- `test_kotlin_bump_version_missing_gradle_properties`
- `test_kotlin_bump_version_gradlew_not_installed`
- `test_read_gradle_properties_empty_file_raises_version_not_found`
- `test_kotlin_lifecycle_does_not_rollback_when_write_fails_before_commit`
- `test_kotlin_list_hooks_at_python_project_raises_value_error`

### F12 (MEDIUM) — `gradle.properties` write regex silently truncates trailing comma-separated values

Task 2, Step 3, `GradlePropertiesVersionSource.write()`:

```python
pattern = rf"^(\s*)({re.escape(key)}\s*=\s*)(\S+?)([,\s]*)$"
new_content, count = re.subn(pattern, rf"\1\2{new_version}\4", content, flags=re.MULTILINE)
```

Consider a gradle.properties line: `version=1.2.3,build=42`. The regex captures `1.2.3` as group 3 and `,build=42` as group 4, then replaces with `1.2.4,build=42`. **But consider** `version=1.2.3  # major release` — the regex captures `1.2.3` and `  # major release` as the trailing whitespace group, and replaces with `1.2.4  # major release`. That's correct.

However, consider `version=1.2.3 #` followed by no trailing content: `re.search(r"(\S+?)([,\s]*)$")` will match `1.2.3` followed by ` #`, which is the trailing group. Replace with `1.2.4 #`. Looks fine.

But `version = "1.2.3"` (Gradle Groovy/KTS syntax) — not in gradle.properties, so not relevant.

The **actual** issue is **for a value containing a hyphen followed by space** like `version=1.2.3-snapshot`. The regex `(\S+?)([,\s]*)$` is non-greedy: it'll capture `1` as group 3, ` `.` as part of group 4. Bump to `1.2.4`. That's wrong — `1.2.3-snapshot` is a valid pre-release identifier.

Worse, the regex anchors with `^...$` (start/end of line) but `[,\s]*` doesn't match `-`. So the match would actually consume up to the FIRST whitespace-or-comma, then look at what follows to match `[,\s]*$`. Let me re-trace:

- Input line: `version=1.2.3-snapshot`
- `(\S+?)` non-greedy: starts with `1`, then checks if next char matches `[,\s]*$`. The char after `1` is `.`, not in `[,\s]`, so `(\S+?)` consumes `.`. Continues: `1.2`. Next char is `.`, not in `[,\s]`. `1.2.3`. Next char is `-`, not in `[,\s]`. **The non-greedy match expands until it can satisfy the rest of the pattern.**
- After consuming `1.2.3-snapshot` (the full non-whitespace string), `[,\s]*$` matches empty string + end-of-line. ✓

So actually the regex handles `1.2.3-snapshot` correctly: it captures `1.2.3-snapshot` as group 3, and the regex replaces with `1.2.4-snapshot`. Bumping `1.2.3-snapshot` to `1.2.4-snapshot` is arguably wrong (pre-1.0 semver says a `major` bump should reset the pre-release), but for a "patch" bump it's correct. For "major" or "minor" with pre-release, semver says the pre-release should be cleared. The plan's `_bump` doesn't handle pre-release suffixes at all.

**For the a11y lens:** the issue is **silent data corruption for projects using pre-release versions** (e.g., `0.1.0-alpha`, `1.0.0-rc.1`). A user running `kotlin_bump_version(level="minor")` on a `1.0.0-rc.1` project gets `1.1.0-rc.1` — semver says it should get `1.1.0`. The CHANGELOG entry says "real-semver `_bump` semantics (major bumps major, matching Python)" — but the implementation doesn't actually implement real semver for pre-release versions.

**Fix:** either (a) document the pre-release limitation in the `KotlinLifecycle._bump` docstring, or (b) strip pre-release suffixes before bumping and re-attach them after (with a clear log message). Both have a11y implications: (a) is fine for sighted users but invisible to screen readers, (b) should emit a `logger.info(...)` line that screen readers can announce.

### F18 (LOW) — Tests use `mock.patch` against `subprocess.run` global (process-environment fragile)

The plan's tests use `mock.patch("subprocess.run")` (Task 3 Step 1, Task 4 Step 1) at module level. If any test imports a helper that does `import subprocess` and then accesses `subprocess.run` via attribute lookup, the mock works. But if any code does `from subprocess import run`, the mock is bypassed (a known Python mocking pitfall; this is a lesson from `httpx2-mock-patch-alias-trap.md` memory). The plan doesn't show whether the production code does `import subprocess` or `from subprocess import run`. **Fix:** ensure the production code in `GradleTaskProbe`, `GradlePropertiesVersionSource._read_via_gradle`, and `git_backend.py` uses `import subprocess` (then accesses `subprocess.run`) — not `from subprocess import run` — so the mocks work.

This is low-severity because the plan will be exercised by the implementer; if the production code uses `from subprocess import run`, the tests will silently pass-with-no-mock-effect (calling the real subprocess). The first run against a real Gradle fixture will catch it, but a screen-reader-only reviewer reading the plan won't see this risk without inspecting the test pattern.
