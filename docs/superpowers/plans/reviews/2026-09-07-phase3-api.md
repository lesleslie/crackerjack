## Findings (most-severe first)

### CRITICAL — `dry_run=True` mutates `gradle.properties` (spec contract violation)

**Confidence**: HIGH
**Location**: Plan Task 5, Step 3 item 3 (`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase3.md` lines 826-828):

> "**NEW step**: after computing `new_version`, call `self._version_source.write(new_version)` BEFORE the dry_run check. This is the Kotlin-specific bump action (gradle.properties write). On failure, raise before any git mutation."

The spec's Error Handling table is explicit:

> `dry_run=True` on lifecycle | All mutations skipped; commit/tag/push return None; result includes `("dry_run",)` in `skipped_steps`

A `dry_run=True` invocation MUST NOT mutate any source file. Writing `gradle.properties` before the dry-run check means the file is changed even when the user requested a no-op preview. This breaks the contract that `dry_run` is a true read-only mode.

Compare to the actual `SwiftLifecycle.run` (`/Users/les/Projects/crackerjack/crackerjack/adapters/swift/lifecycle.py:76-87`) which checks `if options.dry_run: return LifecycleResult(... skipped_steps=("dry_run",))` BEFORE any mutation (Swift has no in-file write step, but the dry_run short-circuit is the established pattern).

The plan's test `test_kotlin_lifecycle_run_dry_run_does_not_mutate` (Task 5, lines 760-766) asserts `result.new_version`, `commit_sha`, `tag_name`, and `skipped_steps` — but it does NOT assert that `gradle.properties` content is unchanged. The test as written would pass even with the bug, hiding the regression.

**Why it matters**: Users running `kotlin_bump_version(level="minor", dry_run=True)` expect an idempotent preview. A side-effecting dry_run silently modifies a tracked file in their working tree — corrupting the next commit they make, breaking their editor's "unsaved changes" indicators, and triggering spurious pre-commit hooks. The MCP `kotlin_bump_version` handler hands this directly to users.

**Fix**:
1. Reorder `KotlinLifecycle.run` to mirror Swift: dry_run check BEFORE any mutation.
2. Add an explicit assertion to the existing dry_run test:
   ```python
   assert (tmp_path / "gradle.properties").read_text() == "version=1.2.3\n"
   ```

### CRITICAL — Rollback contract for `gradle.properties` not specified (Phase 2 doesn't apply)

**Confidence**: HIGH
**Location**: Plan Task 5, Step 3 item 4 (lines 828-829):

> "**Rollback enhancement**: if `write()` fails after `_commit()` has already happened, the rollback path must NOT call `_reset` (the gradle.properties change was the only mutation); `_delete_tag` is also unnecessary. Simplest: catch `VersionWriteError` before `_commit` (since write happens first) so the rollback paths remain symmetric with Swift's."

The framing "symmetric with Swift's" is incorrect. Swift has no in-file write step (git tags are the version), so Swift's rollback is `delete_tag + reset`. Kotlin adds a pre-commit mutation (`gradle.properties` write) that survives a `git reset --hard` ONLY if the write was committed. If `_commit` fails AFTER `write` succeeded, the working tree is dirty with an uncommitted `gradle.properties` change, and `_reset` does nothing (no commit to undo).

The plan does not address this case. The rollback contract per spec API F9:

> "On any failure mid-flow: delete tag, reset commit, raise."

For Kotlin, the contract must be extended: failures after `write()` but before `_commit()` require reverting the working-tree file. Failures after `_commit()` but before `_push()` require `git reset --hard` (which reverts the file via index/tree), but only if the file was actually committed.

**Why it matters**: The plan's test `test_kotlin_lifecycle_rollback_on_push_failure` (Task 5, lines 778-786) covers push failure correctly via `_reset`. But no test covers `_commit` failure or `_tag` failure or post-commit-pre-push failures where the gradle.properties was committed. The "symmetric" framing will lead implementers to write code that silently leaves the working tree dirty.

**Fix**: Explicitly enumerate rollback semantics in `KotlinLifecycle._run_impl`:

| Failure point | Rollback action |
|---|---|
| `version_source.write()` raises | None needed (write hadn't happened) |
| `_commit()` raises after write | Revert `gradle.properties` via `VersionSource.write(old_version)` (requires a stash of the prior content) OR `git checkout HEAD -- gradle.properties` (uncommitted file gets reverted via index if previously committed) |
| `_tag()` raises after commit | `_reset(commit_sha~1)` (reverts commit + gradle.properties) + `_delete_tag(tag_name)` |
| `_push()` raises | Current test path: `_reset(commit_sha)` + `_delete_tag(tag_name)` ✓ |
| `_gh_release()` raises | `_delete_tag` + `_reset` per Phase 2 M5 |

Add tests for commit-failure and tag-failure rollback paths; assert `src.read() == "1.2.3"` after each.

The Phase 2 API review (`/Users/les/Projects/crackerjack/docs/superpowers/plans/reviews/2026-09-07-phase2-api.md`, CRITICAL #2) found that `SwiftLifecycle`'s signatures diverge from `PythonLifecycle` in two ways:
- `_tag` should be `Callable[[str, str], str]` (returns tag name), matching Python; Swift's `Callable[[str, str], None]` is wrong.
- `_gh_release` should be `Callable[[str], str | None]` (None when no release); Swift's `Callable[[str], str]` (never None) is wrong.

Confirmed against the actual file at `/Users/les/Projects/crackerjack/crackerjack/adapters/swift/lifecycle.py:55-66`:

```python

gh_release: Callable[[str], str],
```

Phase 3 explicitly mirrors this shape (plan line 833, 836). The Phase 2 review recommended fixing both at the Swift implementation site, but Phase 3 widens the blast radius by adding a third conforming adapter.

**Why it matters**: The third copy of the wrong signature makes a future unification harder. Any helper like `run_lifecycle_for(lifecycle, options)` that introspects method signatures (or wraps both adapters under a common interface) will silently break because `tag` returns `None` instead of the tag name, and `gh_release` raises if stdout is empty instead of returning `None`.

**Fix**: Either
1. Fix Swift's signatures first per the Phase 2 review CRITICAL, then mirror correctly in Kotlin. (Recommended.)
2. Or, in the Phase 3 plan, deviate from Swift's wrong signatures and use `Callable[[str, str], str]` and `Callable[[str], str | None]`, with a comment noting that Swift's signatures will be fixed in a follow-up.

Either way, do NOT copy the wrong signatures as-is.

### HIGH — Concrete `GradlePropertiesVersionSource` typed where `VersionSource` Protocol expected

**Confidence**: MEDIUM
**Location**: Plan Task 5, Step 3 (line 834):

```python
version_source: GradlePropertiesVersionSource,
```

The plan uses the concrete class instead of the Protocol (`VersionSource`) for the constructor parameter. Same drift in `SwiftLifecycle.__init__` (`version_source: GitTagVersionSource`).

`Capabilities.version_source: VersionSource | None` (base.py:88) accepts both concrete and Protocol-typed values because Protocol uses structural typing — so passing `Capabilities(version_source=GradlePropertiesVersionSource(...))` works at runtime and type-check time.

The concrete-type drift becomes a problem only when:
- Tests substitute fakes (a `FakeVersionSource` typed as `VersionSource` would fail to assign to a parameter typed as `GradlePropertiesVersionSource`).
- A future `LanguageAdapterBase.capabilities()` returns a `VersionSource` and the lifecycle expects the same Protocol-typed parameter.

**Why it matters**: The Phase 2 review flagged this exact pattern as a "future helper" risk. Phase 3 widens the surface area by adding a third concrete-typed parameter where Protocol would suffice.

**Fix**: Type the constructor parameter as the Protocol:

```python
from crackerjack.adapters.base import VersionSource

def __init__(
    self,
    version_source: VersionSource,  # Protocol, not concrete
    ...
):
```

This aligns with the spec's intent (`Capabilities.version_source: VersionSource | None`).

### MEDIUM — `_bump` is duplicated a third time (Phase 2 review HIGH finding perpetuated)

**Confidence**: HIGH
**Location**: Plan Task 5, Sub-task 5.1 (lines 677-699) and "Cross-adapter `_bump` divergence" section (lines 1209-1220).

The Phase 2 API review (HIGH #3) explicitly flagged this:

> "Extract once to `crackerjack/adapters/_semver.py` with a single `bump(version: str, level: str) -> str`. Both Python and Swift import it. Phase 3 reuses the same function. The 'duplication is acceptable' framing in the brief is a Phase-3-debt acknowledgement, not an API design choice."

Phase 3 perpetuates the issue:
- Phase 1 PythonLifecycle._bump (line 16 of `lifecycle.py`).
- Phase 2 SwiftLifecycle._bump (`/Users/les/Projects/crackerjack/crackerjack/adapters/swift/lifecycle.py:17-33`).
- Phase 3 KotlinLifecycle._bump (plan lines 677-699).

Three copies, with divergent semantics (Python real semver, Swift pre-1.0, Kotlin real semver). The plan acknowledges this as a Phase 2.5 follow-up but does NOT extract a shared module.

**Why it matters**: Every future adapter (Phase 4 Web won't have `_bump`, but Phase 5 Rust/Go will) will face the same "copy vs. parameterize" decision. The cross-adapter divergence documented in the plan (option b: "narrow `LifecycleOptions.level` to be a strict semver bump and let each adapter interpret 'major' correctly") is fine as a final design, but it requires a shared dispatcher module to coordinate the per-language semantics. Adding the dispatcher now (even with a `dict[str, Callable]`) costs ~30 LOC and prevents the 4th copy.

**Fix**: Extract `_bump` to `crackerjack/adapters/_semver.py` with the dispatcher:

```python
# crackerjack/adapters/_semver.py
from collections.abc import Callable

_SEMVER_VARIANTS: dict[str, Callable[[tuple[int, int, int], str], tuple[int, int, int]]] = {
    "real": lambda v, lvl: _real_semver_bump(v, lvl),  # Python, Kotlin
    "pre_1_0": lambda v, lvl: _pre_1_0_bump(v, lvl),  # Swift
}


def bump(version: str, level: str, *, variant: str = "real") -> str:
    ...
```

Each adapter declares `BUMP_VARIANT = "real" | "pre_1_0"` and calls `bump(current, level, variant=self.BUMP_VARIANT)`. This makes the divergence explicit at the import site, not buried in three copies.

If Phase 3 doesn't want to disrupt Phase 2 by introducing the module, at minimum add a test asserting that `_bump` in all three modules agree on a known input set (so future divergence is loud).
