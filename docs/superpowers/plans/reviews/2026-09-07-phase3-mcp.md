# MCP Lens Review — Phase 3 Kotlin/Gradle

## Findings (most-severe first)

### BLOCKER 1 — Plan introduces `kotlin_list_hooks` but spec mandates `kotlin_run_hooks`

Spec line 44 ("Per-adapter Kotlin") and line 531 ("Tool naming (per MCP F4)") both say **`kotlin_run_hooks`**:

- Line 44: `**MCP tools**: `kotlin_bump_version` (mutation; auth required), `kotlin_run_hooks`.`
- Line 531: ``kotlin_run_hooks` (not `run_kotlin_hooks`)``

The Phase 3 plan (Task 7 Step 3, line 1065 of plan) renames this to **`kotlin_list_hooks`**:

```python
@mcp_app.tool()
async def kotlin_list_hooks(project_root: str) -> dict:
    """Return Kotlin/Gradle hook metadata (read-only; no auth)."""
```

The renaming is internally consistent with the Phase 2 final review (HIGH 3 in `2026-09-07-phase2-mcp.md`), which renamed `swift_run_hooks` → `swift_list_hooks` to fix a wire-protocol-vs-name mismatch (the Swift tool was a metadata lister but was called `*_run_hooks`). Phase 2's rename was applied to the **implementation** but the **spec was not amended** — and the spec still describes `swift_run_hooks` elsewhere. Phase 3 follows the implementation convention but again does not amend the spec.

Two failure modes:

1. **Implementer reads the spec literally** (`kotlin_run_hooks`) and the plan literally (`kotlin_list_hooks`) and produces something that matches one but not the other. The MCP tool registry will contain a name that conflicts with the spec wire-protocol guarantee.
2. **Spec / implementation / plan** all three drift. The Phase 2 final review already noted that spec MCP F4 carries the old name (`swift_run_hooks`); Phase 3 widens that drift to `kotlin_*` names as well. A future MCP client reading the spec will look for `kotlin_run_hooks`, not find it, and fail.

**Required fix (pick one):**

1. **Amend the spec** (preferred — matches Phase 2 ruling): update spec lines 44 and 531 to say `kotlin_list_hooks` (and also back-patch `swift_run_hooks` → `swift_list_hooks` in spec line 39). Add a "Spec Revision Notes" section entry to the Phase 3 plan documenting the amendment.
2. **Reverse the plan**: keep the name `kotlin_run_hooks` to match the spec, then either (a) actually run the hooks (wrap subprocess in `asyncio.to_thread`) per Phase 2 HIGH 3 option 2, or (b) keep it as a metadata lister and accept that the name lies.

This is a **spec/plan wire-protocol contract** mismatch — exactly the failure mode the 4-step registration pipeline and `_tool_registry_keys.json` fixture (spec MCP F3) are designed to surface.

**Confidence:** HIGH (spec quotes are unambiguous).

### HIGH 1 — `_validate_project_root` silent-bypass on unset `MAHAVISHNU_PROJECT_ROOTS` carried over unchanged

Phase 2 security review flagged this as an **inverted policy**: the most permissive behavior (skip allowlist) activates when the env var is *unset*, and the most restrictive behavior (allowlist enforcement) activates only when the var is *set*. Production deployments that forget to set the var lose all path protection silently.

Current code at `crackerjack/mcp/tools/language_tools.py:71-78`:

```python
allowed_env = os.environ.get("MAHAVISHNU_PROJECT_ROOTS", "")
if not allowed_env:
    logger.debug(
        "MAHAVISHNU_PROJECT_ROOTS unset; allowlist check skipped. "
        "Production deployments MUST configure this env var.",
    )
    return root
```

This is the exact pattern Phase 2 flagged. The Phase 3 plan does not fix it — it just reuses the helper via `_validate_project_root(project_root)` (plan lines 1037, 1067). Two new MCP tools (`kotlin_bump_version` is a *mutation* tool with push/release side-effects; `kotlin_list_hooks` is read-only but still arbitrates file I/O) now expose this bug.

Why it matters:

- An operator who runs `mahavishnu mcp start` without setting `MAHAVISHNU_PROJECT_ROOTS` (a common dev shortcut) gets a server that *appears* to validate paths (the `Path(project_root).resolve(strict=False)` and traversal/NUL checks still run) but actually allows any path on the filesystem. A `kotlin_bump_version(level="major", project_root="/")` would happily attempt to bump the version of the root filesystem.
- The `logger.debug` call only fires at DEBUG level; operators reading INFO logs see no warning. The Phase 2 fix was `logger.warning(...)` plus `raise PermissionError(...)` by default — neither was applied.

**Required fix:**

In `language_tools.py:71-78`, change the unset behavior to **fail-closed**:

```python
allowed_env = os.environ.get("MAHAVISHNU_PROJECT_ROOTS", "")
if not allowed_env:
    raise PermissionError(
        "MAHAVISHNU_PROJECT_ROOTS unset; mutation tools refuse to operate without "
        "an explicit allowlist. Set the env var (colon-separated) before invoking."
    )
```

This is a one-line fix in shared code that affects Phase 2's `swift_bump_version` / `swift_list_hooks` / `detect_languages` AND Phase 3's two new tools. Tests at `tests/mcp/tools/test_language_tools.py:33-39` (`test_swift_bump_version_requires_auth`) and `:75-89` (`test_swift_list_hooks_does_not_require_auth`) both run with `clear=True` (env unset) and would need to set `MAHAVISHNU_PROJECT_ROOTS` to continue passing.

**Confidence:** HIGH (Phase 2 security review quoted verbatim).

### HIGH 2 — `kotlin_bump_version` uses `level: str` instead of `Literal["major", "minor", "patch"]`

Plan Task 7 Step 3 (line 1030):

```python
@mcp_app.tool()
async def kotlin_bump_version(
    level: str,
    project_root: str,
    dry_run: bool = False,
    release: bool = False,
) -> dict:
```

Existing `swift_bump_version` at `crackerjack/mcp/tools/language_tools.py:151-155`:

```python
@mcp_app.tool()
async def swift_bump_version(
    project_root: str,
    level: Literal["major", "minor", "patch"] = "minor",
    release: bool = False,
) -> dict[str, str | None]:
```

Two consequences of using bare `str`:

1. **MCP schema generation:** FastMCP emits `{"type": "string"}` for `level`. The client gets no enum constraint and no autocomplete hint. A typo (`"mimor"`, `"Major"`) silently passes Pydantic validation; `LifecycleOptions.__post_init__` then raises `ValueError` with a less helpful message than a typed-enum rejection at the MCP boundary.
2. **`LifecycleOptions.__post_init__` is the only line of defense.** Phase 2 final-review M-3 noted that `LifecycleOptions.__post_init__` validates `level` against the literal; the Swift tool's `Literal[...]` annotation is a *front-line* check that catches typos before the lifecycle is even constructed. Plan's Kotlin tool removes that front-line.

This is a **consistency regression**: Swift validates twice (Pydantic + LifecycleOptions); Kotlin validates once (LifecycleOptions only). An LLM client calling `kotlin_bump_version(level="mimor", ...)` gets a different error path than `swift_bump_version(level="mimor", ...)`.

**Required fix:** Change `level: str` to `level: Literal["major", "minor", "patch"] = "minor"` in plan line 1030 (and update the function signature ordering to match Swift: `project_root` first, then `level` with default — Swift's signature is `project_root, level, release`).

**Confidence:** HIGH.

### HIGH 3 — Plan's auth-failure test does not exercise the happy path; spec F1 step 4 expects both

Phase 2 review BLOCKER 2 (the precedent this review must mirror) flagged:

> Spec MCP F1 step 4 (TEST) is satisfied at the unit level but NOT at the MCP server integration level.

Plan Task 7 Step 1 (lines 996-1016) only adds two tests:

```python
async def test_kotlin_list_hooks_returns_three_hook_names(tmp_path: Path) -> None:
    ...
    names = set(result.keys())
    assert "kotlin.ktlint" in names
    ...

async def test_kotlin_bump_version_requires_auth() -> None:
    ...
    with pytest.raises(PermissionError):
        asyncio.run(tool.fn(level="minor", project_root="/tmp/nonexistent"))
```

The auth-failure test exercises failure. The `kotlin_list_hooks` test exercises the read-only happy path. **No test exercises `kotlin_bump_version` with auth set + a valid project_root + a mocked lifecycle helper** (the Swift equivalent is `test_swift_bump_version_runs_with_auth` at `test_language_tools.py:42-71`).

Without this, two scenarios are uncovered:

1. The plan's inline-lifecycle approach (plan lines 1042-1054) constructs `KotlinLifecycle` with the **real** `make_git_backend(project_root)`. With auth unset + `MAHAVISHNU_PROJECT_ROOTS` unset (allowlist bypass), the test would attempt to invoke `subprocess.run(["git", ...])` against the actual filesystem. The test would either hang on git operations or silently pass without covering the intended codepath.
2. The `asyncio.to_thread(...)` wrapping (plan line 1051) is not exercised by the auth-failure test (auth raises before `to_thread` is called).

**Required fix:** Add a happy-path test mirroring `test_swift_bump_version_runs_with_auth` (lines 42-71 of the existing test file): set `MAHAVISHNU_AUTH_ENABLED=true` + `MAHAVISHNU_JWT_SECRET=test-secret` + `MAHAVISHNU_PROJECT_ROOTS=<tmp_path>`, mock `make_git_backend` to return `MagicMock` objects, assert the tool returns the expected dict.

**Confidence:** HIGH.

### MEDIUM 1 — `kotlin_list_hooks` raises `ValueError` on `KotlinAdapter.detect() == False`; Swift's `swift_list_hooks` does not

Plan Task 7 Step 3 (lines 1070-1073):

```python
adapter = KotlinAdapter()
if not adapter.detect(root):
    raise ValueError(f"No build.gradle(.kts) at {root}")
caps = adapter.capabilities(root)
return {...}
```

Swift's `swift_list_hooks` at `language_tools.py:180-190` does NOT perform this check; it calls `adapter.capabilities(root)` directly and returns whatever hooks the adapter provides (possibly empty tuple).

Why this matters:

- A Python-only project at `project_root` (no `Package.swift`) calls `swift_list_hooks` and gets `{"swift.test": {...}, ...}` if `SwiftAdapter.detect()` happens to return True, OR an empty dict otherwise. The client decides what empty means.
- A Kotlin/Gradle project at `project_root` (no `build.gradle(.kts`) calls `kotlin_list_hooks` and gets a hard `ValueError`. Inconsistent semantics.

This may be intentional (the plan author may want a louder error), but the spec is silent and the Swift precedent is the opposite. If the design intent is "list_hooks tools refuse on non-matching projects," then `swift_list_hooks` should also raise ValueError. If the design intent is "list_hooks tools return empty," then Kotlin should match.

**Required fix:** Pick one and apply consistently. Recommend removing the `adapter.detect()` check from `kotlin_list_hooks` (let `capabilities()` return empty hooks; client checks `result == {}`); OR add the same check to `swift_list_hooks` (separate Phase 2 follow-up — out of Phase 3 scope, but flag it).

**Confidence:** MEDIUM (consistent-error-handling concern, not a wire-protocol bug).

### MEDIUM 2 — Plan inlines `KotlinLifecycle` construction instead of factoring a `_run_kotlin_lifecycle_sync` helper

Swift established a clean separation at `language_tools.py:101-128`:

```python
def _run_swift_lifecycle_sync(
    project_root: Path, level: str, release: bool,
) -> dict[str, str | None]:
    """Run the Swift lifecycle synchronously. Wrapped by async MCP handlers."""
    version_source = GitTagVersionSource(project_root)
    commit, tag, push, delete_tag, reset, gh_release = make_git_backend(project_root)
    lifecycle = SwiftLifecycle(...)
    result = lifecycle.run(LifecycleOptions(level=level, release=release))
    return {...}
```

Plan Task 7 Step 3 (lines 1038-1061) inlines all of this inside the async tool:

```python
async def kotlin_bump_version(...) -> dict:
    _require_auth_config()
    root = _validate_project_root(project_root)
    from crackerjack.adapters.kotlin.git_backend import make_git_backend
    from crackerjack.adapters.kotlin.lifecycle import KotlinLifecycle
    from crackerjack.adapters.kotlin.version_source import GradlePropertiesVersionSource
    from crackerjack.adapters.base import LifecycleOptions

    version_source = GradlePropertiesVersionSource(root)
    commit, tag, push, delete_tag, reset, gh_release = make_git_backend(root)
    lifecycle = KotlinLifecycle(...)
    result = await asyncio.to_thread(
        lifecycle.run,
        LifecycleOptions(level=level, dry_run=dry_run, release=release),
    )
    return {...}
```

Three issues:

1. **Test mocking is harder.** The existing Swift test patches `_run_swift_lifecycle_sync` directly (`test_swift_bump_version_runs_with_auth`, line 63 of the test file). The Kotlin tool has no such surface to patch; tests must mock `make_git_backend` AND `KotlinLifecycle.__init__` to intercept the lifecycle.
2. **Late imports inside the tool function** — the plan's `from crackerjack.adapters.kotlin.lifecycle import KotlinLifecycle` etc. are inside the async function body. This was done to defer-import before the adapter existed (Task 7 in Phase 2 was created before Phase 3's adapter package); but by Phase 3 execution time, those modules exist and the deferred imports are gratuitous. Move them to module top.
3. **Stylistic drift** — the new tool reads differently from the existing one. Future reviewers will ask "why are these inconsistent?"

**Required fix:** Add `_run_kotlin_lifecycle_sync(project_root, level, dry_run, release) -> dict` to `language_tools.py` mirroring `_run_swift_lifecycle_sync`. Tool body becomes a 4-line async wrapper:

```python
@mcp_app.tool()
async def kotlin_bump_version(...) -> dict:
    _require_auth_config()
    root = _validate_project_root(project_root)
    return await asyncio.to_thread(
        _run_kotlin_lifecycle_sync, root, level, dry_run, release,
    )
```

**Confidence:** HIGH.

## Plan Quality Verdict

**Structurally sound with one wire-protocol divergence (BLOCKER 1) and one security carry-over (HIGH 1).**

The plan correctly mirrors the Phase 2 MCP pattern: tools added to the existing `language_tools` group, `_require_auth_config` and `_validate_project_root` reused, `asyncio.to_thread` wrapping applied, and `MAHAVISHNU_PROJECT_ROOTS` allowlist respected. The registration pipeline step-skipping rationale (steps 2 and 3 are pre-baked by Phase 2) is correctly argued.

The two material findings are:

1. **BLOCKER 1** is a **spec contract drift**, not a code bug. Either the plan must follow the spec (`kotlin_run_hooks`) or the spec must be amended (to `kotlin_list_hooks`). This is the same class of bug Phase 2's HIGH 3 caught for Swift. The Phase 2 rename was applied to implementation but never amended the spec; Phase 3 widens that drift.

2. **HIGH 1** is a **security policy inversion** flagged by Phase 2 but not fixed before Phase 3 lands. Adding two more tools that route through the buggy helper amplifies the blast radius. Fix should land as the first commit of Phase 3 implementation (Task 7 Step 3.5 — "fix `_validate_project_root` inversion").

The remaining HIGH/MEDIUM findings are quality improvements that can land in the same Task 7 or as Phase 3 follow-ups:

- HIGH 2 (`Literal[...]` annotation): one-line fix.
- HIGH 3 (happy-path test): trivial addition; mirrors existing test.
- MEDIUM 1 (consistency on detect-False behavior): pick one, apply to both.
- MEDIUM 2 (factor `_run_kotlin_lifecycle_sync`): aligns with Swift pattern.
- MEDIUM 3 (assert `"kotlin" in result`): one-line addition.

Recommend: fix BLOCKER 1 (amend spec OR rename plan tool) + fix HIGH 1 (inverted `_validate_project_root`) before Task 7 implementation begins. The rest can land in Task 7 or be deferred to Phase 3 follow-ups.
