### F1 (CRITICAL) — `format_jinja_templates` silently ignores the project's `[tool.crackerjack.jinja]` config

Task 6, Step 3 implements `format_jinja_templates` as:

```python
@mcp_app.tool()
async def format_jinja_templates(projects: list[str]) -> dict:
    ...
    from crackerjack.adapters.web.jinja_formatter import format_template
    ...
    for path in proj.rglob("*"):
        if not path.is_file() or path.suffix not in {".html", ".j2", ".jinja"}:
            continue
        try:
            formatted = await asyncio.to_thread(
                format_template, path.read_text(),
            )
            path.write_text(formatted)
```

The handler calls `format_template(source)` with **no `delimiters` argument**, which means the formatter uses `DEFAULT_DELIMITERS` (`{%`, `%}`, `{{`, `}}`, `{#`, `#}`). But fastblocks's templates use custom delimiters (`[%`, `%]`, `[[`, `]]`, `[#`, `#]`) — exactly the use case Jinja F2 was written to support.

The plan acknowledges `[tool.crackerjack.jinja]` exists (line 422–423, 575–576), but the **MCP tool never reads it**. So:

- A user invokes `format_jinja_templates(projects=["src/templates"])` on fastblocks.
- The formatter reads each `.html` file as if it used `{%` delimiters.
- `jinja2.Environment.lex()` returns tokens, but for fastblocks's `[% if x %]` content, `lex()` with default delimiters won't recognize `[%` as a block start — it returns text-only tokens, re-emits the source unchanged.
- The Tier-1 trailing-newline and trailing-whitespace rules STILL apply, so the file gets rewritten with a trailing newline (if missing) and stripped trailing whitespace — silently modifying the user's project without lexing the actual Jinja structure.

**Why this matters for a11y:** a screen-reader user invokes the tool, hears "files: [...]" with no warnings, and assumes the tool formatted their templates. The templates are silently corrupted in a low-stakes way (trailing newlines, trailing whitespace) but the **delimiter configuration they documented in `pyproject.toml` is ignored**. They cannot learn from any error message that their config wasn't loaded. The CLI fallback hypothesis ("I'll just run `crackerjack web jinja format`") suffers the same defect — there is no fallback to mention.

**Fix:** the handler must load `[tool.crackerjack.jinja]` from each project's `pyproject.toml`, pass the 6 delimiter keys to `format_template`, and surface a clear error if the config is missing for a project that has `.j2` files. Mirror Task 2's detection.py pattern: read TOML, fall back to defaults, and emit a structured error if the loader fails for a Jinja project.

### F2 (CRITICAL) — Tier 2 `_normalize_one_space_inside_delimiters` corrupts whitespace-control markers

Task 4, Step 4 implements Tier 2 normalization as:

```python
def _normalize_one_space_inside_delimiters(source: str, delims: Mapping[str, str]) -> str:
    """Tier 2: ensure exactly one space inside each delimiter pair."""
    out = source
    for open_key, close_key in [
        ("block_start", "block_end"),
        ("variable_start", "variable_end"),
        ("comment_start", "comment_end"),
    ]:
        open_d, close_d = delims[open_key], delims[close_key]
        pattern = re.escape(open_d) + r"(\S)(.*?)(\S)" + re.escape(close_d)
        def repl(m: re.Match[str]) -> str:
            return f"{open_d} {m.group(2)} {close_d}"
        out = re.sub(pattern, repl, out, flags=re.DOTALL)
    return out
```

Consider an input like `{%- if x -%}` (a block that strips whitespace on both sides):

- Pattern matches `{%` (open_d), `-` (group 1, the `\S` non-whitespace), ` if x ` (group 2), `-` (group 3), `%}` (close_d).
- Replacement: `{%` + ` ` + ` if x ` + ` ` + `%}` = `{%  if x  %}`.
- **The whitespace-control markers `-` are silently dropped.**

`{%- if x -%}` means "strip whitespace before the if and after the endif block". The replacement `{%  if x  %}` is a *different template* — it doesn't strip. The change is semantically meaningful: rendered output differs (adjacent whitespace is preserved instead of stripped).

**Why this matters for a11y:** a screen-reader user invoking `format_template(..., normalize=True)` on templates that use whitespace-control gets **silently different output**. There is no error, no warning, no log line — the `format_template` function returns a different string. The Tier 1 docstring promises "preserve `{%-` / `-%}` / `{{-` / `-}}` markers" but Tier 2 contradicts it.

**Fix:** either (a) skip normalization for whitespace-control delimiter pairs (regex must include `[+-]?` on the `\S` boundaries and refuse to strip), or (b) document this limitation loudly in `format_template`'s docstring AND in the CHANGELOG entry, AND emit a `logger.warning(...)` for each affected occurrence. Option (a) is the only safe default. The plan currently sets `normalize=False` by default, so casual users are safe — but the API contract still permits `normalize=True` to silently corrupt templates.

### F4 (HIGH) — `format_jinja_templates` writes files in-place with no backup, no dry-run, no preview

Task 6, Step 3:

```python
formatted = await asyncio.to_thread(
    format_template, path.read_text(),
)
path.write_text(formatted)
files.append(str(path))
```

A user invoking `format_jinja_templates` from MCP for the first time has no:
- `--dry-run` flag that prints "would format: <path>".
- Backup of the original file (no `.bak`, no `git stash`, no rollback record).
- Preview of the diff before write.

Combined with F2 (whitespace-control corruption under `normalize=True`), this means a single MCP call can silently rewrite dozens of templates with semantic drift. There is no `dry_run` parameter on the tool signature (compare to Phase 3's `kotlin_bump_version(..., dry_run: bool = False)`).

**Why this matters for a11y:** a screen-reader user who discovers the tool corrupted their templates has no audio cues for what changed — they hear "files: 12" and assume success. Without a dry-run mode, they cannot iterate safely: try, look, revert (with `git`), retry. Every iteration is a full file rewrite.

**Fix:** add `dry_run: bool = False` and `backup: bool = True` parameters; in dry-run mode, populate `files` with `would_format` paths and emit a `diffs` list (truncated for transport); on `backup=True`, write a `.bak` next to the original. At minimum, return a `mode` field in the response so the caller can confirm what was done.

### F5 (HIGH) — `cli_name == "npx"` bypasses the hybrid-fallback check entirely

Task 3, Step 5 implements `run_hook_with_fallback`:

```python
cli_name = hook.cli_command[0]
if cli_name != "npx" and shutil.which(cli_name) is None:
    if hook.fallback is None:
        raise WebHookError(...)
    ...
```

The `cli_name != "npx"` guard means: **for every npx-prefixed hook, the fallback check is skipped**. If `npx` itself is missing (no Node.js install), `subprocess.run(["npx", ...])` raises `FileNotFoundError`, not `WebHookError`. No remediation hint.

This contradicts the spec's intent (Writing F2: "one canonical interpretation — when CLI is missing AND fallback is set, invoke Python fallback"). The plan uses `--no-install` (good for reproducibility) but doesn't probe `npx` availability.

**Why this matters for a11y:** a Python-first user without Node.js installed invokes `crackerjack run` on a Web project, gets a raw `FileNotFoundError: npx` stack trace, and has no way to learn that they can either (a) install Node.js + the linter, or (b) accept that only the Python fallback will run. The Phase 3 review (F4 for `KotlinTaskProbe`) called out the same defect — `GradleTaskProbe.has_task()` was defined but never called. Phase 4 inherits the pattern: probe defined, probe not used at the failure path.

**Fix:** probe `shutil.which("npx")` and the resolved binary path before invoking; if missing, either invoke `hook.fallback(...)` directly OR raise `WebHookError` with installation guidance ("Install Node.js from https://nodejs.org, then `npm install --save-dev stylelint eslint typescript html-validate`.").

### F6 (HIGH — inherited from Phase 2/3) — Detection guard tests don't cover malformed `package.json`

Task 2, Step 1 tests:

```python
def test_web_enabled_returns_true_when_package_json_present(tmp_path: Path) -> None:
    (tmp_path / "package.json").write_text("{}")
    assert web_enabled(tmp_path) is True
```

`web_enabled` returns `True` for any file at `package.json` regardless of validity. A `package.json` containing `{` (truncated JSON) would trigger Web hooks. At hook runtime:
- `npx --no-install stylelint **/*.css` runs. With `--no-install`, `npx` refuses to install; with nothing pinned in `devDependencies`, `npx` errors with "command not found" or similar.
- The Python fallback only fires if `cli_name != "npx"` (per F5), so it doesn't fire here.
- The user gets a noisy stderr and no actionable hint.

**Why this matters for a11y:** a malformed `package.json` is a common state (mid-edit, partial merge). The user expects Web detection to validate the file. The plan doesn't validate. The user gets a confusing error from `npx` instead of a clear "your package.json is malformed; fix it" message.

**Fix:** extend `package_json_present` to `package_json_valid` — load + `json.JSONDecodeError` check. Surface a clear error in `check_web_lint` if the file is present but invalid.

### F7 (MEDIUM) — `format_jinja_templates` errors are lossy

Task 6, Step 3:

```python
except (OSError, UnicodeDecodeError) as exc:
    errors.append({"path": str(path), "error": str(exc)})
```

This catches two different error classes (`OSError` for permission denied, file not found, disk full; `UnicodeDecodeError` for binary files with non-UTF-8 bytes) and flattens both into a single `str(exc)`. The caller cannot distinguish:

- `PermissionError` (file is read-only) — fix: chmod.
- `FileNotFoundError` (race condition between `rglob` and `read_text`) — fix: retry.
- `IsADirectoryError` (matched a directory somehow) — fix: skip.
- `UnicodeDecodeError` (binary file with `.html` extension) — fix: rename or skip.
- `MemoryError` on a 10GB `.html` file — fix: don't try to format it.

All five present as `"errors": [{"path": "...", "error": "<exception message>"}]` with no type tag. A non-sighted user reading the response gets no hint about whether to chmod, retry, or skip.

**Fix:** add a `kind` field: `errors.append({"path": str(path), "kind": type(exc).__name__, "error": str(exc)})`. The MCP caller (or screen reader) can announce "permission denied" vs "binary file" vs "missing file" distinctly.

### F14 (LOW) — `format_jinja_templates` swallows `lex()` failures silently

Task 4, Step 4 `format_template`:

```python
try:
    tokens = list(env.lex(source))
except jinja2.TemplateSyntaxError as exc:
    logger.warning("Jinja lex failed: %s", exc)
    return source  # Best-effort: return source unchanged
```

The function returns `source` unchanged when lex fails. The MCP handler at Task 6, Step 3 then writes `source` (unchanged) back to the file:

```python
formatted = await asyncio.to_thread(format_template, path.read_text())
path.write_text(formatted)  # formatted == source, but still a write
```

So a lex-failing template gets a "successful" file write with no content change. The user sees `files: [...]` in the response and assumes success. There is no error entry in the `errors` dict for lex failures — only for `OSError`/`UnicodeDecodeError`.

**Why this matters for a11y:** a non-sighted user hears "formatted N files" but the lex-failing ones weren't actually formatted. They might assume the tool understood the template. No log line surfaces the lex failure in the MCP response.

**Fix:** when lex fails, append to `errors` with a `kind: "lex_error"` field (mirroring F7's suggestion). The MCP handler should thread lex failures back to the caller.

### F18 (LOW — inherited from Phase 3 F11) — `_npx_command` `--no-install` interaction with package.json pins

Task 3, Step 5 `_npx_command`:

```python
def _npx_command(*args: str) -> tuple[str, ...]:
    """Build an npx-prefixed argv tuple."""
    return ("npx", "--no-install", *args)
```

`--no-install` means `npx` will refuse to install the tool if not present. The hook builders branch on `_has_pinned_version`:


**Fix:** distinguish "pinned but not installed" from "not pinned". Surface a clear error message in the latter case.
