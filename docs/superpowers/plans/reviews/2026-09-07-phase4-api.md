## Findings (most-severe first)

### CRITICAL — `web.eslint_tsc` embeds shell separator `";"` in argv list (spec violation)

**Confidence**: HIGH
**Location**: Plan Task 3, Step 5 (`/Users/les/Projects/crackerjack/docs/superpowers/plans/2026-09-07-crackerjack-multi-language-phase4.md` lines 581-586):

```python
if eslint_pinned and tsc_pinned:
    cmd = ("eslint", ".", "--ext", ".ts,.tsx,.js,.jsx", ";", "tsc", "--noEmit")
elif eslint_pinned:
    cmd = ("eslint", ".", ";", "tsc", "--noEmit")
else:
    cmd = _npx_command("eslint", ".", "--ext", ".ts,.tsx,.js,.jsx") + (";", "tsc", "--noEmit")
```

Plan "Global Constraints" line 30 (verbatim from spec):

> "argv list, no shell for all subprocess invocations. `--` separator before user-influenced positionals."

Spec Web section (line 365) specifies two tools combined:

> "**Hooks**: `stylelint` (CSS), `eslint` + `tsc --noEmit` (JS/TS), `html-validate` (HTML). Hybrid pattern (CLI primary, Python fallback)."

`subprocess.run(["eslint", ".", ";", "tsc", "--noEmit"], ...)` does NOT treat `;` as a command separator — `subprocess.run` with `argv list` and `shell=False` (the default, and what the plan uses) executes the program named by `argv[0]` (here `eslint`) with the remaining `argv` as literal arguments. The literal string `";"` and the strings `"tsc"` and `"--noEmit"` will be passed to eslint as positional arguments, which eslint will reject (`error: unexpected argument 'tsc'`), exit non-zero, and `tsc` will never run.

The accompanying docstring (lines 577-580) acknowledges the gap but does not fix it:

> "The combined hook uses a single subprocess.run in the hook runner; the cli_command encodes the eslint invocation, and tsc is appended by the runner as a follow-up. For the brief, we encode the combined command as a shell-style argv that the runner treats as sequential."

`run_hook_with_fallback` (lines 601-635) does NOT implement a "tsc follow-up" — it does a single `subprocess.run(cmd, ...)` and returns `[]` (line 635) regardless of CLI failure (only logs a warning). So eslint_tsc will silently fail to run `tsc` after eslint rejects the malformed argv.

**Why it matters**:
1. **Spec violation** — argv list with embedded shell separator is exactly what "argv list, no shell" prohibits.
2. **Silent failure mode** — `subprocess.run` non-zero exit only triggers a `logger.warning` (lines 631-634), not a failure surface. JS/TS projects with type errors will pass CI because the warning is invisible.
3. **Spec drift on hook shape** — spec enumerates `eslint` + `tsc --noEmit` (two tools), but the plan defines ONE hook (`web.eslint_tsc`) with shell-style chaining.

**Fix**: Two clean options.

**Option A (recommended) — two hooks, two `Capabilities` entries:**
```python
def _eslint_hook(project_root: Path) -> Hook:
    pinned = _has_pinned_version(project_root, "eslint")
    cmd = _npx_command("eslint", ".", "--ext", ".ts,.tsx,.js,.jsx") if pinned is None else ("eslint", ".", "--ext", ".ts,.tsx,.js,.jsx")
    return Hook(name="web.eslint", cli_command=cmd, fallback=js_ts_fallback, timeout_seconds=600)


def _tsc_hook(project_root: Path) -> Hook:
    pinned = _has_pinned_version(project_root, "typescript")
    cmd = _npx_command("tsc", "--noEmit") if pinned is None else ("tsc", "--noEmit")
    return Hook(name="web.tsc", cli_command=cmd, fallback=js_ts_fallback, timeout_seconds=600)


def web_hooks(project_root: Path) -> tuple[Hook, ...]:
    return (_css_hook(project_root), _eslint_hook(project_root), _tsc_hook(project_root), _html_hook(project_root))
```
Update test `test_web_hooks_returns_three_hooks` → 4 hooks. Update test `test_capabilities_exposes_three_hooks` → 4. Update spec section "Web hooks" to enumerate four.

**Option B (if spec genuinely wants combined)** — `Hook` would need a `sub_commands: tuple[tuple[str, ...], ...]` field (or similar), the runner would iterate, and `Capabilities` would need to advertise this is a single logical hook. This is a Protocol-level change touching `base.py`, out of Phase 4 scope.

Recommend **Option A** — matches spec enumeration, no Protocol change, no runner change.

### HIGH — `Hook.fallback` signature mismatch with `run_hook_with_fallback` invocation

**Confidence**: MEDIUM
**Location**: Plan Task 3, Step 5 lines 621-622:

```python
paths = file_paths or [project_root]
return [issue for p in paths for issue in (hook.fallback(p) or [])]
```

`Hook.fallback` is typed `Callable[..., Any] | None` (base.py:69) — permissive, accepts anything. The three fallbacks are typed `(path: Path) -> list[tuple[Path, int, str]]`. `run_hook_with_fallback` invokes `hook.fallback(p)` with a single `Path` positional arg — consistent.

**But**: when `file_paths` is provided and contains N paths, the runner invokes `fallback(p)` N times. Each invocation reads the file from disk (`path.read_text()` — python_fallbacks.py:437, 465, 489). The same file is read 3 times across the 3 hooks (stylelint, eslint_tsc, html_validate) for any HTML+CSS+JS/TS project (since html_validate reads the same HTML file that stylelint reads CSS from). The current design doesn't dedupe.

**Why it matters**: Not a correctness issue (each fallback has its own correctness). But for a Web project with N files, fallback invocations are O(3N) file reads. Acceptable for now (fallbacks only fire when CLI missing) — but the spec calls fallbacks "intentionally minimal" (plan line 419). Not a fix-required issue.

**Verdict**: Acceptable. Document as known performance characteristic in `python_fallbacks.py` docstring. No fix.

### MEDIUM — `_FALLBACK_ISSUE` type duplicated across two files

**Confidence**: MEDIUM
**Location**: Plan Task 3, Step 4 line 430:

```python
_FALLBACK_ISSUE = tuple[Path, int, str]  # (path, line, message)
```

Plan Task 3, Step 5 line 603:

```python
def run_hook_with_fallback(
    hook: Hook, project_root: Path, file_paths: list[Path] | None = None,
) -> list[tuple[Path, int, str]]:
```

The same `tuple[Path, int, str]` shape appears in both `python_fallbacks.py` (as `_FALLBACK_ISSUE`) and `hooks.py` (inline). The fallback functions are typed as returning `list[_FALLBACK_ISSUE]` but `run_hook_with_fallback` returns `list[tuple[Path, int, str]]` — which is the same shape but expressed differently. `mypy` will not catch a future drift because both are structural `tuple[Path, int, str]`.

**Why it matters**: If a future maintainer extends the issue tuple (e.g., adds a severity field), the two type aliases must be updated in lockstep. Without a shared alias, drift is silent.

**Fix**: Either:
1. Move `_FALLBACK_ISSUE` to `python_fallbacks.py` and export it; import in `hooks.py`.
2. Define `FallbackIssue` in `base.py` (next to `Hook`) since this is a contract that any hybrid hook's Python fallback may need.

Recommend option 2 — co-locate with the `Hook` dataclass that references `fallback: Callable | None`. This makes the type discoverable for third-party adapter authors (per API F1/F2).

## Plan Quality Verdict

**The plan is largely spec-compliant on the API surface**: `WebAdapter` correctly subclasses `LanguageAdapterBase`, `Capabilities` is constructed per spec API F3, `Hook` uses only required fields plus optional `fallback`/`timeout_seconds`, `format_template` signature is clean, MCP tools follow the async/auth/argv conventions. ## Cross-adapter Hook-Name Pattern (Observation)

Phase 2 (`swift.test`, `swift.build`, `swift.format`, `swift.package.update`) and Phase 3 (`kotlin.ktlint`, `kotlin.detekt`, `kotlin.test`) established the hook-name convention as `<language>.<tool>` — one tool per hook, hyphenated tool names converted to underscore-separated. If the spec genuinely intends single hooks per tool (likely, given the `<language>.<tool>` pattern and the argv-list-no-shell constraint), then `web.eslint_tsc` is an outlier that should be split. Recommend splitting. The fix unblocks JS/TS lint coverage and removes the silent-failure mode.
