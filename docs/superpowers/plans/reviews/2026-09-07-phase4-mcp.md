# MCP Lens Review — Phase 4 Web/CSS/HTML/JS/TS/Jinja

## Findings (most-severe first)

### HIGH 1 — `format_jinja_templates` does not enforce the Web detection guard at the MCP layer

Spec Writing F3 (rev 2, line 367) is explicit:

> Web adapter does not fire on Python projects by default. Detection requires `package.json` at project root OR explicit `[tool.crackerjack.web] enabled = true` in `pyproject.toml`. Without this, every Django/Sphinx/MkDocs Python project would falsely trigger Web hooks.

The Python-side enforcement lives in `WebAdapter.detect()` / `web_enabled()` (Task 2 of this plan). The MCP layer must also gate on detection — otherwise a Python project can call `format_jinja_templates(projects=["/path/to/django/templates"])` and the tool will happily rewrite every `{% if %}` block in a Django project even though the Web adapter's `detect()` returned False.

Compare Phase 3's `kotlin_bump_version` (language_tools.py:288-293):

```python
adapter = KotlinAdapter()
if not adapter.detect(root):
    raise ValueError(
        f"No build.gradle(.kts) at {root}. "
        f"Run `gradle init --type kotlin-library` to scaffold.",
    )
```

And `kotlin_list_hooks` (language_tools.py:333-338). Both call `adapter.detect(root)` and raise `ValueError` when False.

Plan Task 6 Step 3 (lines 1193-1235 of the plan) does NOT include this check:

```python
@mcp_app.tool()
async def format_jinja_templates(projects: list[str]) -> dict:
    """..."""
    _require_auth_config()
    for p in projects:
        _validate_project_root(p)
    from crackerjack.adapters.web.jinja_formatter import format_template
    # ... directly iterates projects, formats .html/.j2/.jinja files ...
```

The docstring says:

> Reads each `*.html` / `*.j2` / `*.jinja` file, formats per the two-tier canonical policy

— but never requires the Web adapter to be enabled at the project root. A Python project with Jinja templates (Django, Sphinx, MkDocs, fastblocks itself) is a valid target for "format my templates" but should be gated on the user opting in via `[tool.crackerjack.web] enabled = true`. Today the tool silently rewrites templates in a Python project that has neither opted in nor has a `package.json`.

The risk is concrete: a user running `crackerjack format-jinja --projects src/` on a fastblocks submodule (which has neither `package.json` nor the opt-in) would have its Jinja templates rewritten. That rewrites output for templates the project never intended to be auto-formatted.

**Required fix:** In `format_jinja_templates`, after auth + per-project validation, check `web_enabled(root)` for each project_root. Raise `ValueError` if not enabled (mirroring the Kotlin pattern at language_tools.py:289-293). The plan also needs a test `test_format_jinja_templates_rejects_python_project_no_opt_in` mirroring `test_kotlin_bump_version_rejects_non_kotlin_directory` (test_language_tools.py:253-265).

**Confidence:** HIGH (spec Writing F3 is unambiguous; Phase 3 MCP review MEDIUM 1 already flagged the same inconsistency for `kotlin_list_hooks`).

### HIGH 2 — `format_jinja_templates` happy-path test mocks the wrong layer; won't catch contract regressions

Plan Task 6 Step 1, `test_format_jinja_templates_runs_with_auth` (plan lines 1118-1135):

```python
async def test_format_jinja_templates_runs_with_auth(tmp_path: Path) -> None:
    """Happy-path test (per MCP HIGH-3 / Testing HIGH-1 Phase 3 analog)."""
    (tmp_path / "package.json").write_text("{}")
    (tmp_path / "templates").mkdir()
    (tmp_path / "templates" / "test.html").write_text("{% if x %}A{% endif %}")
    monkeypatch = pytest.MonkeyPatch()
    try:
        monkeypatch.setenv("MAHAVISHNU_AUTH_ENABLED", "true")
        monkeypatch.setenv("MAHAVISHNU_JWT_SECRET", "test-secret")
        monkeypatch.setenv("MAHAVISHNU_PROJECT_ROOTS", str(tmp_path))
        _, tools = asyncio.run(_register())
        tool = tools["format_jinja_templates"]
        result = asyncio.run(tool.fn(projects=[str(tmp_path / "templates")]))
    finally:
        monkeypatch.undo()
    assert "files" in result
    assert any("test.html" in f for f in result["files"])
```

Two gaps:

1. **`test_format_jinja_templates_requires_auth` is the only failure-mode test.** There is no `test_format_jinja_templates_rejects_path_traversal` (Phase 3 review precedent: `test_swift_bump_version_rejects_path_traversal` at test_language_tools.py:96-108). Without it, the `_validate_project_root` call inside `format_jinja_templates` is uncovered by the integration test (the helper itself is covered by Swift's test, but the tool's wiring is not).
2. **The happy-path test does not assert the file content was actually rewritten.** It only asserts the path appears in `result["files"]`. A regression that returns `files=[...]` without ever calling `write_text()` would pass this test. Compare `test_kotlin_bump_version_runs_with_auth` (test_language_tools.py:191-251) which asserts `(tmp_path / "gradle.properties").read_text() == "version=1.3.0\n"` after the call.

The Phase 2 final-review fake-green pattern that the Phase 3 MCP review HIGH 3 explicitly cited ("the fake-green pattern that was caught at Task 7 review") is the same risk here. The Phase 4 happy-path test inherits the failure mode.

**Required fix:** Two additions:

1. Add `test_format_jinja_templates_rejects_path_traversal` mirroring `test_swift_bump_version_rejects_path_traversal` (test_language_tools.py:96-108) but with `format_jinja_templates(projects=[<outside-allowlist>])`.
2. Strengthen `test_format_jinja_templates_runs_with_auth` to read back `(tmp_path / "templates" / "test.html").read_text()` and assert Tier 1 actually applied (e.g., trailing newline).

**Confidence:** HIGH (Phase 2/3 reviews both flagged the same pattern; precedent is well-established).

### MEDIUM 1 — `check_web_lint` adopts the `kotlin_list_hooks` semantics (`ValueError` on detect-False), widening the Phase 3 MEDIUM 1 inconsistency

Phase 3 MCP review MEDIUM 1 flagged:

> `kotlin_list_hooks` raises `ValueError` on `KotlinAdapter.detect() == False`; Swift's `swift_list_hooks` does not.

The review's recommendation: pick one. Phase 4 picks the Kotlin side:

```python
async def check_web_lint(project_root: str) -> dict:
    ...
    if not web_enabled(root):
        raise ValueError(
            f"Web adapter not enabled at {root}. "
            f"Add `package.json` or set `[tool.crackerjack.web] enabled = true`."
        )
```

This widens the existing inconsistency to three tools (`kotlin_list_hooks`, `check_web_lint` raise; `swift_list_hooks` does not). Swift's `detect()` is a single boolean (Package.swift present?), Kotlin's `detect()` is also a single boolean (build.gradle present?). Web's `web_enabled()` is more nuanced (package.json OR opt-in). The "raise on detect-False" semantic is therefore defensible for Web (a Python project without opt-in has no business calling `check_web_lint`), but the inconsistency with Swift remains.

**Required fix:** None strictly required — the design choice is defensible. Flag in the Spec Revision Notes section so the spec can be amended to clarify the policy. Future phase should pick one rule and apply it consistently across all `*_list_hooks`/`check_*_lint` tools.

**Confidence:** MEDIUM (consistency concern, not a wire-protocol bug; defensible per-detection semantics).

### MEDIUM 3 — Inline imports inside `format_jinja_templates` and `check_web_lint` are gratuitous at Phase 4

Phase 3 MCP review MEDIUM 2 noted:

> Late imports inside the tool function — the plan's `from crackerjack.adapters.kotlin.lifecycle import KotlinLifecycle` etc. are inside the async function body. This was done to defer-import before the adapter existed (Task 7 in Phase 2 was created before Phase 3's adapter package); but by Phase 3 execution time, those modules exist and the deferred imports are gratuitous.

Phase 3 corrected itself by moving imports to module top in `_run_kotlin_lifecycle_sync` (language_tools.py:151-154). The Phase 4 plan re-introduces the same pattern:

```python
@mcp_app.tool()
async def format_jinja_templates(projects: list[str]) -> dict:
    ...
    from crackerjack.adapters.web.jinja_formatter import format_template
```

```python
@mcp_app.tool()
async def check_web_lint(project_root: str) -> dict:
    root = _validate_project_root(project_root)
    from crackerjack.adapters.web import WebAdapter
    from crackerjack.adapters.web.detection import web_enabled
```

By Phase 4 execution time, `crackerjack.adapters.web` exists (Task 2, Task 3, Task 5 of this plan). The deferred imports are gratuitous. They slow first-call latency (Python re-runs import), complicate testing (must mock `__import__` rather than module-attribute), and create a stylistic drift from `swift_bump_version` / `kotlin_bump_version` whose dependencies are imported at module top.

**Required fix:** Move the three imports to the top of `language_tools.py`:

```python
from crackerjack.adapters.web import WebAdapter
from crackerjack.adapters.web.detection import web_enabled
from crackerjack.adapters.web.jinja_formatter import format_template
```

(Pair with the existing top-level imports of `SwiftAdapter` / `make_git_backend` / etc.)

**Confidence:** MEDIUM (style drift; same fix the Phase 3 review applied).

### LOW 1 — `format_jinja_templates` does not call `path.resolve(strict=False)` on the Jinja path glob; symlink traversal unguarded

Plan Task 6 Step 3 (line 1223):

```python
for path in proj.rglob("*"):
    if not path.is_file() or path.suffix not in {".html", ".j2", ".jinja"}:
        continue
```

`proj` comes from `Path(project_dir)` where `project_dir` is an entry of `projects` (already validated by `_validate_project_root`). `proj.rglob("*")` resolves the project root to its canonical form (the validation includes `.resolve(strict=False)`), so symlink escapes inside the project root are the only concern.

A Jinja template that is a symlink to `/etc/passwd` (for example) would have `path.is_file()` return True (the symlink target exists) and would be opened with `path.read_text()`. The content would then be reformatted and written back to the symlink, modifying the target file.

Compare with Phase 3's `_validate_project_root` (language_tools.py:74): it resolves the root, but doesn't recursively check symlinks inside.

This is **not strictly a Phase 4 regression** — the existing `_validate_project_root` has the same gap for any tool that reads files inside the validated root. But `format_jinja_templates` is the first mutation tool that touches arbitrary files inside the project (vs. only writing well-known config files like `gradle.properties`). The blast radius is wider.

**Required fix (optional):** Add a symlink guard to the loop:

```python
if path.is_symlink():
    continue  # don't follow symlinks — format only real files in project
```

Or resolve each file and re-check it's under the validated root. Defensive but not strictly required — the existing project's threat model treats the validated root as trusted.

**Confidence:** LOW (defensive hardening; depends on threat model).

### LOW 3 — Plan does not test `format_jinja_templates` against a fixture with CRLF line endings; Tier 1 "no trailing whitespace" may strip `\r`

Spec Jinja F1 (line 378):

> `lex()` normalizes CRLF → LF — preserve CRLF flag from raw input if needed.

The plan's `format_template` (Task 4 Step 4, plan lines 835-876) reconstructs source from `env.lex(source)`. If `source` ends with CRLF, `lex()` strips it and the output is LF. The Tier 1 fix-ups (trailing newline, no trailing whitespace) run on the LF-normalized text. The CRLF provenance is lost.

**This is a spec concern, not a plan concern** — the spec acknowledges the issue without mandating preservation. The plan's implementation matches the spec's minimum. If CRLF preservation is required (e.g., Windows repos), this needs a spec amendment to require it. Otherwise the test corpus should not include CRLF inputs.

**Required fix:** None unless CRLF preservation becomes a spec change. Flag in Spec Revision Notes.

**Confidence:** LOW (spec ambiguity, not plan bug).

## Plan Quality Verdict

**Structurally sound; one security-relevant gap (HIGH 1) and one test-quality gap (HIGH 2).**

The plan correctly mirrors the Phase 2/3 MCP pattern: tools added to the existing `language_tools` group, `_require_auth_config` and `_validate_project_root` (Phase 3-fixed) reused, `asyncio.to_thread` wrapping applied, `MAHAVISHNU_PROJECT_ROOTS` allowlist respected. The registration pipeline step-skipping rationale (steps 2 and 3 pre-baked by Phase 2) is correctly argued and verified by reading `profiles.py` directly.

The two material findings are:

1. **HIGH 1** is a **spec compliance gap**, not a code bug. The Python-side detection guard is implemented in Task 2 and Task 5, but the MCP tool layer (`format_jinja_templates`) doesn't enforce it — a Python project without opt-in or `package.json` can have its Jinja templates rewritten. Fix is one `if not web_enabled(...): raise ValueError(...)` block (mirroring `kotlin_bump_version` pattern at language_tools.py:289-293) plus a corresponding test.

2. **HIGH 2** is a **test-quality regression** of the same pattern the Phase 2/3 reviews caught. The happy-path test asserts only the path appears in the response, not that the file was actually rewritten — exactly the "fake-green" pattern that the Phase 2 final-review caught. The fix is read-back assertions and a path-traversal test.

The remaining findings are quality improvements that can land in the same Task 6:

- MEDIUM 1: `check_web_lint` widens the Phase 3 MEDIUM 1 detect-False inconsistency. Defensible; flag in Spec Revision Notes.
- MEDIUM 2: `test_detect_languages_returns_adapter_names` should assert `"kotlin"` and `"web"` (Phase 3 carry-over gap).
- MEDIUM 3: move inline imports to module top (matches Phase 3 corrected pattern).
- LOW 1: symlink guard inside `format_jinja_templates` (defensive hardening).
- LOW 2: `_tool_registry_keys.json` fixture rebuild (Phase 2 MCP F3 carry-over).
- LOW 3: CRLF handling (spec ambiguity; no plan change unless spec is amended).

Recommend: fix HIGH 1 (MCP-layer Web detection guard) before Task 6 implementation begins — this is the same class of gate the Phase 3 review applied to `_validate_project_root` (HIGH 1 carry-over from Phase 2). Fix HIGH 2 (strengthen happy-path + add path-traversal test) in the same Task 6 commit. The rest can land as Task 6 polish or be deferred to Phase 4.5/Phase 5.
