# Python Lens Review

Reviewed: `docs/superpowers/specs/2026-09-07-crackerjack-multi-language-design.md`
Reviewer role: Python review lens
Status of spec: Draft (Phase 0)
Crackerjack posture: Python 3.14 minimum, 11K+ tests, mypy/pyright strict, `from __future__ import annotations` mandated, no `Any` in tool inputs, Oneiric logger, async I/O at orchestration layer, no `assert` in production (`mahavishnu/**` rule mirrored in crackerjack per CLAUDE.md).

## Findings (most-severe first)

### F1: `Hook` dataclass has no discriminator for "fail vs skip" when the CLI is missing
- **Line**: 142–150 (Hook dataclass), in tension with 174 (Swift = fail) and 209 (Web = hybrid skip).
- **Summary**: The error-handling table specifies two contradictory policies — Swift fails the gate when `swift` is missing, Web falls back to a Python implementation (effectively skip-with-warning). The `Hook` dataclass exposes only `fallback: Callable | None` to carry this signal. With `fallback is None`, a runner cannot generically tell whether the adapter intended "skip-with-warning" (CLI absence is recoverable noise) vs "fail-gate" (CLI absence is fatal). The runner either needs per-adapter side-channel lookup, which breaks the abstraction, or every adapter authors a fallback that just raises — defeating the dataclass.
- **Failure scenario**: A future Rust adapter author copies the Swift pattern (`fallback=None`) but intends the Web pattern (skip-with-warning when `cargo` absent). The runner silently fails the gate for a tool that should be optional. Or vice versa: a CI environment without `swift` installed flags Swift hooks as gating failures when they were designed to be a hard requirement, and a Web hook's missing fallback is treated as a soft warning.
- **Category**: correctness.
- **Recommendation**: Add an explicit field to `Hook`, e.g. `missing_cli_behavior: Literal["fail", "skip_warning", "fallback"]`, defaulting to `"fail"` for adapters that follow the Swift contract. Swift's three hooks set `missing_cli_behavior="fail"` and `fallback=None`; Web hooks set `missing_cli_behavior="fallback"` and supply the Python call. The runner becomes a pure dispatch on the dataclass.

### F2: `Hook.fallback: Callable | None` is structurally too loose
- **Line**: 147.
- **Summary**: The dataclass accepts any callable. Without a typed signature, every adapter invents its own (args, kwargs, return value). Cross-language fallback invocation becomes a stringly-typed API. Crackerjack's pyproject bans `Any` in tool inputs (CLAUDE.md / `crackerjack-compliant-code` skill); a literal `Callable | None` without a `ParamSpec` or `Protocol` is `Any`-in-costume at the function-boundary.
- **Failure scenario**: A Swift hook's fallback returns `(exit_code, stdout)` as a tuple, a Web hook's fallback returns a `HookResult` dataclass, a Kotlin hook's fallback returns nothing. The runner must `isinstance`-check each return shape. Worse, a fallback signature change in v0.81 silently breaks MCP-server tool consumers that expect the tuple shape.
- **Category**: correctness.
- **Recommendation**: Define a `HookResult` dataclass (or `TypedDict`) with `exit_code`, `stdout`, `stderr`, `duration_seconds`, `fixed_files: list[Path]`. Define `HookFallback = Callable[[HookContext], HookResult]` where `HookContext` carries `project_root: Path`, `files: list[Path]`, `cli_command: tuple[str, ...]`. Annotate `fallback: HookFallback | None`. The signature pins both ends.

### F3: Async vs sync adapter protocol is undecided; existing shell.adapter is sync
- **Line**: spec is silent on this. Memory entry `mcp-bootstrap-terminal-adapter-mock-fallback.md` indicates crackerjack's shell adapter is the established dispatch point.
- **Summary**: The spec implies sync (subprocess via `cli_command`, "in-process Python" for Jinja formatter, sync `read()` / `write()` on `VersionSource`). It does not say so. The MCP server (port 8676) is FastMCP, which is async. A runner that is async at the top and dispatches sync hooks via `loop.run_in_executor` would block the event loop on long Swift builds; a fully sync runner can't share FastMCP's event loop without thread gymnastics.
- **Failure scenario**: Phase 1 refactor commits to sync adapters. Phase 2 ships Swift hooks that emit real-time progress on the MCP WebSocket. The current dataclass design has no place to surface progress events. Either the contract changes mid-roadmap (breaking the Phase 1 promise of zero behavior change) or the runner accumulates special-cases that retro-fit progress into stdout-stderr scraping.
- **Category**: risk.
- **Recommendation**: Phase 1 commit explicitly: "Adapter protocol is sync (PEP 544). Hook execution runs in a `ThreadPoolExecutor` from the async MCP runner." State this in `## Architecture` above the dataclass block. Mark this as a Phase-2-evaluable decision; if Swift/Kotlin hooks need progress, switch to `AsyncHook` Protocol then.

### F4: "No behavior change for Python projects" claim lacks a preservation checklist
- **Line**: 311–313.
- **Summary**: Spec says the existing 11K+ tests must keep passing and "no behavior change". The behaviors to preserve are not enumerated. Past experience (`crackerjack-version-bumping-manual.md`, `crackerjack-fast-hooks-ruff-autofix.md`) shows that "no behavior change" claims frequently omit subtle surfaces: fast_hooks order, exact CLI flag set, exit codes, the `--autofix` flag interactions, env-var influence on hooks, and the relationship between `--skip-hooks` and individual hook filtering. A pure reorg is correct in spirit but misses these surfaces.
- **Failure scenario**: After Phase 1, `crackerjack run --autofix` runs hooks in a different order than before (because `hooks()` returned a different list ordering or non-deterministic set). The 11K tests pass, but a downstream consumer (e.g., Mahavishnu's worker that diffs pre/post autofix output) sees different outputs and silently retries. Failure is invisible to the crackerjack suite because none of those 11K tests assert hook-call ordering.
- **Category**: completeness.
- **Recommendation**: In `### Phase 1 — Foundation`, list the surfaces that must be byte-identical: per-hook CLI argv (capture in golden test), per-hook env (same), per-hook timeout (same), `autofix` flag handling (same), exit-code propagation (same), MCP tool output for `detect_languages`-equivalent helpers (same). Add a `tests/golden/test_python_adapter_byte_for_byte.py` fixture that runs existing CLI invocations through both the old and new adapter and diffs.

### F5: VersionSource Protocol snippet omits `self`; copy/paste foot-gun
- **Line**: 154–157.
- **Summary**: The snippet is `def read() -> str: ...`. In `typing.Protocol` classes, `self` is implicit under PEP 544 so this is valid Python — but a crackerjack developer copying this into a concrete adapter class will write `def read() -> str: ...` literally, miss `self`, and crash at call time. Per `crackerjack-p-minor-full-lifecycle.md` and the version-bump spec, `VersionSource.read()` is on the hot path during `crackerjack run -p minor`.
- **Failure scenario**: Concrete `PyProjectVersionSource.read()` defined as `def read() -> str: return self._version` — TypeError: read() takes 1 positional argument but 2 were given — discovered only at runtime by `crackerjack run -p minor`.
- **Category**: correctness.
- **Recommendation**: Show `def read(self) -> str: ...` and `def write(self, new_version: str) -> None: ...` in the spec. The cost is zero; the safety margin is large.

### F6: `Hook` dataclass missing `cwd`, `env`, `parallel_safe`
- **Line**: 142–150.
- **Summary**: The current fast_hooks path supports per-hook CWD, env injection, and parallel-safety tagging. The spec dataclass declares `name`, `cli_command`, `fallback`, `timeout_seconds`, `autofix` only. Three contract regressions are smuggled in: hooks that ran from `project_root` (e.g., `./gradlew`) lose their CWD; hooks that needed `PYTHONPATH` or `VIRTUAL_ENV` lose their env; parallel execution loses the per-hook allow-list.
- **Failure scenario**: `kotlin.ktlint` hook under `./gradlew` — `./gradlew` resolves relative to its own directory, not the process cwd. With no `cwd` field on the dataclass, the runner must invent a per-language CWD policy; the wrong default breaks the hook for every Kotlin project that doesn't run from `gradlew`-root.
- **Category**: completeness.
- **Recommendation**: Add `cwd: Path | None = None` (default = `project_root` at runtime), `env: Mapping[str, str] | None = None` (merged with `os.environ`), and `parallel_safe: bool = True` to the dataclass. Document defaults so the migration is zero-impact for adapters that don't need overrides.

### F7: `from __future__ import annotations` mandate not referenced; Pydantic-fwd-ref bug class is back-door relevant
- **Line**: 121–157 (adapter snippets); 365 (MCP tool registration).
- **Summary**: Per CLAUDE.md "Crackerjack-compliant code", every source file must lead with `from __future__ import annotations`. The spec's code snippets omit it. The dataclass + Protocol snippets will be pasted into `crackerjack/adapters/python/*.py` files where mypy strict enforces this. More importantly, MCP tool registration goes through FastMCP, which uses Pydantic models for the tool-input schemas. Per memory `pydantic-future-annotations-forward-ref.md`, Pydantic v2 + `from __future__ import annotations` + forward-ref (TYPE_CHECKING) is a confirmed bug class. Adding new MCP tools (e.g., `run_swift_hooks`, `bump_swift_version`) creates new Pydantic-v2-input-model sites.
- **Failure scenario**: A `bump_swift_version(version: str)` tool registered with `class Input(BaseModel): ...` and `from __future__ import annotations` produces a Pydantic model that fails to introspect `version: str` field metadata at runtime, manifesting only when an MCP client calls the tool. Crackerjack pre-1.0 doesn't have integration tests against in-process MCP for new tools (memory `2026-08-29-mcp-tool-registration-dual-track-drift-pattern.md` confirms the test gap). The Phase 2 MCP tool integration tests pass via unit tests; the live MCP round-trip fails.
- **Category**: risk.
- **Recommendation**: Spec should state explicitly: "Every adapter module MUST start with `from __future__ import annotations`. MCP tool input models MUST be declared in a `if TYPE_CHECKING: ...` annotated-string or use `pydantic.Field(...)` directly so the introspection survives PEP 563." Cross-reference the existing memory entry in the spec's `## Risks`.

### F8: `Protocol` does not enforce the `name: str` class attribute at runtime
- **Line**: 125–139 (`LanguageAdapter` Protocol).
- **Summary**: `typing.Protocol` with structural typing means `name: str` is a hint, not an enforced attribute. An adapter author can write `class RustAdapter: ...` and forget to define `name` (or typo it as `nme`), the type checker doesn't catch this without `@runtime_checkable`, and the registry silently registers `name=""` adapter. With third-party entry-point adapters (crackerjack-rust-adapter etc.), this is a real upgrade hazard.
- **Failure scenario**: User installs `crackerjack-rust-adapter` v0.1 which defines `nme = "rust"`. Type check passes (Protocol is structural), entry-point loads, registry has two entries: `""` and `"python"`. `cli_command_names` list is wrong, all subsequent logging in MCP responses is wrong, and the user cannot tell which adapter is the culprit.
- **Category**: correctness.
- **Recommendation**: Mark the adapter Protocol `@runtime_checkable` and add an explicit `if not isinstance(adapter, LanguageAdapter): raise AdapterContractError(...)` in the registry loader. Concrete adapters should be `dataclass(frozen=True)` (not bare classes) so `name: str = "python"` is a required class-level field with a default, which dataclass mechanically enforces.

### F9: `version_source()` / `lifecycle()` re-instantiation semantics not stated
- **Line**: 131–138.
- **Summary**: Both methods return instances. If `version_source()` is called twice, does the second call return the same `VersionSource` instance (with bound state) or a fresh one? Same for `lifecycle()`. The spec doesn't say. If a `VersionSource` is intended to hold a read-cache (e.g., for `read()` to be idempotent and cheap), the contract must require a single instance per language per project.
- **Failure scenario**: A future `cached PyProjectVersionSource` returns a cached value the first call and re-reads on the second call because the runner treats them as independent. The `bump → read-back` round-trip (spec line 281: "fail if mismatch") flaps.
- **Category**: completeness.
- **Recommendation**: Add to the contract: "Adapters MUST return the same `VersionSource` / `Lifecycle` instance for repeated calls with the same `project_root`. The registry caches by `(adapter, project_root)`." Pin this in the dataclass docstring or as a `Protocol` method with explicit notes.

### F10: Jinja formatter round-trip invariant is necessary but not sufficient
- **Line**: 216, 290–305.
- **Summary**: `format(parse(format(x))) == format(x)` checks AST preservation. It does not check Jinja2 *rendering* equivalence. A formatter that silently rewrites `{{ x }}` to `{{x}}` (collapsing internal whitespace) passes the round-trip test (the AST is identical) but may collapse the delimiter-pair in custom-delimiter mode (e.g., custom `variable_start_string="[% "` may have different whitespace rules than the default `{{`). The Python formatter and PyCharm formatter could both pass their corpus tests and diverge on rendered output.
- **Failure scenario**: A fastblocks Jinja template with custom delimiters `[% if x %]` is auto-formatted to `[%if x%]` by an overzealous whitespace policy. The round-trip test passes because `[% if x %]` parses to the same AST. PyCharm refuses to load the file (delimiters must be followed by space, per fastblocks convention). User is stranded until manual fix.
- **Category**: risk.
- **Recommendation**: Add a render-equivalence test alongside the round-trip test: pick a fixture subset, render with `jinja2.Template(...).render(...)`, compare the rendered output before and after formatting. Use real fastblocks fixture samples (`[%`, `[[`, `[#` delimiters), not synthetic ones.

### F11: Optional-dependency / `ImportError`-fallback pattern not specified for fallback callables
- **Line**: 147, 207–213.
- **Summary**: Web hooks have "Python fallback if CLI missing" but the spec doesn't say how that import is guarded. The hook module might `import jinja2`; on a system without jinja2, the importer needs a try/except ImportError that yields `fallback=None` with a warning. Without a prescription, each adapter invents its own error-handling. Memory `pydantic-future-annotations-forward-ref.md` plus the crackers' "-D bandit B101" plus existing hook-system conventions all suggest a canonical pattern, but the spec leaves it implicit.
- **Failure scenario**: A user installs crackerjack on a stripped-down image without `jinja2` installed. Web hooks load at import time, ImportError bubbles up to the runner, registration crashes, and the whole `crackerjack run` fails with a stack trace — when the spec's error table says "skip with warning" was supposed to happen.
- **Category**: correctness.
- **Recommendation**: Spell out a per-adapter helper, e.g.: "Use `try:\n    from .jinja_runtime import run_format as _fallback\nexcept ImportError as exc:\n    log.warning(...); _fallback = None` then return `Hook(fallback=_fallback, ...)`. Crackerjack's pyproject has `jinja2` as a transitive dep, but the principle should be documented so future Rust/Go adapters that need a Python fallback guard imports uniformly."

### F12: `cli_command: tuple[str, ...]` glob expansion strategy undefined
- **Line**: 145, 203–207.
- **Summary**: Web hooks like `npx stylelint **/*.css` and `npx html-validate "**/*.html"` rely on shell glob expansion. The runner subprocess invocation can be `subprocess.run(argv, shell=False)` (passes `**/*.css` literally to `npx`, which then calls `node` which doesn't expand it) or `shell=True` (subprocess invokes shell, which expands it, but introduces a shell-injection vector if any component of `cli_command` is parameterized). Spec doesn't pick a policy.
- **Failure scenario**: Linux shell expands `**/*.css` to filenames; defaultcrackerjack's subprocess harness on Windows doesn't (PowerShell's `**` is non-portable). The hook silently runs against no files, returns zero issues, and the gate passes.
- **Category**: correctness.
- **Recommendation**: Pick one and document: (a) "all `cli_command` strings are passed as argv to `subprocess.run(..., shell=False)`; adapters that need globbing call `crackerjack.adapters._glob.shell_glob(argv)` explicitly", or (b) "the runner uses `shlex` to compose, with a documented `ShellSafe` test gate". Either is fine; the cost of not choosing is the Windows-failure scenario above.

### F13: Entry-point discovery + caching strategy not specified
- **Line**: 105–113, 365.
- **Summary**: `[project.entry-points."crackerjack.language_adapters"]` is the documented contract, but the spec doesn't say how/when entry points are loaded. `importlib.metadata.entry_points()` is correct for Py 3.10+, but spec is silent on: (a) whether the registry caches, (b) what happens if the same name is registered by two third-party packages, (c) whether entry-point discovery runs once per `crackerjack run` or once per CLI subcommand.
- **Failure scenario**: A user's `pip install crackerjack` also installs `crackerjack-rust-adapter` from a fork; both register `crackerjack.language_adapters` group, same `name="rust"`. Resolution is first-wins, last-wins, or raise — the spec is silent. A user upgrades `crackerjack-rust-adapter` and the new entry point isn't visible because of stale cache.
- **Category**: risk.
- **Recommendation**: State the contract: "Entry points are loaded once per CLI invocation via `importlib.metadata.entry_points(group='crackerjack.language_adapters')`. Conflicts raise `DuplicateAdapterError`. The result is cached for the duration of the run; CLI exit flushes the cache. Tests use a fixture-entry-point mechanism (not the real metadata) so unit tests don't depend on install state."

### F14: Hook ordering & idempotency preservation unaddressed
- **Line**: 262, 311.
- **Summary**: Spec promises "No behavior change for Python projects" but the new `hooks() -> list[Hook]` shape doesn't guarantee that the order in which Python hooks are returned matches today's order. If today Python hooks run `ruff → mypy → ty → zuban → complexipy → ...` (a well-defined order), and the new `PythonAdapter.hooks()` returns them in a different order (sorted by name, defined order, or random), the gate output changes. The 11K tests presumably don't pin hook order — but downstream Mahavishnu/Dhara code may.
- **Failure scenario**: A test fixture expects `ruff_check.exit_code=0` after mypy failures; today the runner reports both, fails the gate. After refactor, mypy runs first and the runner prints only `mypy.exit_code=1`. A CI test that asserted on stdout text count fails. None of the 11K crackers tests cover this scenario because they exercise `crackerjack` in isolation, not as a Mahavishnu subprocess child.
- **Category**: risk.
- **Recommendation**: In `adapters/python/hooks.py`, build the hook list explicitly in a frozen module-level tuple constant: `PYTHON_HOOKS: tuple[Hook, ...] = (ruff_hook, mypy_hook, ty_hook, ...)`. Both tests and the runtime use the same tuple, guaranteeing order.

### F15: Python 3.14 minimum + PEP 749 (t-strings) interplay
- **Line**: 362.
- **Summary**: Crackerjack is Py 3.14+. PEP 749 t-strings are now stable. The Hook dataclass uses `tuple[str, ...]` which is modern syntax — fine. But if any adapter later wants `t-strings` for templating error messages, the spec's plain `str` fields would force a future ad-hoc refactor. This is a "watch the language move" signal, not a current defect.
- **Category**: completeness.
- **Recommendation**: No change needed now. Note in `## Compatibility notes` that the design assumes Python 3.14+ syntax and that PEP 749 t-strings are available if template-style messages become common later.

## Coverage Statement

This review covered, from the Python lens:

1. **Phase 1 refactor safety**: behavior-preservation surfaces (F4), hook-order preservation (F14), existing shell.adapter / subprocess call sites (F3), 11K+ test confidence check.
2. **`LanguageAdapter` Protocol design**: structural vs nominal typing (F8), sync/async choice (F3), return-instance semantics (F9), entry-point discovery (F13).
3. **`Hook` / `VersionSource` dataclass field types and shapes**: `tuple` vs `list` choice (correct as-is), `Callable | None` loose typing (F2), missing CWD/env/parallel fields (F6), missing missing-CLI-behavior discriminator (F1), `self`-less method snippet (F5), `cwd`/`env`/`parallel_safe` gaps (F6).
4. **Async considerations**: sync-vs-async protocol decision gap (F3), subprocess vs asyncio (F3).
5. **Type hints / modern syntax**: PEP 604 union (`X | None`) usage (✓ in spec), `tuple[str, ...]` (✓), `from __future__ import annotations` mandate not surfaced (F7), PEP 749 future-proofing (F15).
6. **Error-handling idioms**: optional-dep / `ImportError` fallback pattern (F11), CWD glob expansion policy (F12), runtime type enforcement (F8), Jinja render equivalence (F10).

Items **explicitly out of scope** for this lens (covered or to-be-covered by other lenses):

- Wire-protocol parity between `crackerjack` Python formatter and `jinja2-custom-delimiters` IntelliJ plugin (F10 partially, but XML export & corpus parity better reviewed by Kotlin/IntelliJ lens).
- MCP tool registration surface: FastMCP / mcp-common interaction (MCP lens should cover).
- CLI surface (`crackerjack run`, `crackerjack web jinja format`, etc.) — typer / CLI ergonomics (CLI / DX lens).
- Cross-language test fixtures (`tests/fixtures/swift-lib/` etc.) (testing-strategies lens).
- The "Hybrid implementation" pattern at the runner level (general architecture lens — interface contract is in this lens's purview).
