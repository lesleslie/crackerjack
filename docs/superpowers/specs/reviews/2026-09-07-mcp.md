## Findings (most-severe first)

### F1. Spec omits the actual tool registration mechanism (BLOCKING)

**Spec says (line 365):** "MCP tools: must register under existing
`crackerjack.mcp.tools` module to be picked up by the FastMCP server on port 8676."

**Reality (`crackerjack/mcp/server_core.py:204-224` + `crackerjack/mcp/tools/profiles.py:79-115`):**
Crackerjack uses `mcp_common.tools.dispatch._apply_tool_profile` with three coupled
data structures — `PROFILE_REGISTRATIONS`, `REGISTRATION_MAP`, and
`CRACKERJACK_MANDATORY_GROUPS`. To register a new tool group you must:

1. Create `crackerjack/mcp/tools/<group>_tools.py` exporting `def register_<group>_tools(mcp_app)`.
2. Add `register_<group>_tools` to `_build_registration_map()` in `profiles.py`.
3. Add the group key (`"<group>_tools"`) to one of the three profile tier lists
   (`MINIMAL_REGISTRATIONS` / `STANDARD_REGISTRATIONS` / `FULL_REGISTRATIONS`) —
   not just the module path.
4. Inside the module, every tool goes through a private `_register_<tool>_tool(mcp_app)`
   wrapper that declares a nested `async def` and decorates it with `@mcp_app.tool()`.
   The decorated inner function name becomes the MCP tool name.

**What the spec needs to say:** A new section (e.g., "MCP wiring path") that
enumerates these four steps explicitly, plus the explicit choice of which tier
each new group lands in (recommended: `language_tools` -> `FULL_REGISTRATIONS`,
since STANDARD is reserved for `core/execution/utility/doc`). Without this, an
implementer will drop files in `crackerjack/mcp/tools/` and the tools will be
silently invisible at every profile level — the same class of bug called out in
memory `2026-08-29-mcp-tool-registration-dual-track-drift-pattern.md`.

### F2. `bump_*_version` tools have no transactional rollback (HIGH)

**Spec lines 178-179, 196:** Swift and Kotlin lifecycles are "bump -> commit -> tag
-> push -> gh release" with the same shape as Python's.

**Issue:** The spec does not address partial-failure rollback. If
`VersionSource.write("0.2.0")` succeeds but the subsequent `git commit` fails
(network, hooks, dirty sub-tree), the version file is mutated on disk but no
commit exists — the working tree is silently ahead of HEAD on a non-committed
file.

**Evidence this is a known failure mode (`crackerjack/services/git.py:63-65, 639`):**
> "the version-bump rollback would run, and then the orphan commit
>  ... rollback appeared to succeed but the working tree reverted to HEAD"
> "Fix for the 2026-08-24 version-bump rollback failure where ..."

The Python lifecycle already has a documented 2026-08-24 incident. Replicating
the same shape for Swift and Kotlin without surfacing it in the spec means the
second and third occurrence will happen the same way.

**What the spec needs to say:** Either (a) inherit Python's documented rollback
mechanism and call it out by reference, or (b) define a new contract: every
`bump_*_version` MCP tool must capture a pre-write SHA, wrap the commit/tag/push
chain in a try/except that calls `git restore` on failure, and surface a
structured `{"success": false, "rolled_back": true, "error": "..."}` response so
the caller can decide whether to retry. The spec should also pick a behavior for
"bump succeeded but tag failed and rollback failed" — currently undefined.

### F3. Tool-count drift in pinned test fixtures (HIGH)

**Files:** `tests/fixtures/_tool_registry_keys.json` and
`tests/fixtures/_tool_groups_mapping.json`.

**Current count (from fixtures):** 43 tools across 17 groups.

**Spec adds:** 7 new tools (`run_swift_hooks`, `bump_swift_version`,
`detect_languages`, `run_kotlin_hooks`, `bump_kotlin_version`, `check_web_lint`,
`format_jinja_templates`).

**Impact:** Both fixtures are test-pinned (see `tests/test_doc_drift.py:29-64`
which gates on tool count) and will fail as soon as the new tools land. The
spec needs a fixture-update step (or a "rebuild registry keys" command in the
migration plan). Phase 2-4 of the migration plan should include:

```bash
python -m crackerjack.mcp.tools.discover_query --update-fixtures
```

(or equivalent) so the fixtures regenerate alongside the new tool files.

### F4. Generic tool names risk collisions with Bodai ecosystem (MEDIUM)

**Tool names in spec:** `detect_languages`, `format_jinja_templates`,
`check_web_lint`.

**Risk:** These names are generic enough that future Bodai components (or
existing Mahavishnu pool/utility tools) may want the same names. Crackerjack
tools are reached via `mcp__crackerjack__<name>` after FastMCP namespacing, so
collisions across servers are not technically a problem today — but a future
"merge into bodai umbrella" path (the spec line 348 says "Bodai umbrella
integration") could surface the conflict.

**Recommendation:** Either prefix the names with the crackerjack brand
(`crackerjack_detect_languages`) or namespace them by language
(`swift_run_hooks`, `kotlin_run_hooks`, `web_check_lint`, `web_format_jinja`).
The existing crackerjack convention is unprefixed snake_case verbs
(`clean_crackerjack`, `config_crackerjack`), so the cleaner choice is to add
the language segment: `run_swift_hooks` (already in spec, good),
`bump_swift_version` (good), `detect_languages` (rename to
`crackerjack_detect_languages` or accept the risk and document).

### F5. Auth surface for mutation tools is unspecified (MEDIUM)

**Spec:** No mention of auth for the new MCP tools.

**Existing pattern (`crackerjack/mcp/tools/monitoring_tools.py:189-227`):** Only
`get_comprehensive_status` uses auth via
`crackerjack.services.status_authentication.authenticate_status_request` +
`is_operation_allowed`. All other tools (including `init_crackerjack`, which
mutates filesystem state) are unauthenticated.

**Bodai policy (memory `project_bodai_auth_standardization.md`):**
MultiAuthHandler — Claude Code sub / Qwen / JWT. Crackerjack is
pre-1.0/internal-first, so the current "no auth" posture is the codebase-wide
default.

**What the spec should pin:** The `bump_*_version` tools mutate files and (via
subsequent lifecycle steps) push to GitHub. Even if auth is deferred, the spec
should explicitly state the policy: "These tools are unauthenticated by design,
matching all other crackerjack MCP tools; auth is deferred to a cross-cutting
MCP auth phase tracked in the Bodai auth-standardization work." Otherwise the
gap is silent and a future security review will block on it.

### F6. Error contracts for missing toolchains are undefined (MEDIUM)

**Spec (line 279, "Error handling" table):** "CLI not installed (e.g., `swift`
not in PATH) -> Skip hook with warning; do not fail the gate." This is the
**CLI** behavior.

**Gap:** What does the **MCP tool** do when `run_swift_hooks` is called on a
project whose toolchain is absent? Two reasonable shapes:

```python
# Option A (current crackerjack pattern, see _create_error_response in utility_tools.py)
{"success": False, "error": "Swift toolchain not found in PATH",
 "toolchain_status": "missing", "hint": "Install Swift via ..."}

# Option B (mimics mcp_common pattern)
{"status": "skipped", "reason": "swift not in PATH", "hooks_run": []}
```

**What the spec should say:** Pick one and add it to the error-handling table
under a new row "MCP tool called with missing toolchain -> return
`<shape>` with `toolchain_status: 'missing'`". Otherwise the CLI gate can
"skip with warning" while the MCP tool fails silently with an empty response
or vice versa.

### F7. Async/sync split is left implicit (MEDIUM)

**Spec:** No explicit `async def` vs `def` guidance for the new MCP tool
handlers.

**Existing crackerjack convention (see `crackerjack/mcp/tools/`):** Every
decorated tool function is `async def`, even when the underlying work is sync
(`clean_crackerjack` runs `glob` and `unlink` synchronously inside an async
wrapper). This is consistent with `crackerjack`'s CLAUDE.md rule: "All I/O in
the orchestration layer is async."

**What the spec should say:** Explicitly require `async def` for all new MCP
tool handlers, including the Jinja formatter (which is in-process and
"sync-feeling"). The Jinja formatter must either run inside
`asyncio.to_thread` or be re-cast as async — blocking the event loop on a
multi-file format pass will starve concurrent tool calls on port 8676.

### F8. Profile tier placement not specified (LOW)

**Spec:** Doesn't say which `CRACKERJACK_TOOL_PROFILE` tier the new tools live in.

**Recommendation:** Create a new group key `language_tools` and place it in
`FULL_REGISTRATIONS` only (Kotlin/Swift/Web tools are not core crackerjack
functionality — they are extensions). This matches the `pycharm_tools` /
`otel_tools` precedent (both FULL-only). At STANDARD and MINIMAL, the new
tools are not registered, and `discover_tools` does not list them — which is
correct because a Python-only deployment shouldn't see `run_swift_hooks` in its
tool palette.

If the team wants these tools discoverable on a small Swift-only project (so
operators can see "yes, your Swift hooks are available"), the alternative is
to gate on detected languages at startup (load `language_tools` if any
non-Python marker file is present). That is a more complex pattern and is not
recommended for Phase 1-4.

### F9. Tool description strings not specified (LOW)

**Spec:** Names listed without docstrings or descriptions.

**Existing pattern (`crackerjack/mcp/server_core.py:160-194`):** Tools
registered with descriptions via `@mcp_app.prompt(description=...)` or
`@mcp_app.tool(description=...)` — these descriptions surface in
`discover_tools` output and in MCP client UIs.

**What the spec should require:** Each new tool declares a one-line description
string at registration time (e.g., `run_swift_hooks` ->
"Run Swift toolchain hooks (test, build, format) on the current project").
Without this, `discover_tools` falls back to the function name as the
description, which Mahavishnu orchestestrators will not be able to route on
semantically.

### F10. Tool input schema not specified (LOW)

**Spec:** Uses untyped parameters in `LanguageAdapter` Protocol (e.g.,
`bump(level: str)`).

**Existing pattern:** Crackerjack MCP tools are mostly loose (`async def
get_ide_diagnostics(file_path: str, errors_only: bool = False)` — primitives,
no Pydantic). FastMCP infers the JSON schema from type hints.

**Recommendation (optional):** For `bump_*_version`, accept a Pydantic
`BumpRequest` model with a validated `level: Literal["major", "minor",
"patch"]`. This rejects invalid levels at the MCP boundary instead of falling
through to the Python lifecycle which would raise a 500. The Python lifecycle
itself is untyped, so this is an MCP-only guard — but it is the cleanest place
to enforce the contract.

### F11. Pydantic / `from __future__ import annotations` latent-bug class (LOW)

**Spec line 154-157:** `VersionSource` Protocol is a `class ... Protocol` with
`def read(self) -> str: ...` body annotations.

**Risk (per memory `pydantic-future-annotations-forward-ref.md`):** Pydantic v2
+ `from __future__ import annotations` + TYPE_CHECKING creates a latent bug
class when `VersionSource` is used as a Pydantic field type. The spec does not
show whether the adapters use `VersionSource` in any Pydantic model (likely
no, but worth pinning explicitly). If `Hook` (`@dataclass(frozen=True)`) ever
gets serialized through Pydantic (e.g., for the JSON tool responses), this
becomes a real risk.

**Recommendation:** Either use `typing.Protocol` (runtime-checkable=False) +
string annotations, or avoid `from __future__ import annotations` in
`adapters/base.py`. Add a sentence to the spec clarifying the choice.
