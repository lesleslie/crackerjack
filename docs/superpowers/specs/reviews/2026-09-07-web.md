# Web Lens Review

**Spec under review**: `docs/superpowers/specs/2026-09-07-crackerjack-multi-language-design.md`
**Lens**: Web/CSS/HTML/JS/TS (front-end correctness, toolchain realism, monorepo behaviour)
**Reviewer posture**: read-only; no spec changes proposed as edits. Findings are
diagnostic; the spec author decides what to fix.

## Findings (most-severe first)

### F1. [SEVERE] "Hybrid pattern: CLI primary, Python fallback" is dishonest for web hooks — there is no production-grade Python fallback for any of the four external CLIs

**Spec quote** (line 209): *"Hybrid pattern: each hook first checks for the CLI tool, falls back to a Python implementation if the CLI is missing or fails."*

This is not implementable as written:

- **html-validate fallback.** `html5lib` is a parser, not a validator. `lxml.html`/`bleach`/`BeautifulSoup` are parsers and sanitizers, none of them implement the WHATWG parsing + accessibility + ARIA checks that html-validate bundles. A Python fallback here would be a rules-of-thumb subset ("does it parse? does each `<a>` have href?") at best, and would silently disagree with html-validate on edge cases. Worst-case: the Python fallback says "OK" while html-validate would have said "fail" — and the gate flips between machines.
- **stylelint fallback.** `cssutils` is a parser; `tinycss2` is a parser; neither is a linter. There is no maintained Python CSS linter with stylelint-equivalent rule coverage. A Python fallback would be a stale re-implementation that drifts from the real tool. Same divergence risk as above.
- **tsc fallback.** There is no Python implementation of the TypeScript type-checker. None. This is not a matter of effort — TypeScript's checker is ~200kLOC of TS itself and depends on the TS language service. The only honest "fallback" is to shell out via `node`/`tsc`, which is what the primary path already does.
- **ESLint fallback.** Same story: no Python JS/TS linter, and `pylint`/`ruff` do not understand JS syntax. A Python fallback would be a `node`-exec bridge, not a real fallback.

**Impact.** If a contributor reads the spec and implements "Python fallback" for these four hooks, they will spend weeks writing a half-spec'd validator that contradicts the real tool. If they read it and skip the fallback, the spec is wrong. Either way, the design intent is unclear.

**Recommendation language for the spec author.** Replace the "Hybrid pattern" sentence with: *"Web hooks are CLI-only by design. There is no production-quality Python alternative for stylelint, html-validate, ESLint, or `tsc`. If the CLI is missing, the gate fails with an installation instruction naming the missing dependency (see §Error handling row 'CLI not installed')."* The error-handling table on line 279 already gets this right; the architecture description on line 209 contradicts it.

### F2. [SEVERE] `npx`-based invocation is fragile in Yarn / pnpm / monorepo / CI environments

**Spec quote** (lines 203-206): hook commands all start with `npx stylelint`, `npx eslint`, `npx tsc`, `npx html-validate`.

Real-world failure modes that will surface immediately:

1. **Monorepo with workspaces.** `npx` resolves the package from the nearest `package.json` walking up from CWD. In a pnpm/Yarn workspace, the nearest `package.json` may be the root one, which doesn't list `stylelint` as a dep — only as a dev dep of a workspace. `npx stylelint` will silently download a fresh copy from npm (or fail offline) instead of using the pinned workspace version. This produces "works on my machine" reports where the linter version differs from what the team committed to.
2. **No `npx`.** Some Node installs (older LTS via apt, some Docker base images) ship `node` but not `npm`, hence no `npx`. The spec currently assumes `npx` exists whenever Node does.
3. **Corepack-managed projects.** With `packageManager: "yarn@4.x"` pinned in `package.json`, Corepack will shim `npx` to the wrong runtime, or refuse to run it. Modern Yarn (Berry) and pnpm >= 8 have separate exec commands.
4. **Offline CI.** `npx stylelint` will hit the npm registry on first run (no local install). A clean CI runner without network will fail or pull the wrong version.
6. **Version drift.** `npx eslint@latest` (the default) can pull a major-version bump that removes or renames rules the project relies on, suddenly failing CI for reasons unrelated to the code.

**Recommendation language for the spec author.** Specify the package manager detection strategy explicitly:
- Detect via `packageManager` field in `package.json` (Corepack), then the lockfile (`yarn.lock` vs `pnpm-lock.yaml` vs `package-lock.json`).
- Invoke via the matching exec: `pnpm exec stylelint`, `yarn stylelint`, `npx --no-install stylelint` (only if a local install is present and the lockfile is `package-lock.json`).
- Resolve the workspace root via `pnpm-workspace.yaml` / `workspaces` field before running, and `cd` to it before exec.
- Reject the hook (clear error) if the local CLI isn't installed and `--no-network` mode is on. Add a `--offline` flag derived from existing CI conventions.

The spec already lists `gh`/`swift`/`./gradlew` as direct binary paths (no `npx`) — the web adapter should follow the same convention, picking the local bin from `node_modules/.bin/{stylelint,eslint,tsc,html-validate}` and shelling out directly, falling back to `npx --no-install` only when the bin is missing but the package is declared in `devDependencies`.

### F3. [SEVERE] Glob patterns are not ignore-aware and will sweep in `node_modules`, build output, source maps, and generated files

**Spec quote** (lines 203, 206): `"npx stylelint **/*.css"`, `"npx html-validate \"**/*.html\""`, and implicitly `"npx eslint ."` / `"npx tsc --noEmit"`.

Bare double-star globs in shell-expanded form will match (or `**` patterns will resolve to):

- `node_modules/**/*.css` and `**/*.js` — stylelint on `node_modules` will produce thousands of false positives from third-party CSS (Bootstrap, Tailwind preflight, normalize.css), and `tsc --noEmit` walking `node_modules` will choke on JS that doesn't have type declarations.
- Build output: `dist/`, `build/`, `.next/`, `.nuxt/`, `.output/`, `public/build/`, `static/_next/`, `out/`, `coverage/`.
- Source maps: `*.css.map`, `*.js.map`. Stylelint will try to lint these.
- Minified bundles: `app.bundle.js`, `vendor.min.css`, `*.min.css`, `*.min.js`. These are generated, not source — linting them produces meaningless errors.
- Generated code: `*.generated.ts`, `*.d.ts` (sometimes), `*.pb.ts`, OpenAPI clients, GraphQL codegen output.
- Test fixtures: `tests/fixtures/**/*.css`, `tests/fixtures/**/*.html`. These may deliberately include intentionally-broken HTML for downstream consumer tests.
- Vendored third-party: `vendor/`, `third_party/`, `static/lib/`.
- Docs: `docs/_build/`, Sphinx output, MkDocs `site/`.

`npx eslint .` will recurse into all of these by default unless `.eslintignore` is set; many fastblocks-style projects don't have one.

**Recommendation language for the spec author.** Spec the default ignore set explicitly, and require the adapter to compose it with the project's own ignore files. Suggested baseline:

```
node_modules, dist, build, .next, .nuxt, .output, out, coverage,
public/build, static/_next, **/*.min.css, **/*.min.js,
**/*.bundle.{css,js}, **/*.{css,js}.map, **/*.generated.ts,
**/*.d.ts, vendor, third_party, tests/fixtures
```

Plus: respect `.gitignore`, `.stylelintignore`, `.eslintignore`, `tsconfig.json#exclude`, and `.htmlvalidateignore` if present. Note that Stylelint v15+ moved to `ignoreFiles` in flat config and removed `.stylelintignore`; spec should pin the minimum Stylelint version.

### F4. [HIGH] `tsc --noEmit` is underspecified — no project selection, no references, no JS-only handling, no `--skipLibCheck`

**Spec quote** (line 205): `web.js.tsc → npx tsc --noEmit`.

Five concrete problems:

1. **No `--project`.** If the project has more than one `tsconfig.json` (frontend `tsconfig.json` + Node backend `tsconfig.node.json` + tests `tsconfig.test.json`, all extremely common in Vite/Next/Nuxt scaffolds), `tsc --noEmit` without `--project` will silently use the cwd's `tsconfig.json` — which may not be the one with the entry the user actually wants checked.
2. **Project references (`references`).** TS >= 3.0 supports `references` in `tsconfig.json`. `tsc --noEmit` does NOT follow references; only `tsc --build` does. If the project uses references (mono-repo libs, e.g., a `packages/ui` + `packages/core` layout), `tsc --noEmit` from the root will type-check nothing useful and report success incorrectly. **This is the most likely silent-pass bug in the design.**
3. **JS-only with `@ts-check`.** A JS codebase that uses `// @ts-check` at the top of files gets type-checked when `tsc` runs over them — but only if `allowJs` and `checkJs` are on in `tsconfig.json`. The spec doesn't mention this case, but several Bodai web stacks use vanilla JS with `@ts-check` rather than `.ts`.
4. **`skipLibCheck`.** Default behaviour of `tsc` is to type-check `.d.ts` files in `node_modules`. This frequently fails on third-party packages that ship slightly out-of-date types (React 18 peer types, etc.). Convention: most projects set `"skipLibCheck": true`. Spec should default to honoring the project's setting rather than imposing its own.
5. **Performance.** `tsc --noEmit` on a real codebase is often the slowest single hook (minutes for a moderate TS app). The timeout defaults need to reflect this — the spec lists per-hook timeouts in Risks §3 only for Swift/Kotlin (10/15 min), and is silent on web timeouts.

**Recommendation language for the spec author.** Specify:

- Default invocation: `npx tsc --noEmit --project <discovered tsconfig>` where discovery walks up from CWD and picks the most-specific `tsconfig.json` unless `references` is set, in which case use `tsc --build`.
- Honor `references` and emit a warning if `--build` is required but the spec's default command is used.
- Honor `allowJs` + `checkJs` for JS-only repos. Detect via absence of any `.ts`/`.tsx` files AND presence of `.js`/`.jsx` with `// @ts-check` comments.
- Don't override `skipLibCheck`; honor the project's setting.
- Timeout: 600 s ceiling for `--build`, 300 s for `--noEmit`, overridable per project.

### F5. [HIGH] Detection heuristic fires on essentially every Bodai repo, including pure-Python repos that don't want web linting

**Spec quote** (line 200): *"Detect: presence of any `.css`, `.scss`, `.html`, `.ts`, `.tsx`, `.js`, `.jsx`, `.jinja`, `.html.j2`, `.tmpl` files at project root or in `src/templates/`, `templates/`, `assets/`, `static/`."*

Concrete false-positive scenarios in the Bodai ecosystem:

- A pure-Python CLI like `akosha` or `dhara` may have a `templates/` directory containing a single `README.html.j2` file used by docs tooling. The detector fires; the user sees `crackerjack run` try to install/run stylelint for a repo with one CSS-shaped template file.
- A Python repo with `docs/index.html` (Sphinx output checked in for hosting) or `assets/logo.svg` referenced from a Markdown file. Detector fires.
- A repo with `.tmpl` files used by `cookiecutter` or `copier` scaffolding — these aren't Jinja templates and don't want formatting.
- A Python repo with one stray `.html` file (e.g., `playwright/index.html` for a smoke test fixture, or a generated `coverage/index.html`).
- Every repo in the registry that has a `static/` directory for serving a single favicon.

Plus the file-extension list includes `.js` and `.ts` — these are present in **every** Python web framework's tooling (`node_modules`-adjacent or scaffold files like `tailwind.config.js`, `postcss.config.js`, `vitest.config.ts`). Detection will fire and the user will be told they have web hooks to run.

**Recommendation language for the spec author.** Make detection stricter and opt-in:

- Require a project marker: `package.json` (for JS/TS hooks), a non-empty CSS asset directory, or a deliberate `[tool.crackerjack.web] enabled = true` in `pyproject.toml`.
- Restrict `.css`/`.html`/`.jinja` detection to source directories defined by convention: exclude `docs/`, `coverage/`, `tests/fixtures/`, `node_modules/`, `dist/`, `build/`. Better: rely on the same ignore set as F3.
- Don't detect `.tmpl` — it's overloaded (cookiecutter, copier, helm, sendmail) and only the user knows which one they mean. Require the user to configure Jinja paths via `[tool.crackerjack.jinja] template_paths = [...]`.
- For the Python+Web hybrid case (fastblocks, splashstand, mdinject), detection is wanted; gate it on a positive marker (presence of `package.json` + a `static/` or `assets/` CSS asset, OR an explicit `[tool.crackerjack.web] enabled = true`).

The spec currently has the right instinct (this is Phase 4, "hooks only", with Web explicitly excluded from lifecycle), but the detection rule is too eager.

### F6. [MEDIUM] Tool choice — `html-validate` is appropriate but the spec is silent on minimum versions, config formats, and SCSS preprocessor support

- **`html-validate`**: appropriate. It's not the most popular tool in the world, but it IS the canonical HTML linter and is widely used by Swedish government, IKEA, and others. It supports JSON config (`.htmlvalidate.json`) and is actively maintained (v8+ as of 2026). No issue here, but spec should pin `html-validate >= 8.0`.
- **ESLint config format**: spec is silent. ESLint v9 (April 2024) made `eslint.config.js` (flat config) the default and deprecated `.eslintrc.*`. As of late 2025, ESLint v10 is the active line. Stylelint v16 (2024) made flat config the default. Tools that the spec invokes need a declared minimum version, otherwise the hooks will fail mysteriously on older configs.
- **Stylelint + SCSS**: spec lists `.scss` for detection but no Sass/SCSS plugin. To lint `.scss`, you need `stylelint-config-standard-scss` plus `postcss-scss` syntax registration. Without it, stylelint will reject `.scss` files with "Unknown syntax". Spec needs to either drop `.scss` from detection or include the plugin dependency in the recipe.
- **No formatter coverage**: the spec covers Jinja formatter but not `prettier` / `dprint` / `biome` for JS/TS/CSS. If users expect `crackerjack run` to format their JS, they'll be surprised. Document the formatter gap explicitly.
- **No accessibility tooling**: `axe-core` via `@axe-core/cli` is the standard for a11y testing. Spec doesn't mention. If `web.html.validate` is the only HTML check, a11y regressions won't be caught.
- **No bundler-aware linting**: in Vite/Webpack projects, `import` paths resolve via aliases (`@/components/...`) that ESLint can't resolve without `eslint-import-resolver-alias` or `eslint-plugin-import`. Spec assumes out-of-box ESLint works.

**Recommendation language for the spec author.** Add a "Tool versions & config formats" subsection that pins minimum versions:

- `stylelint >= 16` (flat config default)
- `eslint >= 9` (flat config default; v10 if active at GA)
- `html-validate >= 8`
- `typescript >= 5.4` (for `--build` + project references reliability)

State explicitly: ".eslintrc.* is not supported; if the project uses legacy config, the hook runs `eslint --config eslint.config.js` only." And either drop `.scss` from detection or include `stylelint-config-standard-scss` as a required peer dep.

### F7. [MEDIUM] No formatter parity with the rest of the crackerjack pipeline; web hooks are lint-only, but the Jinja formatter is the only writer

The spec describes web hooks as lint-only (which is appropriate) but the Jinja formatter is a writer. This asymmetry is fine, but the spec doesn't reconcile it with the existing Python hooks: bandit/ruff/refurb/complexipy are all read-only linters, while `ruff format` is a writer. The hook naming `web.jinja.format` aligns with this convention, but `web.css.stylelint`, `web.html.validate`, `web.js.eslint`, `web.js.tsc` do not — they're called `<linter>.check` in the Python adapter (bandit.check, ruff.check, mypy.check). Spec inconsistency.

Also: the autofix flag (`autofix: bool`) on the `Hook` dataclass (line 149) defaults to false, which is correct for tsc/eslint/stylelint, but stylelint and eslint both support `--fix`. The spec's autofix discussion (line 358) only mentions `swift.format`, `ktlint.format`, `web.jinja.format`. It should mention `web.css.stylelint --fix`, `web.js.eslint --fix` as candidates too — but with a clear opt-in rather than default, since autofix can rewrite user code.

**Recommendation language for the spec author.** Reconcile hook names with the Python adapter convention (`<lang>.<tool>.check` for read-only, `<lang>.<tool>.format` for writers). Add autofix opt-in for stylelint/eslint to the open-questions list.

### F8. [LOW] MCP tool names don't match hook names

**Spec quote** (line 50): MCP tools are `check_web_lint` and `format_jinja_templates`.

Hook names from §Web adapter (lines 203-207): `web.css.stylelint`, `web.js.eslint`, `web.js.tsc`, `web.html.validate`, `web.jinja.format`.

The MCP tool `check_web_lint` maps to the four CSS/JS/HTML hooks but has no namespace structure — clients can't ask "just run the html-validate hook". `format_jinja_templates` matches `web.jinja.format` semantically but doesn't follow the same naming convention.

**Recommendation language for the spec author.** Either rename MCP tools to mirror hooks (`run_web_css_stylelint`, `run_web_html_validate`, `format_web_jinja`) or document the mapping as a deliberate facade (with reason).

### F9. [LOW] Jinja formatter parity claim needs a regression-test corpus at the spec level

The spec mentions a 30-file corpus in `tests/fixtures/jinja-corpus/` (line 304) for parity testing between crackerjack and `jinja2-custom-delimiters`. That's good, but:

- Spec doesn't specify which delimiters the corpus covers. Fastblocks-style `[%`/`[[`/`[#` is mentioned; default `{%`/`{{`/`{#` should also be tested.
- Spec doesn't say who maintains the corpus when delimiter sets are added (cookiecutter uses `{% %}` with different defaults; Copier uses `{% %}` + `{{ }}`).
- Spec assumes PyCharm parity is verified "manually + via a documentation note" (line 306). For a design doc, that's an honest acknowledgment, but the timing of manual verification matters — before or after the 30 files are updated?

This is a forward-looking concern, not a current bug, but it's worth flagging in review since the parity claim is load-bearing for the design.

### F10. [LOW] No ignore-file for jinja autodetect — and the autodetect rule is under-specified

**Spec quote** (line 212): *"Falls back to auto-detection (scan a sample `.jinja` file for the first non-default delimiter)."*

Edge cases:

- What if the file uses default delimiters? Then autodetect returns `None`, and the formatter uses Jinja defaults — but `jinja2.Environment.parse()` will succeed either way. That's fine, but the spec should state "auto-detect returns None means: use Jinja defaults (which are the most common case for cookiecutter/copier templates)."
- What if the file is empty or contains only HTML? Autodetect scans for `{%` first; if absent, falls back to defaults. Spec should specify the precedence.
- What about `{# ... #}` Jinja comments? They're a third delimiter set. Spec lists `comment_start_string` but not what autodetect does when comments use a non-default prefix.

This is low-severity but easy to nail down in the spec.

---

### F11. [LOW] Hook timeout defaults are not specified for web hooks

The Risks section mentions Swift/Kotlin timeouts (10/15 min) but the Web adapter section has no timeouts. Realistic expectations:

- `stylelint`: < 30 s on most projects. 60 s ceiling.
- `eslint`: 30 s – 5 min depending on project size. 600 s ceiling.
- `tsc --noEmit`: 30 s – 10 min. 900 s ceiling.
- `tsc --build`: minutes to tens of minutes. 1800 s ceiling.
- `html-validate`: < 30 s. 60 s ceiling.

Without timeouts in the spec, the first CI run on a large TS project will hit Crackerjack's default subprocess timeout and produce a confusing error. Spec should specify per-hook timeouts with override mechanism.

## Coverage Statement

This lens review covered:

1. **Tool choice reality check** — html-validate, ESLint config formats, Stylelint config formats, TypeScript config handling. Found: F1 (no Python fallback is realistic), F4 (`tsc --noEmit` is under-specified), F6 (no min versions pinned, SCSS gap, no a11y tooling).
2. **npx invocations** — monorepo workspaces, Yarn/pnpm/Corepack, offline CI, version drift. Found: F2 (`npx` is the wrong default invocation).
3. **File glob patterns** — node_modules, build output, source maps, minified bundles, generated files, fixtures. Found: F3 (no ignore set).
4. **`tsc --noEmit`** — project selection, references, JS-only repos, skipLibCheck, performance. Found: F4 (also covers this).
5. **Hybrid CLI + Python fallback** — html5lib/cssutils/tsc-Python. Found: F1 (the design claim is dishonest).
6. **Detection heuristic** — false positives in pure-Python repos. Found: F5 (too eager).

Adjacent observations worth flagging but not blocking:

- Hook name convention inconsistency with Python adapter (F7).
- MCP tool naming mismatch (F8).
- Jinja formatter corpus maintenance (F9).
- Jinja autodetect edge cases (F10).
- Missing per-hook timeouts (F11).

**Severity tally**: 2 SEVERE, 2 HIGH, 2 MEDIUM, 4 LOW.

**Most important issues to address before Phase 4 implementation begins**: F1 (the "Hybrid pattern" claim must be rewritten as CLI-only), F2 (replace `npx` invocation with local-bin resolution), F3 (define ignore set), F5 (tighten detection heuristic with opt-in marker).
