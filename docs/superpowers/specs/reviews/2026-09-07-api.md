# API Lens Review

Reviewed: `docs/superpowers/specs/2026-09-07-crackerjack-multi-language-design.md`
Reviewer role: Public API design lens
Status of spec: Draft (Phase 0)
Crackerjack posture: Crackerjack is at v0.81+; it exposes both a CLI surface and an MCP server (port 8676). The `LanguageAdapter` Protocol, once shipped, becomes a third-party authoring surface — `crackerjack-rust-adapter`, `crackerjack-go-adapter`, etc. — so the protocol is effectively a published API for plugin authors. It is graded accordingly: ergonomic, typed, runtime-checkable, and resistant to copy-paste foot-guns.

---

## Findings (most-severe first)

### F1 — CRITICAL — `LanguageAdapter` is `typing.Protocol` with no `@runtime_checkable`, no nominal enforcement; `name: str` is a structural hint, not a contract

- **Line**: 124–138.
- **Summary**: `class LanguageAdapter(Protocol)` is structural typing. PEP 544 says runtime `isinstance` checks fail unless the protocol is decorated `@runtime_checkable`. The spec registers adapters via entry points (`crackerjack.language_adapters` group) and then presumably loads them. The registry loader will `importlib.import_module(...)` a third-party package (crackerjack-rust-adapter), grab the class, instantiate it, and add it to a `dict[str, LanguageAdapter]`. With structural typing and no runtime check, the loader can register a class that is missing `name`, or has a typo'd method, or implements `detect()` with the wrong signature, and the failure surfaces only when an end user runs `crackerjack run` on a real project. This is the worst possible failure mode: silent, late, user-visible.
- **Failure scenario**: A third-party author writes `class RustAdapter: name = "rsut"  # typo` plus a `detect()` that takes `(self, root, options=None)` (extra arg). Entry-point loads, registry stores under the empty key, runtime falls through to the bundled adapters, and `crackerjack run` on a Rust project silently runs Python hooks that "don't apply" and exits 0. The user assumes Rust support is broken; in fact the adapter is misregistered but never reported as such.
- **Category**: correctness, public API contract.
- **Recommendation**: Two complementary changes:
  1. Decorate `LanguageAdapter` with `@runtime_checkable` and have the registry loader do `if not isinstance(instance, LanguageAdapter): raise AdapterContractError(...)` with a clear message naming which method is missing.
  2. Switch the recommended authoring pattern from "bare class" to `@dataclass(frozen=True)` with `name: str` as a required field (no default). A bare `@runtime_checkable Protocol` plus a `@dataclass(frozen=True)` concrete base is the cleanest hybrid: structural for the protocol, nominal for the actual base class. The registry can offer both `class PythonAdapter(LanguageAdapterBase)` (subclass) and `register_function(adapter)` (decorator) — see F2.
  Reference: Python's own `EntryPoints` from `importlib.metadata` uses this exact pattern (`EntryPoint.load()` returns a `runtime_checkable`-able protocol).

### F2 — HIGH — Authoring pattern is unspecified; "implement a Protocol" is the worst possible DX for third-party packages

- **Line**: 124–138 (the entire `LanguageAdapter` block).
- **Summary**: The spec says "third-party language adapters register themselves by adding the same entry point in their own pyproject.toml" but never explains what the third-party author writes. Implementing a `Protocol` from scratch is awkward in Python: the author has to write `name: str = "rust"` as a class attribute, four method bodies, and remember the exact method signatures. The recommended pattern in 2026 Python is either (a) subclass a documented base class with sensible defaults, or (b) use a decorator that registers a function. The spec doesn't pick either.
- **Failure scenario**: A new maintainer of `crackerjack-rust-adapter` reads the spec, sees a Protocol with four methods, writes:
  ```python
  class RustAdapter:
      name = "rust"
      def detect(self, project_root): return (project_root / "Cargo.toml").exists()
      def version_source(self, project_root): return None
      def hooks(self): return []
      def lifecycle(self, project_root): return None
  ```
  This passes type check (structural), loads fine, but: the base class isn't importable from a stable location (the spec says "from `crackerjack.adapters.base`" but that path is an implementation detail), the Protocol's `self` is implicit so mypy strict complains, and the author can't get sensible defaults for `hooks()` (e.g., a Rust adapter that has *no* lifecycle still has to define `lifecycle()` returning `None`).
- **Category**: developer experience, public API.
- **Recommendation**: Spec an explicit base class as the recommended authoring pattern:
  ```python
  from crackerjack.adapters.base import LanguageAdapterBase

  class RustAdapter(LanguageAdapterBase):
      name = "rust"
      def detect(self, project_root): return (project_root / "Cargo.toml").exists()
      def version_source(self, project_root): return None  # no lifecycle yet
      def hooks(self): return [rustfmt_hook, cargo_test_hook]
  # lifecycle() defaults to None from the base class
  ```
  This is the pattern used by `setuptools`'s `Command`, pytest's `pytest.Item`, and most successful plugin systems. The Protocol stays for typing, but the base class is the public authoring surface. Update the spec's third-party section accordingly.

### F3 — HIGH — Four-method Protocol (`detect`/`version_source`/`hooks`/`lifecycle`) decomposes poorly; `capabilities()` is more discoverable

- **Line**: 127–138.
- **Summary**: The four methods each answer a separate question (does this language apply here? does it have lifecycle? what hooks does it expose?). The decomposition has a problem: the runner typically wants *all* of these at once. Today the runner calls four methods, each with a different return type, each of which can be `None` or `[]`. That's four places where the "this language doesn't do that" signal lives. It also makes introspection hard — `crackerjack adapters list` (a likely Phase-5 CLI subcommand) needs to call four methods per adapter to print a capability summary. A single `capabilities() -> Capabilities` method that returns a typed `Capabilities` dataclass collapses all the optionals into one place, makes introspection trivial, and gives the runner one source of truth.
- **Failure scenario**: `crackerjack adapters list` runs against a mixed registry (Python, Swift, Web, plus a third-party Rust adapter). The CLI author has to call `detect()` for *every* project (which is what the spec implies) and then call `version_source()` and `hooks()` and `lifecycle()` to build the capability table. That's three method calls per adapter per project — and `detect()` requires a `project_root` argument, so the CLI has to either pick a project or call `detect()` against a synthetic "no project" root, which may produce incorrect answers for some adapters. A `capabilities() -> Capabilities` dataclass with `version_source: bool`, `lifecycle: bool`, `hook_count: int` lets the CLI render the table in one call per adapter with no `project_root` needed.
- **Category**: ergonomics, public API.
- **Recommendation**: Replace the four methods with a single `capabilities() -> Capabilities` plus a `detect()`:
  ```python
  @dataclass(frozen=True)
  class Capabilities:
      has_lifecycle: bool
      version_source: VersionSourceFactory  # Callable[[Path], VersionSource] | None
      hooks: tuple[Hook, ...]              # empty tuple if no hooks

  class LanguageAdapter(Protocol):
      name: str
      def detect(self, project_root: Path) -> bool: ...
      def capabilities(self, project_root: Path) -> Capabilities: ...
  ```
  The `Capabilities` dataclass has explicit `has_lifecycle: bool` (replaces the `None` return on `version_source()` and `lifecycle()`) and a tuple of `Hook` (replaces the `[]` return). The runner never sees `None` from these calls; it just reads the dataclass. This also fixes F4 and F5 in the same pass.

### F4 — MEDIUM — `version_source() -> VersionSource | None` conflates "no lifecycle" with "method returned None"; same for `lifecycle()`

- **Line**: 130, 136.
- **Summary**: Both methods return `X | None` to signal "this language doesn't have a lifecycle". This is two separate concerns conflated into one return value: (a) the answer to "does this language have lifecycle?" and (b) the construction of the lifecycle object. The Optional return forces the runner to do `if adapter.lifecycle(project_root) is not None:` — which is fine for a one-off, but every consumer of the API has to write that check, and an adapter that returns a `Lifecycle()` object that *happens* to have no actions would silently behave the same as "no lifecycle". The bool flag is explicit and self-documenting.
- **Failure scenario**: A future `RustAdapter` author writes `def lifecycle(self, project_root): return Lifecycle(steps=[])` (because they intend to add steps later). The runner sees a non-None `Lifecycle` object, attempts to orchestrate it, finds no steps, logs "Rust lifecycle ran 0 steps", and the user is left wondering why `crackerjack run -p minor` did nothing for their Rust project. An explicit `has_lifecycle: bool` field on a `Capabilities` dataclass would make the contract declarative: "I have lifecycle support" vs "I don't".
- **Category**: correctness, public API.
- **Recommendation**: See F3 — fold `version_source()` and `lifecycle()` into a `Capabilities` dataclass with `has_lifecycle: bool` as the explicit signal. The `VersionSource`/`Lifecycle` factories remain (still callable with `project_root`) but they're not "Optional" anymore; the bool is the gate. If the dataclass approach is rejected, at minimum split into `has_lifecycle() -> bool` + `lifecycle() -> Lifecycle` so the contract is unambiguous.

### F5 — MEDIUM — `hooks() -> list[Hook]` returning `[]` is the wrong "no hooks" signal; empty list vs missing capability indistinguishable

- **Line**: 133.
- **Summary**: An adapter that has no hooks (e.g., a future `MarkdownAdapter` that's documentation-only) returns `[]`. An adapter that has hooks but the registry failed to load them also returns `[]` (defensive `try/except` around hook construction). The runner can't tell the two apart. A `tuple[Hook, ...]` (which is what F3 proposes) makes the contract `len(hooks) == 0` for "no hooks" but the type system can't enforce that. The dataclass field `hooks: tuple[Hook, ...] = ()` plus a docstring "If empty, the adapter has no hooks for this language" is the cleanest contract.
- **Failure scenario**: A `WebAdapter` ships with a try/except that catches all exceptions during hook construction (e.g., a missing `jinja2` import). It returns `[]` and the runner proceeds, but the Web adapter silently does no work. A `Tuple[Hook, ...]` (immutable) plus a runtime check `assert all(isinstance(h, Hook) for h in hooks)` in the registry catches the defensive try/except at registration time.
- **Category**: correctness, observability.
- **Recommendation**: Type `hooks` as `tuple[Hook, ...]` (not `list`). The runtime check in the registry should be `if not isinstance(hooks, tuple): raise AdapterContractError(...)`. The dataclass default is `()` so adapters that don't override it get "no hooks" for free. Also, the registry should *not* catch exceptions during adapter construction; let them propagate so registration failures are loud, not silent.

### F6 — MEDIUM — `Hook` dataclass: 6 fields with no defaults; minimum required set is unclear

- **Line**: 142–150.
- **Summary**: `Hook` has 6 fields: `name`, `cli_command`, `fallback`, `timeout_seconds`, `autofix`. The spec doesn't say which are required. Crackerjack's pyproject bans `Any` and the Python review lens flagged the loose `Callable | None` type. From a public-API perspective, the field-set itself is the contract: third-party authors must fill in every field on every hook, even when most are `None` or a default would do. A `dataclass(frozen=True)` with sensible defaults (`timeout_seconds: int = 600`, `autofix: bool = False`, `fallback: HookFallback | None = None`) lets the minimum hook be `Hook(name="cargo.test", cli_command=("cargo", "test"))` — which is a much better DX. The Python review lens (F1, F2, F6) already covers the loose typing and missing `cwd`/`env`/`parallel_safe`; this finding is the public-API angle on the same surface.
- **Failure scenario**: A `crackerjack-rust-adapter` author writes 20 Rust hooks (cargo test, cargo build, cargo clippy, cargo fmt, ...). With no defaults, they have to write `Hook(name="...", cli_command=(...), fallback=None, timeout_seconds=600, autofix=False)` 20 times. The tedium invites copy-paste errors. With defaults, they write `Hook(name="cargo.test", cli_command=("cargo", "test"))` for the common case and only override fields when needed.
- **Category**: developer experience, public API.
- **Recommendation**: Make every field except `name` and `cli_command` have a default. Required minimum is `name` + `cli_command`; everything else is opt-in. Combined with the Python review lens's F1 (missing-CLI-behavior discriminator) and F6 (cwd/env/parallel_safe), the final shape is:
  ```python
  @dataclass(frozen=True)
  class Hook:
      name: str
      cli_command: tuple[str, ...]
      fallback: HookFallback | None = None
      timeout_seconds: int = 600
      autofix: bool = False
      cwd: Path | None = None
      env: Mapping[str, str] | None = None
      parallel_safe: bool = True
      missing_cli_behavior: Literal["fail", "skip_warning", "fallback"] = "fail"
  ```
  Required fields: `name`, `cli_command`. All others default.

### F7 — MEDIUM — `detect()` name is fine; `version_source()` and `lifecycle()` names are confusing because they read as nouns but are factory methods

- **Line**: 127–138.
- **Summary**: `detect()` reads naturally as a verb (good). `version_source()` and `lifecycle()` read as nouns (a *thing*, not an *action*). The runner has to remember that these are factory methods that return objects — they don't *read* the version or *run* the lifecycle, they *construct* a `VersionSource` or `Lifecycle`. A reader scanning the Protocol sees `version_source()` and thinks "where's the version string?" (it's inside the returned `VersionSource`, which is an indirection the API forces).
- **Failure scenario**: A new crackerjack contributor reads `adapter.version_source(project_root)` and writes `current = adapter.version_source(project_root)` expecting a `str`. At runtime they get a `VersionSource` instance, type-check fails, they're confused. The names invite the same misread every time a new contributor arrives.
- **Category**: API clarity.
- **Recommendation**: Rename to factory-verb forms: `version_source()` → `make_version_source()` (or `create_version_source()`); `lifecycle()` → `make_lifecycle()`. The factory form is the standard Python idiom (`collections.namedtuple(...)`, `dataclasses.make_dataclass(...)`, `pathlib.Path(...)` are all factory-named). Alternatively, if the F3 `Capabilities` dataclass refactor is adopted, both methods disappear into the dataclass and the naming concern evaporates. Either is fine; what's important is that the current noun-named factories are renamed or removed before this becomes a public API.

### F8 — MEDIUM — `VersionSource.read()` / `write()` error contract is unspecified; Python `FileNotFoundError` is the wrong layer for a version-write failure

- **Line**: 152–157, 280–281.
- **Summary**: The spec says "fail the gate (data integrity)" on a `write()`-read-back mismatch but doesn't name the exception class. Crackerjack's CLAUDE.md and `crackerjack-compliant-code` skill mandate a custom exception hierarchy in `crackerjack/core/errors.py`. The spec should mirror that pattern: `VersionSourceError` (base), `VersionReadError` (parse failure, file not found), `VersionWriteError` (write failed, read-back mismatch), all with structured context (current version, attempted version, file path, line number for parse errors).
- **Failure scenario**: A `VersionSource.write("0.2.0")` does the regex replacement, then `read()` returns "0.2.0" — but the file has *two* `version:` matches (one in a comment, one in the manifest), and the spec's "fail if mismatch" check passes because both got rewritten. The runner logs `FileNotFoundError` (no, `FileNotFoundError` doesn't apply here) — actually, the runner catches a bare `Exception` and logs "version bump failed" with no context. The user can't tell whether the regex matched the wrong line, whether permissions failed, or whether the file was on a read-only filesystem.
- **Category**: correctness, error handling.
- **Recommendation**: Spec the exception hierarchy explicitly:
  ```python
  class VersionSourceError(Exception): ...           # base, with .context: dict
  class VersionReadError(VersionSourceError): ...   # .path, .reason
  class VersionWriteError(VersionSourceError): ...  # .path, .expected, .actual
  class VersionParseError(VersionSourceError): ...  # .path, .line, .column
  ```
  Reference: `mahavishnu/core/errors.py` already follows this pattern. Crackerjack should mirror it. The `read()` / `write()` Protocol signatures stay the same; only the exception contract is added.

### F9 — MEDIUM — Lifecycle shape: `bump(level)` + `commit` + `tag` + `push` + `release` as separate methods is too granular; one `run(level)` is more cohesive

- **Line**: 136–138, 175–179.
- **Summary**: The spec defines `Lifecycle` as having separate methods `bump(level)`, `commit`, `tag`, `push`, `release`. The runner orchestrates them as a sequence. This decomposition has two problems: (a) every adapter reimplements the same orchestration logic (the spec says "same as Python lifecycle (reuse core git helpers)"), and (b) the order is fixed by the runner, but adapters may want to customize it (e.g., "tag *before* push" vs "push *before* tag"). A single `Lifecycle.run(level, *, tag: bool = True, push: bool = True, release: bool = True)` method takes a config object and runs the full sequence, with the per-step orchestration centralized in a base class.
- **Failure scenario**: Phase 2 ships Swift with `bump → commit → tag → push → release`. Phase 3 ships Kotlin with the same. Phase 4 wants to add `--no-push` (a real flag in `crackerjack run -p minor --dry-run`). The runner has to thread a config through all five method calls. A new "Web lifecycle" wants to do `bump → tag → release` but no push (web assets don't have a git-tag meaning). The five-method decomposition forces the runner to special-case per adapter.
- **Category**: API design.
- **Recommendation**: Collapse to one `run(level, options: LifecycleOptions)` method. The `LifecycleOptions` dataclass carries `commit: bool = True`, `tag: bool = True`, `push: bool = True`, `release: bool = True`, `dry_run: bool = False`. The base class implementation does the standard sequence; adapters that need to customize override the relevant helper methods (`_commit()`, `_tag()`, `_push()`, `_release()`). This is the same pattern as `setuptools`' `Distribution.run_commands()`.

### F10 — LOW — `Protocol` snippet omits `self` on `read()` and `write()`; copy-paste foot-gun (re-raised as public-API concern)

- **Line**: 152–157.
- **Summary**: The Python review lens (F5) flagged this. As a public-API concern: a third-party author who copies the spec's `def read() -> str: ...` into their adapter will write a method missing `self`, hit `TypeError: read() takes 1 positional argument but 2 were given` at runtime, and file a bug against crackerjack. Spec snippets in a public API are code templates; they must be drop-in correct.
- **Category**: public API, documentation.
- **Recommendation**: Show `def read(self) -> str: ...` and `def write(self, new_version: str) -> None: ...` in the spec. Pair this with a "minimum viable adapter" code block in the spec's authoring section that third parties can copy verbatim.

### F11 — LOW — Naming inconsistency: `version_source` (snake_case function) vs `VersionSource` (PascalCase class)

- **Line**: 130 vs 152.
- **Summary**: The method `version_source()` returns a class `VersionSource`. Snake-case method and PascalCase return type, both naming the same concept, is jarring. A reader sees `def version_source(...) -> VersionSource: ...` and reads "function `version_source` returns class `VersionSource`" — the duplication is noisy. Renaming either side (per F7, `version_source()` becomes `make_version_source()`) resolves this. Or rename the class to `VersionSourceReader` and the method becomes self-explanatory.
- **Category**: naming.
- **Recommendation**: Pick one canonical form. If F3 is adopted, the class becomes a `Capabilities` field and the duplication disappears. If not, rename the method (F7) so the class and method don't share a name with different conventions.

### F12 — LOW — Entry-point discovery contract (loading cadence, conflict policy, caching) unspecified

- **Line**: 105–113.
- **Summary**: The Python review lens (F13) flagged this. From a public-API angle: third-party authors will want to know (a) when their entry point is loaded (per CLI invocation? per process? per session?), (b) what happens if two packages register the same name, (c) whether the registry can be inspected (`crackerjack adapters list`). None of this is in the spec.
- **Category**: public API, observability.
- **Recommendation**: Spec the registry contract:
  - Entry points loaded once per `crackerjack` CLI invocation (not cached across invocations).
  - Name conflicts raise `DuplicateAdapterError`; bundled adapters have priority over third-party only if explicitly opted-in via a `priority` field on the entry point (or some similar mechanism).
  - Public API: `crackerjack.adapters.registry.get_all_adapters() -> tuple[LanguageAdapter, ...]` for tools that need to introspect.
  - `crackerjack adapters list` is added to the CLI surface (or called out as a Phase-5 follow-up).

### F13 — LOW — No minimum viable adapter example; spec lacks a "hello world" authoring section

- **Line**: 105–117 (third-party section).
- **Summary**: The spec's third-party section says "register themselves by adding the same entry point" but doesn't show a complete, runnable, 20-line example. A public API spec without a "hello world" forces every author to reverse-engineer the Protocol from snippets scattered across the document. The spec should include a "Writing a third-party adapter" subsection with a complete, copy-pasteable Rust adapter stub that a maintainer can fork and run.
- **Category**: developer experience, public API.
- **Recommendation**: Add a subsection under "Architecture — Approach A" titled "Writing a third-party adapter" with:
  - A 20-line stub for `crackerjack-rust-adapter` showing all the moving parts: `pyproject.toml` entry point, `RustAdapter` class, `CargoTomlVersionSource`, two `Hook` instances, optional `Lifecycle`.
  - A one-paragraph "what to test" list.
  - A link to a reference implementation (the bundled Python adapter is the canonical example).

### F14 — LOW — `tuple[str, ...]` for `cli_command` is correct but undocumented why `list[str]` was rejected

- **Line**: 145.
- **Summary**: `cli_command: tuple[str, ...]` is the right call (immutable; hashable; `frozen=True` dataclass compatible). But the spec doesn't say *why*. A future maintainer might "improve" it to `list[str]` (mutable, easier to append), which would break the dataclass's `frozen=True` invariant and silently change subprocess argv semantics if someone mutates the list between registration and execution. A one-line docstring on the field would head this off.
- **Category**: API documentation.
- **Recommendation**: Add `# tuple is required (not list) so the frozen dataclass is hashable and so adapter authors cannot mutate the argv after registration` to the field definition. Cross-reference the Python review lens F14 (hook ordering) — the same tuple-immutability argument applies to `PYTHON_HOOKS` as a module-level constant.

### F15 — LOW — `autofix: bool` field on `Hook` is too coarse; a `fix_mode: Literal["none", "format", "lint"]` enum is more expressive

- **Line**: 148.
- **Summary**: A boolean `autofix` field conflates three different fix modes: (a) pure formatting (always safe, like `swift format`), (b) lint autofix (usually safe but sometimes aggressive, like `eslint --fix`), (c) dependency upgrades (risky, like `swift package update`). A boolean is a code smell when it represents a tri-state. An enum or a `Literal` type lets the runner pick the right gate.
- **Failure scenario**: The spec lists `swift.format` as `autofix=true` and other Swift hooks as `autofix=false`. But `swift package update` (deferred) is a fix mode *and* a dependency change, not a pure format. When it's added (per the Python review lens and the Swift review lens F3), the boolean breaks. A `Literal["none", "format", "lint", "deps"]` lets the runner emit different warnings and gate the autofix on a per-mode CLI flag (`--autofix-format`, `--autofix-lint`, `--autofix-deps`).
- **Category**: extensibility.
- **Recommendation**: Replace `autofix: bool` with `fix_mode: Literal["none", "format", "lint", "deps"] = "none"`. The runner can default to "only run format autofix without explicit flag" and require the others to be opt-in. This is a Phase-2-evaluable change; not blocking, but the boolean should be replaced before any third-party adapter is published.

## Coverage Statement

This review covered, from the public API design lens:

1. **`LanguageAdapter` Protocol shape and decomposition** (F3 — four methods vs `capabilities()` dataclass; F4 — Optional returns as "no capability" signal; F5 — `[]` vs missing capability; F7 — verb vs noun naming; F11 — class/method name collision).
2. **Authoring ergonomics for third-party packages** (F1 — runtime checkability; F2 — base class vs Protocol vs decorator; F13 — minimum viable adapter example; F10 — `self` in snippet).
3. **`Hook` and `VersionSource` dataclass design** (F5 — empty list vs missing; F6 — defaults; F8 — exception contract; F14 — tuple vs list rationale; F15 — `autofix` boolean vs enum).
4. **`Lifecycle` decomposition** (F9 — five separate methods vs one `run(level, options)`).
5. **Entry-point discovery and registry contract** (F12 — load cadence, conflict policy, introspection).
6. **Error contract for `VersionSource.read()` / `write()`** (F8).
7. **Naming consistency** (F7, F11).

Items **explicitly out of scope** for this lens (covered by other lenses):

- Subprocess glob expansion, Windows portability (Python review lens F12).
- Async vs sync adapter Protocol (Python review lens F3).
- Hook subprocess CWD/env/parallel-safe fields (Python review lens F6).
- Missing-CLI-behavior discriminator (Python review lens F1) — partially covered as F15 but the detailed contract is Python-lens territory.
- `from __future__ import annotations` + Pydantic forward-ref interaction (Python review lens F7).
- Specific language adapter correctness (Swift lens F1–F5, Kotlin lens, Web lens, Python lens).
- MCP tool registration surface (MCP lens).
- CLI subcommand ergonomics (CLI/DX lens).
- Test fixture strategy for cross-language parity (testing-strategies lens).
