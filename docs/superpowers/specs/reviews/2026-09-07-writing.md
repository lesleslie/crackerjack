## Findings (most-severe first)

### F1 — HIGH — Phase 1 "REFACTOR existing Python logic into this shape" is unsourced; new contributors cannot find the targets

**Spec claim (lines 78-82, 318-319):**

> `python/ # REFACTOR existing logic into this shape`
> ...
> - Add `adapters/base.py`, `adapters/registry.py`, `core/language_detector.py`
> - Refactor existing Python logic into `adapters/python/` (preserves all behavior)

**Why this is a writing defect, not just a code smell:**

The spec names three new files but never points at the **existing** Python logic that has to move. A new contributor cannot answer:

- Which module today owns `bump_version` / `tag_and_push` / `twine publish`?
- Is the current code in `crackerjack/cli/`, `crackerjack/core/`, `crackerjack/managers/`, or scattered across hooks?
- Are there call sites outside crackerjack that import the current paths and would need deprecation shims?

The "no behavior change" guarantee (line 312, Risk 1) is the central Phase 1 promise, and the spec provides no inventory of what must not change. The Swift reviewer was able to flag `Package.swift` semantics precisely because that adapter has clean starting state; the Python adapter starts from a moving target the spec does not name.

**Recommended fix:**

Add an "Existing Python pipeline inventory" subsection listing the current modules/functions that must move (e.g., "Move `bump_version` from `crackerjack/managers/version.py`, `publish_to_pypi` from `crackerjack/lifecycle/publish.py`, hook orchestration from `crackerjack/hooks/`"). One bulleted list, 5-10 lines, ends the ambiguity.

### F2 — HIGH — "Hybrid implementation strategy" (Goal, line 17) and "falls back to a Python implementation if the CLI is missing or fails" (line 209) are ambiguous about the trigger

**Spec text (Goal):**

> Hybrid implementation strategy: external CLI primary, Python fallback

**Spec text (web hooks, line 209):**

> each hook first checks for the CLI tool, falls back to a Python implementation if the CLI is missing or fails.

**Why two readings, both defensible:**

1. Fallback only on **binary missing** (`which stylelint` returns non-zero).
2. Fallback on **any non-zero exit** — but then `stylelint` finding real CSS errors would silently trigger the Python fallback and report "no issues" because the Python formatter doesn't lint.
3. Fallback on **specific failure patterns** — but those patterns aren't enumerated per hook.

A reader implementing this has three plausible interpretations. The "Error handling" table (lines 277-285) says CLI missing = skip with warning, Python fallback missing = fail gate — but does not say which mode the hybrid uses. The user-visible behavior (does `stylelint` skip on errors? reformat via Python?) cannot be derived from the spec.

**Recommended fix:**

Replace "or fails" with an exact contract. Suggested canonical interpretation: "Fallback triggers only when the CLI binary is absent (`shutil.which` returns None) or returns exit code 127 (command not found). Any other non-zero exit fails the gate per the existing hook contract; Python fallback is never reached." Add this sentence verbatim to the Goal or to a new "Fallback trigger contract" subsection.

### F3 — HIGH — Web adapter detection rule (line 200) will false-positive on essentially every Python project

**Spec text (line 200):**

> **Detect**: presence of any `.css`, `.scss`, `.html`, `.ts`, `.tsx`, `.js`, `.jsx`, `.jinja`, `.html.j2`, `.tmpl` files at project root or in `src/templates/`, `templates/`, `assets/`, `static/`. (Detection is shallow — checking for file extensions, not full inventory.)

**Why this is wrong on contact:**

- A pure-Python Django project has `static/admin/css/base.css` and templates under `templates/admin/`. Per the rule, the web adapter activates for Django's built-in admin assets — almost certainly not what the project owner wants linted.
- A pure-Python documentation project (Sphinx, MkDocs) has `*.html` and `*.css` shipped with the theme.
- A pure-Python CLI tool with a `docs/` or `assets/` directory trips the rule.

The "Detection is shallow" disclaimer is the **opposite** of a fix — it's a confession. Detection should be **deep enough** to be useful.

**Recommended fix:**

Add a more discriminating rule. Suggested canonical interpretation: "Web adapter activates when (a) any of the listed files exists in `assets/` / `static/` / `src/` **AND** (b) the project declares CSS/JS toolchain config: `package.json` with `stylelint`/`html-validate` deps, `.stylelintrc*`, `.eslintrc*`, `tsconfig.json`, or a `[tool.crackerjack.jinja]` block. Otherwise detection returns False even if scattered web files are present."

### F5 — MEDIUM — `[tool.crackerjack.jinja]` config schema is referenced twice but never specified

**Spec references:**

- Line 212: "Loads the project's Jinja delimiter config from `pyproject.toml` `[tool.crackerjack.jinja]` block."
- Line 354: "`[tool.crackerjack.disabled_hooks] = ["web.js.eslint"]` for projects using Biome instead"

**Why this is a writing gap:**

The first reference says "delimiter config" but never shows what fields, defaults, or types it accepts. The second reference shows a different config block (`disabled_hooks`) with example syntax. The reader can't tell:

- Is the block `[tool.crackerjack.jinja]` or `[tool.crackerjack]` with a `jinja` subkey?
- Are delimiters a tuple of three strings? A dict with `block_start_string` etc.? An ini-style section?
- What's the precedence vs. autodetection?
- Does the disabled_hooks example show syntax that the Jinja block also follows, or is it independent?

**Recommended fix:**

Add a "Configuration schema" subsection that gives one concrete example for each block:

```toml
[tool.crackerjack.jinja]
block_start_string = "[%"
variable_start_string = "[["
comment_start_string = "[#"

[tool.crackerjack.disabled_hooks]
"web.js.eslint" = "project uses Biome instead"
```

8-12 lines ends the ambiguity.

### F6 — MEDIUM — "CLI + MCP mirror for every new feature" (line 56) is asserted but not enforced in the per-adapter sections

**Spec text (Scope → Cross-cutting, line 56):**

> CLI + MCP mirror for every new feature

**Spec text (per-adapter sections):**

The Swift section names MCP tools (`run_swift_hooks`, `bump_swift_version`, `detect_languages`) but only mentions the CLI in passing ("The CLI surface is `crackerjack run -p {major|minor|patch}` for all languages"). The Kotlin section lists MCP tools and says lifecycle is the same shape — no CLI tool named. The Web section lists MCP tools (`check_web_lint`, `format_jinja_templates`) and the data flow mentions `crackerjack web jinja format src/templates/` — but `check_web_lint` has no CLI counterpart in the spec.

**Why this matters:**

The "CLI + MCP mirror" rule is the kind of promise readers rely on to design their workflows. If it's not enforced in each adapter's section, future contributors will ship MCP-only features without noticing they've violated scope.

**Recommended fix:**

Add a per-adapter "CLI surface" line mirroring the "MCP tools" line, e.g.:

**Swift adapter:**
- CLI: `crackerjack swift hooks`, `crackerjack swift bump [-p major|minor|patch]`
- MCP: `run_swift_hooks`, `bump_swift_version`, `detect_languages`

Same shape for Kotlin and Web. 12 lines total; restores consistency with the stated scope rule.

### F7 — MEDIUM — "Open questions / future work" and "Out of scope (deferred)" overlap

**Spec text:**

- Lines 60-66 (Out of scope): "Kotlin/JetBrains Marketplace automated publishing (manual or future plan)" / "Watch mode"
- Lines 351-358 (Open questions): "JetBrains Marketplace publishing for Kotlin plugins (deferred; current `gh release` is the GitHub side)" / "Watch mode: real-time hook running on file change — defer to v0.83"

**Why this is structurally weak:**

Two sections list the same items in different prose. A reader can't tell whether "deferred to v0.82" in Open questions means "planned for the next minor" or "maybe someday." Three problems:

1. **JetBrains Marketplace publishing** appears in both — the second time it doesn't add information, it just dilutes.
2. **Per-project hook config** is in Out of scope as "deferred" but in Open questions with a concrete `[tool.crackerjack.disabled_hooks]` example, which is more concrete than "deferred." Contradicts tone.
3. **Future Work** is a heading without content — the section is "Open questions / future work" but contains only open questions.

**Recommended fix:**

Consolidate into one "Deferred work" section that lists each item exactly once, with three columns: **Item**, **Target version (or "unscheduled")**, **Reason for deferral**. Delete the duplication. The Risks section can stay as is — it captures *known unknowns during implementation*, distinct from *intentional deferrals*.

### F8 — MEDIUM — Spec-vs-plan bleed: Migration plan section is prescriptive step-by-step; spec-vs-plan boundary is crossed

**Spec section "Migration plan" (lines 314-349):**

> Phase 1 — Add `adapters/base.py`, `adapters/registry.py`, `core/language_detector.py`. Refactor existing Python logic into `adapters/python/`. Verify: full crackerjack test suite passes.

> Phase 2 — Implement Swift adapter. Add entry-point registration in `pyproject.toml`. Add MCP tools: `run_swift_hooks`, `bump_swift_version`, `detect_languages`. Test on `swiftui-ipc-client` and `mdinject` Swift app. Tag and document.

**Why this is a spec-vs-plan problem:**

Per the brainstorming-skill rule the prompt cites: specs describe WHAT/WHY; plans describe HOW (step by step). "Add `adapters/base.py`, add `adapters/registry.py`, add `core/language_detector.py`, refactor, verify" is a 4-step implementation plan. So is Phase 2 ("Implement, Add, Add MCP tools, Test, Tag").

Worse: the same spec was clearly written by a process that included 6 Q&A rounds producing this design — the commit message references that history. A reader who wasn't in those rounds has no signal for *why* Approach A was chosen, *what* the rejected alternatives were, or *what* tradeoffs the author already weighed.

**Recommended fix:**

Two complementary changes:

1. Trim the Migration plan section to "Outcome per phase" bullets (e.g., "Phase 1 outcome: Python-only projects see no behavior change; `LanguageAdapter` protocol is published but unused"). Move the step-by-step into a follow-up `plan/2026-09-07-crackerjack-multi-language-phase1.md` (or similar) referenced from the spec.

2. Add a "Design history" appendix (50-100 lines) summarizing the 6 Q&A rounds: which alternatives were considered (Approach B? C?), why each was rejected, what tradeoffs were resolved (e.g., "Q3: regex vs. AST for `Package.swift`? — chose AST, see Swift review F1"). This prevents implementation reviewers from re-relitigating closed decisions.

### F13 — LOW — `LanguageAdapter` Protocol mixes responsibilities; two methods return `None` for the same reason

**Spec text (lines 124-139):**

```python
def version_source(self, project_root: Path) -> VersionSource | None:
    """Where to read/write version. None if no lifecycle support."""

def lifecycle(self, project_root: Path) -> Lifecycle | None:
    """Lifecycle steps (bump, tag, push, release). None if no lifecycle."""
```

**Why this is awkward:**

Both methods return `None` "if no lifecycle support." If `version_source` returns None, `lifecycle` must also (or what would it operate on?). The two-None case adds an implementation check at every call site without documenting why both exist as separate methods.

**Recommended fix:**

Consolidate into a single method:

```python
def lifecycle(self, project_root: Path) -> Lifecycle | None:
    """Returns None if the adapter has no lifecycle support (e.g., Web)."""
```

`version_source` becomes a property of `Lifecycle`, not a separate top-level method. Reduces the surface area and eliminates the "which None wins?" question.

(Alternative: leave the split but document that `version_source is None` ⟺ `lifecycle is None`. A one-line note is enough.)
