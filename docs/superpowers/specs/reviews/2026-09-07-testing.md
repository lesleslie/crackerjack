# Testing Lens Review

## Findings (most-severe first)

### F1: Fixture projects are unrealistic for the budget implied
- **Line**: 298-299 (testing strategy, integration tests)
- **Summary**: Spec claims fixture projects "exercise the full `crackerjack run` end-to-end" in CI but does not budget for the cost of standing up Swift, Gradle, and Node toolchains per job.
- **Failure scenario**: `tests/fixtures/swift-lib/` requires Xcode CLT (`xcode-select -p` succeeds) plus a working `swift build` against a real `Package.swift`. The first CI job on a fresh Linux runner fails outright (no Swift); on macOS it succeeds but `swift build` + `swift test` on a trivial lib still costs 30-90s. `gradle-plugin/` requires Gradle wrapper download (~80-120MB cached, ~25-45s cold) and `./gradlew test` is notoriously slow even for an empty project (Daemon startup, configuration phase, test task wiring). `web-app/` requires `npm install` of stylelint/eslint/tsc/html-validate (~150MB-300MB and 30-90s cold). Summed: 2-4 minutes of cold toolchain setup per fixture, every CI run. There is no mention of caching (`~/.gradle`, `~/Library/Developer/Xcode/DerivedData`, `~/.npm`, `node_modules/`), no `pytest -m "not slow"` carve-out for integration tests, and no parallel matrix strategy. Phase 5 says "Test on fastblocks, splashstand" — these are real projects with real dep trees, not fixtures.
- **Category**: completeness
- **Recommendation**: Explicitly mark fixture e2e tests with `@pytest.mark.slow` and `@pytest.mark.integration`, keep them out of the default fast-feedback gate (`-m "not slow"`). Pin toolchain versions in `tests/fixtures/<name>/.tool-versions` (or equivalent) so CI can pre-cache. Add a fixture-cost table to the spec: name, cold setup sec, warm sec, fixture size MB, expected wall-clock per CI job. If the budget exceeds ~3 min per language, drop the e2e fixture and rely on unit tests + one smoke run on the real Bodai repo.

### F2: MCP integration tests cite `mcp-common` testing helpers that may not exist
- **Line**: 300
- **Summary**: "tests call them via in-process MCP client (`mcp-common` testing helpers)" — this is asserted without a code reference and reads like the author assumes the helper exists rather than verifying it.
- **Failure scenario**: Phase 2 ships `run_swift_hooks`, `bump_swift_version`, `detect_languages`. The integration test tries to import `mcp_common.testing.InProcessMCPClient` or similar and the import fails because mcp-common exposes `ClientSession` / `stdio_client` (FastMCP primitives) but no turnkey in-process harness. Team either writes the harness inline (now scope creep on Phase 2), blocks Phase 2, or skips MCP integration tests entirely and ships the tools with only CLI-level verification.
- **Category**: risk
- **Recommendation**: Before merging the spec, point at the exact symbol (file path + function name) that provides the in-process client. If it doesn't exist, replace this line with "MCP tools are tested via subprocess `mahavishnu mcp start` + raw JSON-RPC over stdio (per the existing crackerjack MCP smoke-test pattern)" or carve out an explicit Phase-1.5 task to add the helper to mcp-common. Do not let Phase 2 plan depend on a helper that is unverified.

### F3: Hybrid pattern has no two-path test plan
- **Line**: 209 (and 279-281 error handling)
- **Summary**: "each hook first checks for the CLI tool, falls back to Python" — to cover both paths the test matrix needs `(cli present, cli absent) × (fallback succeeds, fallback fails)` = 4 combinations per hook, but the spec says nothing about how to flip `cli present`.
- **Failure scenario**: The web adapter's `web.css.stylelint` falls back to a Python implementation when `npx stylelint` is missing. CI typically has `npx` available (Node is installed), so the fallback path is never exercised. The fallback ships with a bug (e.g., it doesn't strip the BOM before counting lint hits). CI passes for months. A Bodai developer with Node disabled hits it on their laptop and gets wrong output. Same problem in reverse: a CI matrix that DOES disable Node only tests the fallback and never sees the CLI happy path.
- **Category**: completeness
- **Recommendation**: Define the test matrix explicitly. Two viable approaches: (a) `monkeypatch` / `unittest.mock.patch` on `shutil.which("stylelint")` to make detection return `None` for the fallback tests and a real path for the CLI tests — this is the cheap option and works in one CI env. (b) A pytest marker (`@pytest.mark.requires("stylelint")`) that skips if the tool is absent — but that means fallback tests need a separate marker (`@pytest.mark.requires_no("stylelint")`) and a CI matrix job that runs without Node. Option (a) is strictly better; spec should mandate `monkeypatch.setattr(shutil, "which", lambda name: None if name=="stylelint" else real)` style helpers per hook.

### F4: Jinja canonical-policy parity is not testable in CI and the spec accepts that
- **Line**: 302-307 (Cross-package parity tests)
- **Summary**: Spec acknowledges "we can't invoke PyCharm from headless CI, parity is verified manually + via a documentation note". For a release-quality formatter that ships canonical whitespace rules shared with another project, manual verification is below the bar — and "documentation note" is not a test, it is a confession.
- **Failure scenario**: Crackerjack ships v0.81 with the canonical policy. PyCharm-side maintainer upgrades `jinja2-custom-delimiters` to use a slightly different inline-expression rule (e.g., `{{ x }}` vs `{{x}}` inside HTML attribute context). The two implementations diverge. There is no CI signal. The Bodai ecosystem silently produces different-looking output depending on which side ran last. The next round of parity debugging costs hours of bisection.
- **Category**: correctness
- **Recommendation**: Two layered fixes. (1) For the Python side, add a `@pytest.mark.parametrize` over the 30-corpus files that asserts output against a frozen expected-output directory (`tests/fixtures/jinja-corpus/expected/`). Pin the expected outputs as test fixtures (reviewable diffs when policy changes). (2) For the PyCharm side, since the plugin is Kotlin/IntelliJ, automate it via IntelliJ's CLI test framework (or a Gradle task that spins up the IntelliJ Community Edition test fixture and runs the formatter). The spec's "Future: headless IntelliJ CLI test framework" sentence should be promoted to a Phase 4 deliverable, not deferred. A "documentation note" without a CI signal should not be a parity test.

### F5: Mock subprocess surface for 20 hook wrappers is under-specified
- **Line**: 291 (Unit tests)
- **Summary**: "Per-adapter unit tests with mocked subprocess (use `unittest.mock`)" glosses over the combinatorial surface — 5 hooks × 4 languages × {success, exit-nonzero, timeout, cli-missing, fallback-missing, malformed-stderr} = significant mock fixture maintenance.
- **Failure scenario**: Each language adapter's `hooks.py` ends up needing a per-hook mock fixture (`mock_swift_test_success`, `mock_swift_test_timeout`, `mock_swift_test_missing_cli`, ...). Five hooks per language, four languages = 20 fixtures. Each fixture has subtle differences (env vars, cwd, signal handling, output capture). When a 21st language lands, the developer copies-pastes the pattern and one of the copies is wrong (e.g., doesn't simulate the `KeyboardInterrupt` cleanup path on timeout). The bug ships because the test passed for the original language but the pattern was subtly wrong.
- **Category**: maintainability / risk
- **Recommendation**: Specify a `FakeHookRunner` abstraction that all adapters use. The runner takes a `Hook` and a `subprocess.CompletedProcess` shape and returns the same dataclass the real runner returns. Each adapter test parametrizes over `(hook_name, scenario)` and the runner abstraction makes scenarios reusable across languages. Concretely: define `class HookResult: stdout, stderr, returncode, duration, fallback_used`. Then 6 scenarios × 5 hooks = 30 parametrized cases per language, but the scenarios are shared. Also: include a "live CLI" tier (slow, marked `@pytest.mark.slow`) that actually runs `swift test` against `tests/fixtures/swift-lib/` so the mock surface doesn't drift from reality.

### F6: Version-source round-trip is unsafe for `build.gradle.kts` (Kotlin DSL)
- **Line**: 294 (Version source: round-trip tests) and 189 (Kotlin adapter VersionSource.write)
- **Summary**: Spec says "For projects without `gradle.properties` (single-module, version in `build.gradle.kts`), fall back to regex on the `version = "..."` line" — round-tripping a regex replacement over Kotlin DSL is lossy for any non-trivial version expression.
- **Failure scenario**: A Kotlin DSL `build.gradle.kts` contains `val version = "0.2.0" // published version`. The regex replaces `"0.2.0"` with `"0.3.0"` and writes back. Read returns `"0.3.0"`. Round-trip passes. Three months later, the same file contains `val version = providers.gradleProperty("version").getOrElse("0.2.0")` (idiomatic Gradle convention). Regex still finds and replaces the literal `"0.2.0"` but loses the surrounding `providers.gradleProperty(...)` template. The test fixture passes (simple case) but the real project breaks. Even worse: `version = "0.2.0"` inside a multi-line `extra["version"] = "..."` block survives a regex but loses formatting because Kotlin DSL preserves whitespace per the parser — and the spec's regex-with-read-back does not catch whitespace loss. The version-source layer is responsible for data integrity, not formatting; this needs an explicit guard.
- **Category**: correctness / risk
- **Recommendation**: Two changes. (1) Make `gradle.properties` the only supported version source for Kotlin. Detect `build.gradle.kts` without `gradle.properties` and fail loudly with "create gradle.properties or set version-source explicitly" rather than silent regex fall-through. The spec's "falls back to regex" sentence is dangerous and should be removed or restricted to legacy Groovy DSL only. (2) For the round-trip test, do not assert just `read(write(x)) == x`. Assert a structural hash: `read(write(x)) == x AND len(write(read(write(x)))) == len(write(x)) AND parse(write(x))["version"] == x` — i.e., write-once must equal write-of-read. This catches the regex-rewrite-with-subtle-format-loss class of bugs. Apply the same to Swift `Package.swift` regex path (line 167).

### F7: 11K+ tests Phase-1 gate has no budget or cache strategy
- **Line**: 320 ("Verify: full crackerjack test suite passes (currently 11K+ tests)")
- **Summary**: Phase 1 is "no behavior change, just internal reorg" but the success criterion is running the full 11K+ test suite. There is no timing budget, no parallel-execution strategy, no cache story, and no marker split.
- **Failure scenario**: Phase 1 refactor lands. Developer runs `pytest` locally on a laptop: 11K tests × ~2-5ms each in unit, but with integration tests hitting subprocess, network, and filesystem it's easily 15-30 minutes wall clock. CI on GitHub-hosted runners: similar. The Phase-1 PR sits in review for two weeks because every reviewer who tries to verify locally times out or skips the gate. Phase 2 (Swift) lands on top of unverified Phase 1. The whole multi-language rollout builds on an unrun refactor.
- **Category**: completeness
- **Recommendation**: Specify three numbers: (a) Phase-1 PR-check budget (target ≤5 min on cold cache, ≤2 min warm). (b) Pre-merge smoke subset: name the exact test markers (`pytest -m "unit and not slow"`) that must pass before review is accepted. (c) Full-suite nightly schedule. State these explicitly. Use pytest-xdist with `-n auto` for the full run; add `pytest --co` smoke (collect-only) as a CI-fast smoke that catches import errors without running tests. This is the same pattern that already saved the Bodai ecosystem per the `dhara-test-isolation-issue.md` memory ("time-box bisection then switch to pytest --forked") — apply it pre-emptively, not after a 30-min bisection.

### F8: Fastblocks fixture couples two slow dep graphs in one CI job
- **Line**: 259-265 (Data flow) and Phase 4 (test on fastblocks)
- **Summary**: A "fastblocks-like" fixture mixing Python + Web forces CI to install both `pyproject.toml` deps (Python ecosystem: jinja2, fastblocks, etc.) AND `package.json` deps (stylelint, eslint, tsc, html-validate, and their plugin chains). Each ecosystem is ~30-90s cold; together ~2-4 min.
- **Failure scenario**: Phase 4 fixture is built. First CI run downloads 400MB of npm + uv packages. Test takes 6 minutes. Developer bisecting a flake reruns the same job 4 times in an hour — 24 minutes of CI spend on one fix. The flake goes unfixed because bisection is too expensive. Maintainer "fixes" by adding `pytest.skip` in CI when the fixture is slow, and the fixture becomes dead weight.
- **Category**: risk / maintainability
- **Recommendation**: Two small fixtures, not one. `tests/fixtures/web-only/` (a tiny static site with one CSS file, one HTML file, one JS file, one `.jinja` file, one `package.json` with the lint deps, NO Python source). This is web-adapter-only. The Python-adapter tests already have plenty of fixtures; cross-cutting tests live in a tiny `tests/fixtures/mixed/` with deliberately minimal deps (one `.py`, one `.css`, one `package.json` with only `stylelint`). The full "looks like fastblocks" test happens once on the real fastblocks repo in a weekly/manual smoke, not in CI per-PR. Spec should make this split explicit.

### F9: Round-trip idempotence test for Jinja is weaker than it looks
- **Line**: 216 (Round-trip invariant) and 292
- **Summary**: `format(parse(format(x))) == format(x)` proves the formatter is idempotent on its own output but does NOT prove the formatter produces a canonical result.
- **Failure scenario**: A bug introduces a rule-violating whitespace policy (e.g., collapsing blank lines between two `{% if %}` blocks when the canonical rule says "preserve"). The formatter outputs `format(x)` with two collapsed lines. `format(format(x))` returns the same collapsed version. Idempotence test passes. The fixture corpus is wrong because it was generated against the same broken formatter. No test ever catches the regression.
- **Category**: correctness
- **Recommendation**: Add a second invariant: for each fixture `f`, `format(f)` must equal a frozen expected-output `expected[f]` checked into the repo (`tests/fixtures/jinja-corpus/expected/<name>.jinja`). Reviewers diff the expected files when policy changes. This is the golden-master pattern and it's strictly stronger than idempotence alone. The spec's "Canonical policy: each of the 7 rules has 3+ positive cases and 3+ negative cases" (line 293) is closer to what's needed, but those 21 cases need to assert specific expected output, not just round-trip through them.
