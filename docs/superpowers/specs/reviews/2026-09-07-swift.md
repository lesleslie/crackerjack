# Swift Lens Review

## Findings (most-severe first)

### F1 — CRITICAL — `Package.swift` does not have a top-level `version:` field; regex-based rewrite is misdirected

**Spec claim (lines 165-167):**

> `read()`: parse `Package.swift`, extract the `version:` field from `.product(...)` if present (some SwiftPM libs don't carry a version field). Falls back to `git describe --tags --abbrev=0` if no in-file version.
> `write(new_version)`: regex replacement on the version field.

**Why this is wrong:**

SwiftPM does **not** support a `version:` field on `Package` itself, nor on `.product(...)` declarations. The `version:` token only appears inside **dependency** clauses (`.package(url: ..., from: "1.0.0")`, `.exact(...)`, `.branch(...)`) — those are *consumed* versions, not the package's *own* version. A regex on `version:` would happily rewrite a *dependency* range (e.g., `.package(url: "...", from: "1.0.0")`) when bumping the project, producing a silent corruption where every dependency jumps to the new "version."

The idiomatic SwiftPM versioning path is the **git tag**, which `Package.swift` resolution uses transitively. The spec gets this backwards: `git describe --tags --abbrev=0` should be the **primary** source, not the fallback. Regex rewriting `Package.swift` should not happen at all in v1.

**Edge cases the spec did not consider:**

- **Multi-package workspaces (Swift 5.9+):** a workspace has N `Package.swift` files (one per package); the spec has no concept of "which package are we versioning?" There is no cross-package manifest that aggregates versions.
- **`Package.swift` with `#if` directive around a dependency**: a regex match could land inside a disabled-by-platform branch and corrupt a dependency range that wasn't visible at parse time.
- **`Package.swift` with `// swift-tools-version:` directive and multiple products**: regex on the substring `version:` has multiple match candidates — the spec doesn't define disambiguation rules.
- **`Package.resolved` lockfile**: the bump should not touch this file (SwiftPM regenerates it), but the spec says "rewrite Package.swift" — a careless implementation that matches too broadly could rewrite the lockfile too.
- **`version` as part of a `Package.swift` comment or doc comment** would also match a naive regex.

**Recommended fix:**

- Primary version source: `git describe --tags --abbrev=0 --match "v*"`, strip the `v` prefix, fall back to `0.0.0` if no tags.
- Write path: **do not mutate `Package.swift`**. Create an annotated tag (`git tag -a v0.2.0 -m "..."`) and push it. SwiftPM resolution consumes the tag.
- Defer the `Package.swift`-rewrite path until a real use case appears (e.g., the user explicitly sets `version:` in their manifest as a hint and wants crackerjack to keep it in sync). When you do, use the SwiftSyntax parser (`PackageDescription` AST), not regex. SwiftSyntax is in SwiftPM and ships with the toolchain — no extra deps.
- For multi-package: explicit per-package version selection, or `crackerjack run -p minor --package <subdir>`.

### F2 — CRITICAL — `swift format` (built-in) vs `swift-format` (third-party) ambiguity is not addressed

**Spec (line 172):**

> `swift.format` → `swift format` (autofix=true)

**Why this matters:**

The Swift ecosystem has **two unrelated formatters** with confusable names:

1. **`swift format`** — a built-in SwiftPM subcommand (Swift 5.7+) using the upstream `swift-syntax` library. This is what the spec picks.
2. **`swift-format`** (hyphenated) — the third-party formatter Apple published as a separate package, also driven by `swift-syntax`, often invoked as `swift-format format` or via Mint/brew. Many projects pin this in CI for stable formatting.

If a project uses `swift-format` in CI (extremely common — Apple themselves, Vapor, many open-source libs), `crackerjack run` will format with the toolchain's bundled rules (which may differ from `.swift-format` config the project pins), and the project's CI will reject the commit. Conversely, if `swift-format` is installed and `swift format` is invoked, the spec's hook silently does the wrong thing on Apple Silicon toolchains where the built-in formatter is sometimes shadowed.

The spec also doesn't mention the **`.swift-format`** configuration file, which the built-in formatter reads. A naïve hook will format with defaults and produce a different style than the project enforces.

**Recommended fix:**

- Hook implementation order: 1) detect `.swift-format` config in project root; 2) prefer `swift-format` (third-party) if installed (more stable across toolchain versions); 3) fall back to `swift format` (built-in) and warn that formatting may diverge from project's CI.
- Document this precedence in the hook's help text and in the MCP tool description.
- Alternatively: make the formatter a project-config decision (`[tool.crackerjack.swift] formatter = "swift-format" | "swift-format-builtin"`) — this aligns with the deferred "per-project hook config" item in the open-questions list.

### F3 — HIGH — `swift package update` is deferred but is part of the same lifecycle as `bump`; the gap is real

**Spec (line 65):**

> Swift dependency upgrade (`swift package update`) — separate plan

**Why this is a gap, not a deferral:**

The lifecycle the spec describes is *project version* bump + tag + release. `swift package update` is a *dependency* refresh — it rewrites `Package.resolved`. These are different concerns, but:

- The user-facing mental model is "crackerjack keeps my Swift project current" — that includes deps.
- `uv lock --upgrade` and `npm update` are routinely part of a quality/lifecycle run in Python and JS ecosystems; SwiftPM users expect parity.
- If a Swift project ships a release with stale deps, the Swift Package Index flags it and downstream consumers can't adopt. `crackerjack run -p minor` ships a release; that release should ship with current deps.
- The MCP tool `run_swift_hooks` is the natural surface to expose `swift package update` as an optional hook (autofix=false, since it modifies `Package.resolved`).

**Recommended fix:**

- Add `swift.package.update` hook (autofix=false; runs `swift package update` and surfaces the diff in the report).
- Wire it into `crackerjack run` alongside `swift test`/`swift build`/`swift format`.
- Optionally include it in the lifecycle phase so `bump -p minor` always runs with current deps.

### F4 — HIGH — No platform/version gating; `swift test` will silently no-op or fail on iOS-only packages

**Spec assumption (line 40, line 170):**

> Hooks: `swift test`, `swift build`, `swift format`

**Why this is incomplete:**

The spec doesn't acknowledge that `swift test` and `swift build` behave differently per platform:

- **iOS-only packages** (e.g., `swiftui-ipc-client` targets iOS 16+): `swift test` requires an iOS Simulator destination. Without `-destination 'platform=iOS Simulator,name=iPhone 15'`, the command fails or no-ops depending on toolchain.
- **macOS-only packages**: `swift build` works on macOS; on Linux it fails entirely (no `AppKit`).
- **Multi-platform packages** with `platforms: [.macOS(.v13), .iOS(.v16)]`: each `swift build` invocation tests one platform by default; CI usually needs both.
- **`Package.swift` platforms directive**: should be parsed; if it lists iOS-only, the hook should pass `-Xswiftc -sdk` and a destination flag.
- **Swift toolchain version**: Swift 6.0 introduced strict concurrency; a project with `swift-tools-version: 6.0` may emit strict-concurrency errors that 5.x toolchains ignore. The spec should warn when crackerjack's installed toolchain is older than the project's minimum.

The spec's "no Python fallback — if `swift` is not in PATH, the hook fails with a clear message" applies equally to "Xcode/iOS SDK not installed."

**Recommended fix:**

- Parse `platforms:` from `Package.swift` (via SwiftSyntax) during detection.
- For iOS-targeted packages: pass `-destination 'generic/platform=iOS Simulator'` to `swift test`/`swift build`; require `xcrun` and an available SDK.
- For macOS-only on Linux: skip the hook with a clear "requires macOS toolchain" message rather than failing.
- Detect toolchain version (`swift --version`); emit a warning if older than `// swift-tools-version:` in the project.

### F5 — MEDIUM — Hooks run sequentially; parallel `swift test` + `swift build` will collide on `.build/`

**Spec assumption (line 256):**

> Hooks phase (if --skip-hooks not set): runs all Swift hooks (`swift test`, `swift build`, `swift format`)

**Why this is risky:**

SwiftPM writes all build artifacts to a single `.build/` directory at the project root. Two concurrent `swift` invocations against the same root will corrupt each other's derived data (manifest cache, module cache, index store). The existing Python hook pipeline in crackerjack runs hooks in parallel by default for speed; that model will break for Swift.

Additionally, `swift test` and `swift build` internally parallelize across cores; spawning both concurrently from crackerjack gives no speedup and risks lock files (`Package.resolved`, `.build/manifest.cache`).

**Recommended fix:**

- For the Swift adapter, override the default parallel-hook execution model: run hooks **sequentially** with an explicit barrier.
- Or, run `swift build` once, then `swift test` against the built artifacts (a separate `swift test --parallel` for test execution parallelism is fine — that's inside one subprocess).
- Add an integration test that runs the full hook phase twice in a row and asserts `.build/` is not corrupted.

### F6 — MEDIUM — `gh release create v{version}` doesn't notify the Swift Package Index, but the spec implies it does

**Spec (line 179):**

> `release`: `gh release create v{version} --generate-notes`

**Why this is a partial implementation:**

For SwiftPM libraries, `gh release create` is necessary but not sufficient. The **Swift Package Index** (swiftpackageindex.com) is the canonical discovery surface for SwiftPM libraries; it watches GitHub tags but with a lag, and a release without a body that mentions breaking changes won't surface. `--generate-notes` produces GitHub-flavored notes that are fine for the GitHub UI but do not give SPI enough structure to auto-categorize.

Also: `--generate-notes` requires the tag to already exist when called with `v{version}`. The lifecycle already creates the tag in step 4 ("`git tag -a v0.2.0 -m "..."`"), so the order is correct — but the spec should make this dependency explicit.

**Edge cases:**

- Protected branches: `gh release create` is a GitHub API call, not a git push; branch protection rules don't apply. But `git push origin main --tags` in step 4 will fail on protected main without `--force-with-lease` or a PAT. The spec is silent on this.
- Pre-existing tag: if a tag with the same name already exists, `gh release create v0.2.0` fails. The lifecycle should check or use `--force` deliberately.

**Recommended fix:**

- Document the tag-before-release ordering constraint.
- Add a `--draft` option for projects that want a manual review step before publishing.
- Add a follow-up hook: `swift.package_index.trigger_build` (calls `https://swiftpackageindex.com/api/packages/{owner}/{repo}/trigger-build` for the SPI auto-build workflow). This is a one-line `gh api` call but materially improves discoverability.

### F7 — MEDIUM — 10-minute timeout for `swift test` is insufficient for cold-cache test runs

**Spec (line 372):**

> `--timeout` per hook with reasonable defaults (10 min test, 15 min build)

**Why 10 min is too low:**

A first-time `swift test` on a clean checkout will: resolve dependencies, compile every transitive target, link the test bundle, run the tests. On Apple Silicon with a non-trivial project, this routinely exceeds 10 minutes (Vapor's test suite clocks ~8 minutes on M2; an iOS-only project with UIKit testing is 12-20 minutes). The default will produce flake.

**Recommended fix:**

- Default `swift test` timeout: 30 minutes; `swift build` timeout: 20 minutes.
- Make both configurable per-project via `[tool.crackerjack.swift] timeouts` (consistent with the deferred per-project config item).
- Cache `~/.swiftpm/` across hook invocations within a single `crackerjack run` (currently each subprocess starts cold).

### F8 — LOW — `swift package audit` does not exist; spec should not imply a CVE scanner

**Spec (reviewer prompt question, not in spec body):**

> What about `swift package audit` (CVE scan)?

**Answer:** There is no built-in `swift package audit` in SwiftPM as of Swift 6.0. The community-standard CVE check is via third-party tools (e.g., `swift-dependency-audit`, `osv-scanner` adapted for `Package.resolved`). The spec correctly omits this from hooks, but a future-proofing note in the "future work" section would prevent reviewer confusion.

**Recommended fix:**

- Add an explicit note in "Open questions / future work" that SwiftPM has no built-in vulnerability scanner and the adapter pattern makes adding one (e.g., `swift.osv_scan`) trivial when a community tool stabilizes.

### F9 — LOW — No `swift run` hook despite being a first-class SwiftPM subcommand

**Spec gap:**

The spec lists `swift test`, `swift build`, `swift format` but not `swift run`. For SwiftPM **executables** (not libraries), `swift run` is the canonical smoke test. `swiftui-ipc-client` is a library, so this doesn't bite today, but `mdinject`'s Swift app (mentioned in Phase 2 test plan) is an executable target.

**Recommended fix:**

- Add `swift.run` hook (autofix=false; runs `swift run <executable-name>` if the package declares executable products).
- Auto-detect executable products from `Package.swift` `.executableTarget(...)` / `.executable(...)`.

### F10 — LOW — Swift 6 strict concurrency is not surfaced; CI gating on toolchain version is missing

**Spec assumption:**

The spec does not mention Swift 6 strict concurrency at all. With Swift 6 (released 2024-09, current as of spec date), a `// swift-tools-version: 6.0` package enables strict concurrency checking by default. Crackerjack's `swift build` hook will surface those errors, but:

- The hook report doesn't distinguish "Swift 6 concurrency violation" from generic compile errors.
- The auto-fix hook (`swift format`) cannot fix concurrency errors — they're design-level, not style-level.
- A project on Swift 6 being CI-gated by an older toolchain will silently get a passing `swift build` that doesn't reflect what the project actually supports.

**Recommended fix:**

- In the MCP tool `run_swift_hooks` output, classify errors by kind (compile error vs. concurrency violation vs. warning).
- Surface a `[swift] toolchain X.Y.Z < project minimum A.B.C` warning when `swift --version` is older than `// swift-tools-version:`.

## Coverage Statement

This review covered the Swift-relevant portions of `docs/superpowers/specs/2026-09-07-crackerjack-multi-language-design.md`:

- `Package.swift` version source (lines 165-167): regex-based rewrite, fallback to `git describe`, multi-package, conditional fields, tag-derived versions.
- Swift hooks (lines 170-174, 256): `swift test`, `swift build`, `swift format`, plus third-party formatters, missing `swift run` and `swift package update`.
- Lifecycle (lines 177-180, 254-255): `gh release create`, tag ordering, branch protection, Swift Package Index integration.
- Cross-cutting concurrency (line 256): hook execution model, `.build/` collision risk.
- Platform/version gating (line 40, implicit throughout): iOS/macOS version targets, toolchain-version drift, Linux build parity.
- Out-of-scope items (lines 65, 354-358): `swift package update` deferral justification; CVE scan gap.
- General SwiftPM lifecycle: lockfile (`Package.resolved`), workspace support (Swift 5.9+), executable targets.

Findings ordered most-severe first. Read-only review; no spec modifications proposed beyond recommended fixes for the implementation team to consider.
