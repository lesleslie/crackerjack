# Jinja Lens Review

Reviewed against `jinja2 3.1.6` (the version installed in `crackerjack/.venv`).
Every claim marked "verified" below was checked by running the real lexer/parser,
or by reading the actual source of `fastblocks` / `jinja2-custom-delimiters`.

## Findings (most-severe first)

### F1: `Environment.parse()` cannot be re-emitted — the AST is lossy and has no unparser

- **Line**: 213 (`...parse(source)` to build an AST"), 216, 98
- **Summary**: The spec's core mechanism ("parse to an AST, reformat, emit") is not implementable with `jinja2.Environment.parse()`.
- **Failure scenario**: Verified against jinja2 3.1.6. `parse()` returns an `nodes.Template` with no `unparse()` / `to_source()` / `to_string()` method (`[n for n in dir(ast) if 'unparse' in n or 'source' in n]` is empty). Worse, the AST discards exactly the information a formatter needs:
  ```python
  src = '{# a comment #}\n{%- if x -%}\n{{- y -}}\n{% raw %}{% notatag %}{% endraw %}\n{% endif %}\n'
  jinja2.Environment().parse(src)
  # Template(body=[If(test=Name(name='x'), body=[Output(nodes=[
  #   Name(name='y'), TemplateData(data='{% notatag %}'), TemplateData(data='\n')])],
  #   elif_=[], else_=[])])
  ```
  The comment is gone. The `-` whitespace-control markers are gone. `{% raw %}` has collapsed into an indistinguishable `TemplateData`. Reconstructing source from this AST would silently delete every comment and every whitespace-control marker in the file — a catastrophic formatter.
- **Category**: correctness
- **Recommendation**: Build the formatter on `Environment.lex(source)`, not `parse()`. The token stream is high-fidelity and preserves everything the AST drops — verified it emits `comment_begin/comment/comment_end`, `block_begin '{%-'`, `variable_begin '{{-'`, `raw_begin/data/raw_end` as distinct tokens. Two caveats to design around: `lex()` drops the file's trailing newline (`lex('hello\n')` yields only `data 'hello'`) and silently normalizes CRLF to LF (`lex('a\r\nb')` yields `data 'a\nb'`), so final-newline and line-ending fidelity must come from the raw string, not the stream. Use `parse()` only as a *validation* gate ("does this still compile after formatting?"), never as the emit path — and see F7 for why even that gate is unsafe on fastblocks.

### F2: The `Environment(...)` config omits all three `*_end_string` kwargs and cannot parse fastblocks templates

- **Line**: 213, 212
- **Summary**: The spec configures only `block_start_string`, `variable_start_string`, `comment_start_string`. Jinja needs all six; without the end strings the environment cannot read a single fastblocks template.
- **Failure scenario**: Verified — the spec's literal config raises on fastblocks' own delimiters:
  ```python
  env = jinja2.Environment(block_start_string='[%', variable_start_string='[[', comment_start_string='[#')
  env.parse('[% if x %]hi[% endif %]')
  # TemplateSyntaxError: unexpected ']'
  ```
  With all six set (`block_end_string='%]'`, `variable_end_string=']]'`, `comment_end_string='#]'`) it parses cleanly. fastblocks does configure all six — `fastblocks/adapters/templates/jinja2.py:803-808` (`TemplatesSettings.delimiters`) and again at `fastblocks/actions/gather/templates.py:536-541`. The spec's Motivation section names the custom delimiters as `[%`, `[[`, `[#` (line 27) and never mentions the closers, which is likely where the omission crept in.
- **Category**: correctness
- **Recommendation**: Specify all six delimiter strings in both the `[tool.crackerjack.jinja]` schema and the `Environment(...)` construction. Mirror fastblocks' key names (`block_start_string`, `block_end_string`, `variable_start_string`, `variable_end_string`, `comment_start_string`, `comment_end_string`) so the config can be lifted from a fastblocks project verbatim.

### F3: Rules 2, 4, and 5 change rendered output — Jinja whitespace is program output, not formatting

- **Line**: 224 (Rule 2), 226 (Rule 4), 227 (Rule 5)
- **Summary**: Unlike Python, whitespace *between* Jinja tags is literal template output. Three of the seven canonical rules therefore change what the template renders.
- **Failure scenario**: Verified with default `Environment()` (`trim_blocks=False`, `lstrip_blocks=False`):
  ```python
  '{% if a %}A{% endif %}{% if b %}B{% endif %}'        -> 'AB'
  '{% if a %}A{% endif %}\n\n{% if b %}B{% endif %}'    -> 'A\n\nB'   # Rule 2 inserted this
  ```
  Rule 2 alone converts `AB` into `A\n\nB`. On an HTML template that is usually cosmetic; on a template that emits JSON, CSV, a `Content-Length`-sensitive body, a `<pre>` block, an email header block, or inline `<span>` markup where the browser collapses-but-does-not-delete whitespace, it is a behavior change shipped by a "formatter." Rule 5 has the same property (`'a   \nb'` renders with the three spaces; stripping them changes the bytes). Rule 4 is *accidentally* safe only because jinja2's default `keep_trailing_newline=False` eats the final newline — verified `from_string('x\n').render() == 'x'` — but the same template under `keep_trailing_newline=True` renders `'x\n'`, so Rule 4 is output-changing for any project that sets that flag.
- **Category**: correctness
- **Recommendation**: Split the policy into two tiers and say so explicitly. **Tier 1 (semantics-preserving, always applied)**: Rule 1 (verified inert — `{%if a%}` and `{% if a %}` both render `'A'`), Rule 6's tag-vs-inline classification where it does not move text, and normalization *inside* delimiters generally. **Tier 2 (output-changing, opt-in only)**: Rules 2, 4, 5. Gate Tier 2 behind explicit config, and require the formatter to know `trim_blocks` / `lstrip_blocks` / `keep_trailing_newline` before it can reason about whether a given rewrite is inert. The testing strategy (line 293) should add a semantic assertion — `render(format(x), ctx) == render(x, ctx)` over the corpus — which is the only test that catches this class.

### F4: Whitespace-control coverage is incomplete — `{%+`, `{{- -}}`, and asymmetric trims are unhandled

- **Line**: 229 (Rule 7)
- **Summary**: Rule 7 names only `{%- ... -%}`. Jinja's whitespace control is richer in three ways the rule does not cover.
- **Failure scenario**: All verified against the 3.1.6 lexer.
  1. **The `+` modifier**: `lex('{%+ if x %}')` emits `block_begin '{%+'`. `+` is the escape hatch that disables `lstrip_blocks` for one tag. A formatter that only knows about `-` will either drop the `+` (breaking indentation-sensitive output in every `lstrip_blocks=True` project) or fail to recognize the delimiter at all.
  2. **Variable and comment delimiters trim too**: `lex('{{- y -}}')` emits `variable_begin '{{-'` / `variable_end '-}}'`, and comments accept the same markers. Rule 7 is written as if only block tags do.
  3. **Asymmetric trims**: `{%- if x %}` (strip left, keep right) is common and meaningful. "Trim only when the source already trims" does not say whether the unit of preservation is the tag or the side.
- **Category**: completeness
- **Recommendation**: Restate Rule 7 as: *whitespace-control markers (`-` and `+`) are preserved verbatim, per side, per delimiter, for all three delimiter kinds; the formatter never adds, removes, or migrates one.* That is both simpler to specify and simpler to implement than the current phrasing, and it makes the rule trivially testable.

### F5: `{% raw %}` blocks are unaddressed — their contents must be byte-preserved

- **Line**: 218-232 (policy makes no mention of `raw`)
- **Summary**: Raw block contents are literal output that may contain text resembling Jinja tags. Any normalization inside them is corruption.
- **Failure scenario**: Verified — `lex('{% raw %}{% z %}{% endraw %}')` yields `raw_begin`, `data '{% z %}'`, `raw_end`. The good news is the token stream makes raw regions identifiable. The bad news is that a naive text-level pass applying Rule 1 ("one space inside delimiters") to the whole file would rewrite the `{% z %}` *inside* the raw block, changing the rendered output of a template whose entire purpose is emitting that literal. This is the standard failure mode for documentation templates that show Jinja syntax, and for templates emitting Vue/Angular/Handlebars markup. Note also that `{%raw%}` with no spaces lexes as a single `raw_begin '{%raw%}'` token, so the raw tags themselves are normalizable — it's only the enclosed `data` that must not be touched.
- **Category**: completeness
- **Recommendation**: Add an explicit rule: *content between `raw_begin` and `raw_end` is copied byte-for-byte; only the `raw`/`endraw` tags themselves are subject to Rule 1.* Add a raw-block case to the corpus (line 304 lists "nested blocks, inline expressions, comments, whitespace stripping" — raw is the missing fifth).

### F6: `line_statement_prefix`, `line_comment_prefix`, and the whitespace booleans are absent from the config surface

- **Line**: 212-213
- **Summary**: `Environment.__init__` takes 8 syntax-affecting parameters the spec doesn't mention. Two of them change the token grammar entirely; three more change what whitespace means.
- **Failure scenario**: Verified — with `Environment(line_statement_prefix='#', line_comment_prefix='##')`, the source `'# if x\nbody\n# endif\n## a comment\n'` lexes as `linestatement_begin '#'` … `linestatement_end '\n'` and `linecomment_begin '##'` / `linecomment '…'` / `linecomment_end ''`. These are *different token types* with no closing delimiter — the terminator is the newline. Rule 1 ("one space inside delimiters") is meaningless for them, and a formatter that assumes every construct is delimiter-bounded will either no-op on such a file (silent under-formatting) or, if it tries to apply Rule 6's "block-level tags get their own line," corrupt a line-statement by wrapping it. Separately, `trim_blocks`, `lstrip_blocks`, `keep_trailing_newline`, and `newline_sequence` are all required inputs for the Tier-2 reasoning in F3 — and note that fastblocks' `TemplatesSettings.delimiters` dict (`jinja2.py:803`) carries only the six delimiters, so these flags must be sourced separately.
- **Category**: completeness
- **Recommendation**: Extend the `[tool.crackerjack.jinja]` schema to the full syntax surface: six delimiters, `line_statement_prefix`, `line_comment_prefix`, `trim_blocks`, `lstrip_blocks`, `keep_trailing_newline`, `newline_sequence`. If either line-prefix is set, either implement the line-statement token forms or refuse the file with a clear "line-statement mode not supported" message — silently mangling it is the one unacceptable outcome.

### F7: Unknown tags from Jinja extensions are a hard parse error — fastblocks templates will fail 100% of the time

- **Line**: 213, 283 (error table: "Jinja parse error → report file:line:col; do NOT rewrite")
- **Summary**: `parse()` rejects any tag it doesn't recognize, and extension-provided tags are only recognized if the Environment was built with that extension. fastblocks loads several.
- **Failure scenario**: Verified:
  ```python
  jinja2.Environment().parse('{% trans %}hi{% endtrans %}')
  # TemplateSyntaxError: Encountered unknown tag 'trans'.
  jinja2.Environment(extensions=['jinja2.ext.i18n']).parse('{% trans %}hi{% endtrans %}')
  # parses fine
  ```
  fastblocks imports `i18n` and `loopcontrols` at `fastblocks/adapters/templates/jinja2.py:94`, and *dynamically discovers* arbitrary `Extension` subclasses (`jinja2.py:927`, `:1251`, `actions/gather/templates.py:251`), plus a user-configurable `TemplatesSettings.extensions: list[str]` (`jinja2.py:800`). So a bare-`Environment` formatter run against fastblocks would hit the error-table row on every `{% trans %}` template, report a "parse error," and decline to format — a silent 100% false-negative rate on the exact repo Phase 4 targets (line 341). And because the row says "do NOT rewrite," the failure looks like a clean skip rather than a bug.
- **Category**: correctness
- **Recommendation**: Two options, and the second is strictly better. (a) Read the project's extension list from config and pass it to `Environment(extensions=...)` — fragile, since fastblocks discovers extensions at runtime. (b) Don't use `parse()`. Verified that `lex()` tolerates unknown tags happily: `lex('{% cache 60 %}x{% endcache %}')` yields ordinary `block_begin` / `name 'cache'` / `integer 60` / `block_end` tokens with no error. A lexer-based formatter (per F1) is extension-agnostic by construction, which is a second independent reason to prefer it. If `parse()` is retained as a validation gate, an unknown-tag error must be treated as "cannot validate, skip formatting" and reported distinctly from a genuine syntax error, or the error table's promise becomes misleading.

### F8: The round-trip invariant is malformed and, once fixed, doesn't test the thing that matters

- **Line**: 216, 292
- **Summary**: `format(parse(format(x))) == format(x)` type-checks only if `format` accepts both a string and an AST, and even read charitably it tests idempotence rather than correctness.
- **Failure scenario**: `parse()` returns `nodes.Template`, `format()` takes source text, so the inner and outer `format` cannot be the same function. Read as intended it collapses to `format(format(x)) == format(x)` — idempotence. That is worth asserting, but it is satisfied by a formatter that deletes every comment in the file (deleting them twice is the same as deleting them once), and it is satisfied by every one of the output-changing rewrites in F3. It cannot catch either the F1 or F3 bug class.
- **Category**: correctness
- **Recommendation**: State three separate invariants: (1) **idempotence** — `format(format(x)) == format(x)`; (2) **semantic preservation** — `render(format(x), ctx) == render(x, ctx)` for a fixed context over the corpus, which is the invariant that actually guards F3; (3) **parse-stability** — `parse(format(x))` succeeds whenever `parse(x)` does, guarding against the formatter emitting something Jinja can't read back.

### F9: Delimiter autodetect is the primary path (not a fallback), and content-scanning is unreliable

- **Line**: 212
- **Summary**: The spec frames pyproject config as primary and autodetect as fallback. For fastblocks the reverse is true, and the proposed autodetect heuristic has both false positives and a single-answer-per-project limitation.
- **Failure scenario**: fastblocks' delimiters are a *code default* in `TemplatesSettings.delimiters` (`jinja2.py:801-810`), not a `pyproject.toml` entry — `git grep` finds no `[tool.crackerjack.jinja]`-shaped config anywhere in the repo. So "scan a sample `.jinja` file for the first non-default delimiter" becomes the load-bearing path on the flagship target. Three problems with it: (a) `[%`, `[[`, and `[#` are legal literal text in a standard-delimiter template — a Markdown link followed by an array (`[[1,2]]`), a JS array literal, a CSS attribute selector — so "first non-default delimiter found" fires on files that use standard delimiters; (b) it yields one global answer, but a project can hold both custom-delimiter templates and vendored standard-delimiter ones; (c) sampling "a" file makes the answer depend on directory iteration order.
- **Category**: risk
- **Recommendation**: Make explicit configuration required, and support a per-glob mapping rather than one project-wide answer (e.g. `[[tool.crackerjack.jinja.profiles]]` with `paths = ["templates/**"]` plus that profile's delimiter set). When no profile matches a file, skip it with a message naming the file and the missing config — never guess. If a convenience detector is still wanted, scope it to `crackerjack web jinja detect` as an interactive one-shot that prints a config block for the user to paste, so a wrong guess can't silently rewrite files.

### F10: PyCharm parity as specified is unachievable — the plugin has no formatter of its own

- **Line**: 234-242, 371 (Risk 2), 302-307
- **Summary**: The spec assumes both sides implement a policy that can be documented and matched. Reading the plugin source, its entire design is to *delegate* formatting to PyCharm Professional's built-in Jinja2 formatter.
- **Failure scenario**: `jinja2-custom-delimiters/src/main/java/.../formatting/CustomJinja2PreFormatProcessor.java` converts custom delimiters to standard via `DelimiterConversionUtil.convertCustomToStandard()` (a sorted-by-length `String.replace` chain), then returns control to IntelliJ; the post-processor converts back. There is no whitespace policy in the plugin at all. Consequences: (1) the output policy is IntelliJ's, changes with IDE releases, and is user-configurable through Code Style settings — so "both formatters must produce identical output" (line 242) is a claim about an IDE the spec doesn't control; (2) the `export-intellij-style` XML (line 241) can only set knobs IntelliJ exposes — it cannot make IntelliJ implement Rules 2, 6, or 7; (3) the path is gated on `LicenseGate.ensureLicensed(...)` and is Professional-only (`plugin.xml:19` — "Community editions do not provide the built-in Jinja2 formatter used by this plugin"), so for a Community user the plugin formats nothing and parity is vacuous. Worth noting the delimiter conversion itself is naive string replacement with no raw-block or string-literal awareness — verified that a standard-delimiter template can legally contain `"%}"` inside a string (`lex('{{ "%}" }}')` gives `string '"%}"'`), which that replacement chain would corrupt on the way back. That is the plugin's bug, not this spec's, but it undercuts the premise that the two implementations can be made to agree.
- **Category**: risk
- **Recommendation**: Replace "identical output" with a one-way, testable claim: *crackerjack's formatter output must be a fixed point of PyCharm's formatter* — i.e. reformatting a crackerjack-formatted file in PyCharm produces no diff. That is verifiable by hand on the corpus, is robust to IntelliJ's policy differing from ours on rules it doesn't implement, and doesn't require IntelliJ to change. Keep the XML export as a convenience for the knobs that do overlap (indent, continuation indent, spaces-inside-delimiters), and label it as partial. Also record the Professional-only + licensed-only constraint in the spec, since it determines who parity is even observable for.

### F11: `jinja2 >= 3.0` is not a crackerjack dependency, transitive or otherwise

- **Line**: 363 ("jinja2 >= 3.0 for `Environment.parse()` (already a transitive dep)")
- **Summary**: The compatibility note is factually wrong, and relying on the incidental venv state is a known Bodai failure mode.
- **Failure scenario**: Verified — `grep -n jinja pyproject.toml` returns nothing. jinja2 3.1.6 is present in `.venv` only because dev-tree packages pull it (`fastapi[standard]`, `nbconvert`, `transformers`, `jedi[docs]`, `starlette[full]`). None of those are runtime deps of the web adapter, so a lean production install of crackerjack would `ImportError` the moment `jinja_formatter.py` is imported. This is the same shape as `bodai-mcp-uv-sources-shadowing`: a dev-only presence mistaken for a declared dependency.
- **Category**: correctness
- **Recommendation**: Declare it. Given the web adapter is opt-in, a PEP 735 optional group (`[dependency-groups] web = ["jinja2~=3.1"]`) with a lazy import and a clear `RuntimeError` when missing matches the pattern already used elsewhere in Bodai for `pypdf`/`ebooklib`. Pin `>=3.1`, not `>=3.0` — the `{%+` lstrip-escape (F4) and `keep_trailing_newline` semantics (F3) both matter here, and `3.1` is what the corpus will actually be validated against.

### F12: `TemplateSyntaxError` has no column — the promised `file:line:col` cannot be produced

- **Line**: 283
- **Summary**: The error table commits to `file:line:col`. jinja2 does not carry a column.
- **Failure scenario**: Verified — `TemplateSyntaxError` exposes `lineno`, `message`, `filename`, `name`, `source`; `hasattr(e, 'col')` is `False`. Implementing the table as written means either fabricating a column (`:0`, or a guess) or the implementer quietly dropping it and the doc drifting from the code.
- **Category**: correctness
- **Recommendation**: Specify `file:line: message` and note that jinja2 does not provide column information. If a column is genuinely wanted, it can be derived from the token stream by tracking offsets, but that should be an explicit design decision rather than an inherited assumption.

### F13: The 200-400 LOC estimate reflects the AST design that doesn't work

- **Line**: 98
- **Summary**: With the corrections above the formatter is materially larger, and the estimate risks Phase 4 being scoped as a small task.
- **Failure scenario**: The implementable design must handle: six configurable delimiters plus two line-prefix modes (F6); per-side `-`/`+` preservation across three delimiter kinds (F4); byte-preserved raw regions (F5); comment preservation (F1); final-newline and CRLF fidelity outside the token stream (F1); Tier-1/Tier-2 rule separation with `trim_blocks`/`lstrip_blocks` awareness (F3); and a per-glob delimiter profile resolver (F9). That is realistically 600-900 LOC before tests, plus the ~30-template corpus. The number itself isn't load-bearing — the risk is a Phase 4 plan that budgets a weekend for a two-week job.
- **Category**: risk
- **Recommendation**: Re-estimate after the design is corrected, or drop the LOC figure and scope by capability tiers instead (Tier 1 rules first, ship, then Tier 2 behind config). Tier 1 alone is genuinely small and is the part with no semantic risk.

### F14: The policy module is named inconsistently and is missing from the package layout

- **Line**: 98 (`jinja_formatter.py`) vs 231 (`crackerjack/adapters/web/jinja_canonical.py`)
- **Summary**: Two filenames for the policy, and the second doesn't appear in the layout diagram.
- **Failure scenario**: The layout at lines 93-98 lists only `jinja_formatter.py`; line 231 introduces `jinja_canonical.py` holding `JinjaCanonicalFormatter` as "the single source of truth." An implementer following the diagram creates one file; one following the policy section creates another. Low stakes, but "single source of truth" claims are worth getting right in the doc that makes them.
- **Category**: completeness
- **Recommendation**: Pick one. Given the split recommended in F3, two modules is actually defensible — `jinja_canonical.py` for the rule definitions and `jinja_formatter.py` for the token-stream driver — but say that explicitly and add both to the layout diagram.

## Coverage Statement

This review covered the Jinja-specific mechanics of the spec only:

- `jinja2.Environment.parse()` viability for re-emission, and the `lex()` alternative (F1, F7)
- The full `Environment` syntax-configuration surface: six delimiters, both line prefixes, `trim_blocks`/`lstrip_blocks`/`keep_trailing_newline`/`newline_sequence` (F2, F6)
- Each of the 7 canonical whitespace rules, evaluated for output-preservation (F3) and completeness (F4, F5)
- Specific Jinja constructs named in the review brief: `{%- if x -%}`, `{{- var -}}`, `{%+ %}`, `{% raw %}`, macros, `{% include %}`/`{% extends %}`, filters, multi-line block tags (F4, F5, F10-adjacent)
- Delimiter autodetect reliability, including fastblocks' actual config location (F9)
- The round-trip / idempotence invariant and what it can and cannot catch (F8)
- PyCharm parity feasibility, read against `jinja2-custom-delimiters`' real formatter source (F10)
- The `jinja2` dependency claim and error-reporting contract (F11, F12)
- LOC estimate and module naming (F13, F14)

Verified empirically against jinja2 3.1.6 in `crackerjack/.venv`; fastblocks claims read from `fastblocks/adapters/templates/jinja2.py` and `fastblocks/actions/gather/templates.py`; plugin claims read from `jinja2-custom-delimiters/src/main/java/com/wedgwoodwebworks/jinja2customdelimiters/formatting/`.

**Not covered** (other lenses): the web adapter's external CLI hooks (stylelint/eslint/tsc/html-validate), web file detection heuristics, npx invocation strategy, MCP tool naming and registration, Swift and Kotlin adapters, the `LanguageAdapter`/`Hook`/`VersionSource` protocol design, the Phase 1 Python refactor, and general spec-writing concerns. Macros and includes are noted as structurally unproblematic (verified `{% include %}` and `{% extends %}` parse with no loader configured) and need no formatter-specific handling beyond the block-tag rules.
