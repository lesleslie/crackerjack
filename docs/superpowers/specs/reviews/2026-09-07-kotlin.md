## Findings (most-severe first)

### 1. CRITICAL — `version=` regex won't read the version of the named Phase 3 test fixture

Spec (line 188): "parse `gradle.properties` and read `version=` field."

`/Users/les/Projects/jinja2-custom-delimiters/gradle.properties` has no
`version=` line. It has:

```properties
pluginVersion = 1.0.3
pluginSinceBuild = 252
pluginUntilBuild = 253.*
pluginSinceBuild = 252                  # repeats
pluginGroup = com.wedgwoodwebworks....  # group, not version
gradleVersion = 9.1.0                   # tool version, not project version
```

If the implementation uses an unanchored regex like `^version\s*=` it returns
nothing and Phase 3 starts with a missing `VersionSource`. If it uses a
loose regex like `version\s*=` it will grab **`pluginSinceBuild = 252`** or
**`gradleVersion = 9.1.0`** as the "version" — both are silent data-integrity
bugs the spec's own read-back check (`VersionSource.write()` fails to read
back) will miss, because the wrong-key read happens before any write.

The IntelliJ Platform Gradle Plugin convention (which the spec is implicitly
targeting — it's the most common Kotlin/Gradle plugin in the Bodai
ecosystem, and `jinja2-custom-delimiters` is exactly that) uses
`**pluginVersion`**, not `version`. Other plausible keys in real-world Kotlin
projects:

| Convention | Where it appears |
|---|---|
| `pluginVersion` | IntelliJ Platform plugin projects (`org.jetbrains.intellij.platform` Gradle plugin) |
| `projectVersion` | Some convention plugins |
| `version` | Spring Boot, Android, vanilla Kotlin libs |
| `libraryVersion` | Some multi-module setups |
| `kotlinVersion` (a Kotlin toolchain version) | Multi-project builds with explicit toolchain pinning |

A correct adapter should:

1. Probe `pluginVersion`, `projectVersion`, `version` (in that order),
   anchored with `\b` or `^`.
2. If none match in `gradle.properties`, fall back to a `build.gradle.kts`
   scan for `version = "..."` on the right side of the assignment.
3. Treat any match as candidate and verify with a follow-up
   `./gradlew properties | grep '^version:'` round-trip before
   committing the version bump — that is the source of truth Gradle itself
   uses.

Severity: **critical** — the spec's stated Phase 3 acceptance criterion
("test on `jinja2-custom-delimiters`") cannot be met end-to-end with the
proposed parser.

### 2. CRITICAL — Hook invocations assume plugins that aren't applied in the ground-truth fixture

Spec (lines 192-194):

```
kotlin.ktlint  → ./gradlew ktlintCheck (with ktlintFormat for autofix)
kotlin.detekt  → ./gradlew detekt
kotlin.test    → ./gradlew test
```

`/Users/les/Projects/jinja2-custom-delimiters/` applies **none** of the
ktlint / detekt plugins. Running `./gradlew ktlintCheck` against it yields:

```
Task 'ktlintCheck' not found in root project 'jinja2-custom-delimiters'.
```

Same for `detekt`. (`test` will work because the `java` plugin creates it.)

Two possible fixes; pick one explicitly in the spec:

- **(a)** Add an apply-plugin step to the test fixture as a Phase 3
  prerequisite. This makes the fixture non-representative of a real
  Bodai IntelliJ plugin and is a leak of Phase 3 work into the upstream
  repo.
- **(b)** Make the adapter probe for task existence per-hook, e.g.
  `./gradlew tasks --all | grep -E '^(ktlintCheck|detekt)$'`. If absent
  → skip with a structured warning naming the missing plugin
  (`org.jlleitschuh.gradle-ktlint-plugin` for ktlint,
  `io.gitlab.arturbosch.detekt` for detekt). This is the more honest
  behaviour and matches the spec's broader "CLI not installed → skip
  with warning" rule (line 279).

Recommend (b) — it generalises to Kotlin projects that have, say,
ktlint but not detekt (very common).

### 3. HIGH — `./gradlew --no-daemon` for CI / crackerjack subprocess invocations not specified

Spec says "`./gradlew ktlintCheck`" without flag advice. Crackerjack runs
hooks as subprocesses; the Gradle daemon:

- Adds ~3-8s JVM startup overhead per hook (kills fast feedback loops).
- Holds file descriptors between hook calls — invisible to crackerjack
  and not cleaned up if a sub-process is killed mid-way.
- Fails intermittently in containerised CI / Dockerised runners (the
  Gradle daemon's "daemon expiration" check races with fast pytest
  teardown).

Recommended canonical invocation:

```python
# ./gradlew invoked WITHOUT daemon, WITHOUT configuration cache.
# Both are incompatible with crackerjack's short-lived subprocess
# pattern and the spec's `--no-daemon` for CI convention.
Hook(
    name="kotlin.ktlint",
    cli_command=("./gradlew", "--no-daemon", "--no-configuration-cache", "ktlintCheck"),
    ...
)
```

The `--no-configuration-cache` flag pairs with the spec's not-yet-made
choice about how to handle the IntelliJ plugin's
`org.gradle.configuration-cache = true` setting (which the fixture
enables). On cache-miss this costs ~5-10s of configuration time per
hook; on daemon-less runs it's worse, and the cache itself becomes
stale when `gradle.properties` is rewritten by the lifecycle step.

Severity: **high** — these are operational foot-guns the codebase
already has memory about (`crackerjack-hides-ty-output.md`-class
silent-failure patterns).

### 4. HIGH — Multi-project / buildSrc / version catalog sources not covered

Spec (line 188): "Most idiomatic location for Gradle multi-project
builds." — underspecified.

Three patterns the parser must cover, none of which are addressed:

**(a) `buildSrc/`-managed versions.**
Real-world Gradle projects centralise versions in a `Versions` object:

```kotlin
// buildSrc/src/main/kotlin/Versions.kt
object Versions {
    const val Kotlin = "2.0.21"
    const val Lib = "1.2.3"
}
```

Crackerjack would need `version = Versions.Lib` traversal.

**(b) Convention plugins (`buildSrc/src/main/kotlin/foo.gradle.kts`).**
Common in Bodai-adjacent multi-module repos. The version literal lives
in a shared convention plugin and each subproject `apply`s it.

**(c) Gradle version catalog (`gradle/libs.versions.toml`).**
The ground-truth fixture ships one. Future Kotlin projects (this is the
Gradle-recommended approach) put versions in a `[versions]` block:

```toml
[versions]
plugin = "1.0.3"
```

The `version-ref = "plugin"` reference chain still points at the literal.

Spec should explicitly scope v0.81 to **(c)** (catalog) and **(a)**
(`gradle.properties`), explicitly deferring **(b)**, and the version-write
operation should round-trip via `gradle properties` rather than parsing
TOML/KTS ad hoc. Adapter contract should expose:

```python
def candidates(project_root: Path) -> list[Path]:
    """Ordered list of files that may carry the version literal."""
    # gradle/libs.versions.toml  (version catalog — preferred)
    # gradle.properties          (legacy/IntelliJ Platform)
    # settings.gradle.kts        (only as last resort; check version= literal)
```

### 5. HIGH — `build.gradle.kts` version= fallback regex too narrow

Spec (line 189): "fall back to regex on the `version = "..."` line."

In Kotlin DSL the assignment is overloaded:

```kotlin
// Easy case — literal
version = "1.2.3"

// Provider case — must be skipped, NOT bumped
version = providers.gradleProperty("pluginVersion").get()

// Catalog case — must be followed to its source
version = libs.versions.plugin.get()

// Closure case — uncommon but exists
version = "1.2.3".let { ... }
```

A naive regex `(version\s*=\s*")([^"]+)(")` will mutate the provider case
silently (`version = providers.gradleProperty("1.2.3").get()`), which
will then fail to evaluate on next `./gradlew` run — a clear data-loss
incident masquerading as a successful bump.

Spec should explicitly say:

1. The parser must recognise `version = <literal-string>` and nothing
   else as the writable pattern.
2. `version = providers.gradleProperty(<key>).get()` is a *pointer* — the
   bump must update the upstream `gradle.properties` key, not this
   line.
3. `version = libs.versions.<ref>.get()` is a catalog reference — bump
   must update `gradle/libs.versions.toml`.

### 6. MEDIUM — Detekt config absence unhandled

Spec assumes `./gradlew detekt` works. The `io.gitlab.arturbosch.detekt`
plugin reads `config/detekt.yml` (or `detekt.yml`) by default; if
absent, detekt 1.x fails the build with `Config file not found`. The
ground-truth fixture ships no such file (and applies no detekt plugin).

Spec should add:

- Probe for `<root>/config/detekt.yml` and `<root>/detekt.yml`.
- Hook behaviour by detection outcome:
  - Plugin + config both present → run `./gradlew detekt`.
  - Plugin present, config absent → run `./gradlew detekt` with
    `--config /dev/null` or skip-with-warning naming the missing config
    (the detekt 2.x default config ships with the plugin and may be
    acceptable).
  - Plugin absent → skip-with-warning (per finding 2 above).
- Allow `crackerjack.toml` / `[tool.crackerjack.kotlin]` block to
  configure a per-project `detekt_config` path. Spec already lists
  per-project hook config as deferred-to-v0.82 (line 354), so for v0.81
  just probe and warn.

### 7. MEDIUM — Marketplace publishing deferred without an in-spec warning

Spec (line 60): "Kotlin/JetBrains Marketplace automated publishing
... out of scope."

This is the actual *terminal* step for the named Phase 3 test fixture,
which is an IntelliJ plugin. The lifecycle currently produces a `git
tag` and a `gh release` — but the JetBrains IntelliJ Platform Plugin
Gradle Plugin already provides `./gradlew publishPlugin` (consuming
`PUBLISH_TOKEN`) for shipping the artifact. Deferring the auto-invoke
is reasonable, but the spec should:

1. Surface a clear warning during `kotlin.bump` when the project has
   `org.jetbrains.intellij.platform` applied: "Marketplace publishing
   not configured — manual `./gradlew publishPlugin` required."
2. Detect Marketplace readiness via `./gradlew tasks --all | grep
   publishPlugin` so the warning is conditional, not noisy for
   non-IntelliJ Kotlin projects.
3. Note in the Open Questions / future work that shipping via
   `gh release create` alone is **not sufficient** for JetBrains plugin
   consumers — `gh release` is the GitHub source tarball, not the
   installable plugin.

The user's auto-memory `crackerjack-version-bumping-manual.md`
explicitly says user-initiated bumps and PyPI publishes; the Kotlin/
JetBrains marketplace analog is the same posture. Spec should reflect
it in the lifecycle rules, not just leave it deferred.

### 8. MEDIUM — Gradle wrapper update not in lifecycle

Spec lifecycle: "bump → commit → tag → push → gh release."

Gradle project releases typically also bump:

- `gradle/wrapper/gradle-wrapper.properties` (`distributionUrl`)
- The `gradleVersion` property in `gradle.properties`

The ground-truth fixture shows these are *already* out of sync
(`gradleVersion = 9.1.0` property; wrapper `9.4.1`). A version bump
that doesn't address the wrapper will drift further on the next
contributor's machine.

Minimum: spec should mention in the lifecycle's pre-bump phase a
`gradle wrapper --gradle-version <new>` invocation, gated by a
`--update-wrapper` flag, off by default. This matches the spec's
"Auto-fix safety" open question (line 358) and keeps the lifecycle
honest.

### 9. LOW — KSP / annotation processors not mentioned

Spec's hook section omits KSP-generated sources entirely. Modern Kotlin
projects (Hilt, Room, Moshi-X, Koin annotations, Compose Compiler
2.x) generate code under `build/generated/ksp/` or
`build/generated/source/ksp/`.

Both ktlint and detekt have explicit exclude patterns for generated
sources:

```yaml
# detekt.yml
excludes:
  - 'build/generated/**'
  - '**/generated/**'

# .editorconfig (ktlint)
ktlint_excludes = build/generated/**
```

Spec should at minimum:

- Default `--exclude 'build/**'` for both tools (matches existing
  Gradle plugin defaults).
- Add a `crackerjack.toml` knob (`[tool.crackerjack.kotlin] ksp_excludes`)
  for v0.81 or later.
- Mention KSP by name in the open questions so v0.82+ can make the
  exclude configurable.

### 10. LOW — `gradlew.bat` for Windows not in spec

Spec says `./gradlew` (POSIX-only). The Bodai CI pipeline may run on
Windows agents; `gradlew.bat` is the canonical Gradle wrapper entry
point for CMD/PowerShell.

Spec should expose a `wrapper_script()` helper that returns:

- `gradlew` on POSIX
- `gradlew.bat` on Windows (detected via `os.name`)

Severity is low because no current Bodai Kotlin project ships
Windows-targeted build scripts, but it's a 3-line fix that prevents
a class of cross-platform bug.

---

### 11. LOW — Composite builds not addressed

Spec's hook invocation `./gradlew ktlintCheck` runs hooks only at the
root. Composite builds (`includeBuild("...")` in `settings.gradle.kts`)
have multiple Gradle builds with separate task graphs; running hooks
at the root misses the included builds.

Spec should add to the lifecycle:

- A pre-bump step: `./gradlew projects` to enumerate Gradle builds.
- A per-build hook invocation, OR a documented "run hooks via root
  only" mode.

Defer to v0.82 unless a composite-build Kotlin repo lands in Bodai
before Phase 3 ships.
