# A11y Lens Review — Crackerjack Multi-Language Extension

**Reviewer**: Accessibility lens (WCAG 2.1/2.2 AA perspective, universal design, screen reader & keyboard-first)
**Spec under review**: `docs/superpowers/specs/2026-09-07-crackerjack-multi-language-design.md`
**Mode**: Read-only. No spec changes recommended via diff; findings only.

---

## Findings (most-severe first)

### F1 — Web adapter ships zero a11y tooling (Critical)
**Category**: Web hooks scope / Phase 4
**WCAG reference**: All Level A and AA success criteria (tooling is the enforcement mechanism)
**Finding**: The Web adapter hook list (`stylelint`, `eslint`, `tsc --noEmit`, `html-validate`) contains **no accessibility tool**. The "hooks only" scope decision in Phase 4 explicitly excludes a11y — and the doc never even acknowledges the gap. For a tool that will run on `fastblocks/`, `splashstand/`, and other Bodai web projects, this is an enforcement vacuum: a Python web project passes `crackerjack run` cleanly while emitting, e.g., `<img src="logo.png">` (alt-text missing, WCAG 1.1.1), `<button>` without accessible name (4.1.2), or `<div onclick=...>` with no keyboard handler (2.1.1). The spec's "Same operational surface, more languages" claim cannot be honored for the web layer without an a11y dimension — that layer ships *less* coverage than the Python layer's ruff/bandit surface for security-adjacent rules.
**Recommendation**:
- Phase 4 must include **at minimum**:
  - `@axe-core/cli` (or `axe-core` invoked via a tiny Node bridge) for static HTML WCAG checks.
  - `pa11y-ci` for whole-page WCAG audits (requires a running server, so gate it behind a `--serve` / fixture-server hook).
  - `stylelint` config extended with `stylelint-config-standard` plus a color-contrast / focus-visible plugin (e.g. `stylelint-no-unsupported-browser-features` for `:focus-visible` regression, and a custom rule set verifying `outline: none` is not used without an explicit `:focus-visible` replacement).
  - `eslint-plugin-jsx-a11y` registered automatically when JSX/TSX files are detected (it is opt-in even with `eslint-plugin-react` installed, so silent omission is the failure mode).
- Add a "Web a11y hooks" subsection to §Architecture and §Per-adapter responsibilities (Web adapter) parallel to the existing four hooks.
- The Phase ordering should make Web a11y Phase 4, not Phase 6+ — shipping the Web adapter *without* a11y creates the very audit gap `mcp-surface-health-illusion` warns about (tools present, results empty, gates green).

### F2 — `crackerjack run` does not gate on WCAG AA (Critical)
**Category**: Quality-gate semantics
**WCAG reference**: WCAG 2.1 AA is the regulatory floor (Section 508, EN 301 549, AODA)
**Finding**: Spec §Data flow says both adapter groups "contribute to the success/failure report" and the error-handling table treats any hook subprocess failure as "fail the gate." But there is no commitment about *which* failures fail the gate vs. warn. Concretely: if F1 is fixed and `axe-core` is added, does a single WCAG Level A violation fail `crackerjack run`? Does it block `crackerjack run -p minor` from tagging a release? Spec is silent. For Python's existing layer, the gate philosophy is "fail-loud on hard limits, warn on stylistic." The spec does not translate that to a11y — and a11y is in the "hard limit" bucket for any web project shipping to public users.
**Recommendation**:
- Add a §Quality-Gate Semantics subsection to Architecture.
- Define explicit tiering: WCAG Level A violations = gate fail; Level AA violations = gate fail (or warn with `--strict-a11y` flag); Level AAA = warn only.
- Treat a11y gate failures as blockers for `run -p {major|minor|patch}` (similar to how `crackerjack-p-minor-full-lifecycle.md` treats hook failures blocking version bumps).
- Default level: AA (industry baseline). Allow `[tool.crackerjack.a11y]` config to relax or escalate per project.

### F3 — `html-validate` ≠ WCAG conformance (Major, conceptual)
**Category**: Tool scope conflation
**WCAG reference**: WCAG is a behavioral & perceptual conformance standard; `html-validate` is structural only
**Finding**: The spec lists `html-validate` alongside the other Web hooks without distinguishing it from a WCAG tool. `html-validate` checks syntactic/semantic HTML correctness — closing-tag pairing, valid ARIA attribute usage per ARIA spec, deprecated elements, etc. It does *not* evaluate:
- Color contrast ratios (1.4.3, 1.4.11)
- Keyboard accessibility (2.1.1, 2.4.7)
- Focus order and visibility (2.4.3, 2.4.7)
- Screen-reader announcement order and live-region behavior (4.1.3)
- Form error identification and label association (3.3.1, 3.3.3, 4.1.2)
- Text resize up to 200% (1.4.4)

The spec treats "html-validate" as if it covers the same domain as the linting hooks, but a passing `html-validate` run says essentially nothing about whether a page is usable by a screen-reader user. A reviewer reading the spec would reasonably conclude "html-validate passed → a11y is fine." It is not.
**Recommendation**:
- Rename or annotate the hook list: `web.html.validate` is structural (current), and add a separate `web.a11y.axe` (or equivalent) for WCAG.
- Update §Per-adapter responsibilities (Web) to explicitly note "html-validate covers structural/ARIA syntax; a separate a11y hook covers WCAG conformance."
- Document in the spec that ARIA attribute *validity* (checked by html-validate) and ARIA attribute *effectiveness* (checked by axe) are two different gates.

### F4 — Jinja formatter whitespace rules can corrupt a11y-critical markup (Major)
**Category**: Jinja canonical whitespace policy (§Canonical Jinja whitespace policy)
**WCAG reference**: 1.1.1 (alt text), 1.3.1 (info/relationships), 2.4.6 (headings/labels), 4.1.2 (name/role/value)
**Finding**: The 7-rule canonical policy has several edges that interact badly with attributes and inline content that screen readers and a11y tooling care about. Specifically:

- **Rule 6** ("Inline `{{ var }}` may remain inline"): consider an a11y-sensitive attribute like `aria-label="Search {{ category|default('all') }} results"` or `alt="{{ image_alt|e }}"`. If the formatter decides an inline expression is "too long" or wraps it, the attribute value whitespace changes. Screen readers and ARIA-spec implementations treat certain attribute whitespace inconsistently:
  - ARIA spec: `aria-label` is whitespace-collapsed per the HTML spec; multiple spaces collapse to one.
  - But `aria-describedby` references an `id`, and any whitespace change in the *referenced* text node can change what the screen reader announces.
  - `alt` attribute: per HTML spec, leading/trailing whitespace is collapsed, but the surrounding template's whitespace *outside* the attribute is fine — *inside* the attribute value, behavior is stricter.
- **Rule 7** ("Trim `{%- ... -%}` only when the source already trims"): the policy says don't introduce new trim markers. But consider `<a href="/x">{% if foo %}Show{% else %}Hide{% endif %}</a>` rendered to a screen reader — the inline text node has whitespace from the indentation. Trimming is *not* the only risk; the formatter must also not strip *content* whitespace inside `<a>`, `<button>`, `<label>`, `<legend>`, `<caption>`, etc. that screen readers use to set prosody.
- **Rule 2** ("Blank line between block-level tags at the top level"): top-level blank lines in a Jinja source become either nothing in output (between sibling blocks) or whitespace between text nodes. If two adjacent blocks render to inline `<span>` content separated only by whitespace, the screen reader may or may not announce a word boundary — this is implementation-defined.
- **Rule 5** ("No trailing whitespace on lines"): fine.
- The spec's "round-trip invariant" `format(parse(format(x))) == format(x)` only ensures *stability*, not *correctness*. It will pass even if the formatter produces markup that is valid HTML but breaks ARIA name calculation.

**Recommendation**:
- Add an explicit "a11y-safe subset" clause to the canonical policy: attributes that affect accessibility (`aria-label`, `aria-labelledby`, `aria-describedby`, `alt`, `title`, `<label>`, `<legend>`, `<caption>`, `<button>` text content, heading text) must preserve *byte-for-byte* whitespace inside their quoted values.
- Add a fixture corpus section in `tests/fixtures/jinja-corpus/` for a11y-sensitive templates: `aria-label with expression`, `alt with fallback`, `label wrapping input`, `heading inside conditional`. Each fixture must render to a string where the critical attribute value is unchanged before and after `format`.
- Cross-check against the HTML spec's whitespace handling (§§13.2.5.42, 13.2.5.43, and ARIA's text calculation algorithm in https://www.w3.org/TR/accname-1.2/ — which uses `.strip()` then space-collapse).
- Consider a `--strict-a11y` mode that runs the formatter in a "no whitespace change inside attribute values" pass for projects that care.

### F5 — CSS a11y hooks unspecified (Major)
**Category**: Stylelint configuration
**WCAG reference**: 1.4.3 (contrast min), 1.4.11 (non-text contrast), 2.4.7 (focus visible), 2.4.13 (focus not obscured, WCAG 2.2)
**Finding**: §Per-adapter responsibilities (Web) says `web.css.stylelint → npx stylelint **/*.css`. No config file, no plugin set, no rule list. This is a thin shell that delegates everything to whatever config the consuming project ships. For a tool that ships a "same operational surface" promise, the bare-CLI invocation:
- Will use the project's own `.stylelintrc` if present — *different per project*, so the "same surface" is illusory.
- Will silently pass on projects that have no config (defaults to `stylelint-config-recommended`, which is *not* an a11y config).
- Will not detect: `:focus { outline: none; }` without replacement (WCAG 2.4.7 violation), color-only state indicators (1.4.1), `display: none` on interactive elements, missing `:focus-visible` (2.4.13 WCAG 2.2), or `user-select: none` on text.

**Recommendation**:
- Define a **default** stylelint config in `crackerjack/adapters/web/stylelint_config.json` (or `stylelint.config.js`) shipped as part of the adapter package. At minimum:
  - Extend `stylelint-config-standard`.
  - Include the `stylelint-no-unsupported-browser-features` plugin set to errors (catches `:focus-visible` regressions in old-browser fallbacks).
  - Disallow `outline: none` and `outline: 0` without an accompanying `:focus-visible` rule (custom rule or community plugin).
  - Disallow `display: none` on `button`, `a`, `input`, `select`, `textarea` selectors (custom rule).
  - Warn on `user-select: none` outside specific selector allowlist.
- Document the config in the spec, not just in code.
- Projects can override with their own config (existing escape hatch), but the **default** must be a11y-aware.

### F6 — `eslint-plugin-jsx-a11y` opt-in trap (Major)
**Category**: JS/TS linting
**WCAG reference**: Most Level A and AA SCs for interactive components
**Finding**: §Per-adapter responsibilities (Web) lists `web.js.eslint → npx eslint .` with no plugin enumeration. `eslint-plugin-jsx-a11y` is *not* bundled with `eslint` or `eslint-plugin-react`; it must be installed and configured separately. The spec's bare invocation guarantees the plugin is not active by default. This is exactly the class of omission that produces an MCP server reporting tools present but producing empty signals (cf. memory `mcp-surface-health-illusion.md`).
**Recommendation**:
- Add an explicit `web.js.eslint` plugin list: `eslint-plugin-jsx-a11y`, `eslint-plugin-react` (if JSX detected), `@typescript-eslint/eslint-plugin` (if TS detected).
- Either bundle the recommended config via `extends: ['plugin:jsx-a11y/recommended']` in a shipped `eslint.config.js`, or document that projects must add it themselves.
- Detection logic: if any `.jsx` or `.tsx` file exists in the project, `web.js.eslint` must require `eslint-plugin-jsx-a11y` or fail the hook with an actionable error message (not silent skip).

### F7 — Severity & reporting model unspecified for a11y (Major)
**Category**: Reporting
**Finding**: §Data flow says "Both contribute to the success/failure report" and §Error handling gives a single "fail the gate" row for "Hook subprocess fails." For a11y, the report granularity matters because:
- A WCAG Level A violation on a single page is fundamentally different from a stylistic `lang` attribute warning on the same page.
- Reporting 3,000 contrast warnings as "hook failed" produces alert fatigue and erodes trust in the gate (cf. `ty-hides-ty-output.md` patterns where swallowed signals cause regressions).
- For accessibility, the WCAG conformance level (A / AA / AAA) **is** the severity tier. Without explicit tiering, an axe-core dump of all severities becomes noise.

**Recommendation**:
- Define an a11y report category distinct from linting reports. Surface:
  - `WCAG-A-critical`: count, locations, SC reference
  - `WCAG-AA-critical`: count, locations, SC reference
  - `WCAG-AAA-warn`: count, locations, SC reference
  - Per-URL or per-file breakdown (not a flat list)
- Default gate behavior (per F2): A/AA failures fail the gate; AAA warns.
- The MCP tool result for `check_web_lint` should distinguish a11y from lint in its response schema so downstream agents (Claude Code, etc.) can route them differently.

### F8 — `aria-label` & ARIA text calculation is whitespace-sensitive (Major, minor variant of F4)
**Category**: Jinja formatter / cross-language risk
**WCAG reference**: 4.1.2 (name/role/value), ARIA name calculation algorithm
**Finding**: Per the Accessible Name and Description Computation spec (accname 1.2), the accessible name of an element is computed by stripping leading/trailing whitespace and collapsing internal whitespace runs. **However**, the source markup's whitespace *outside* the named element also affects text node announcement in flow content. If the Jinja formatter:
- Strips whitespace between an inline `<span>` and its adjacent text node, the screen reader may concatenate the two with no word boundary (e.g., "Open menu" → "Openmenu").
- Adds whitespace where there was none, it may insert an unwanted pause or word boundary.
- This is *content whitespace*, not attribute whitespace — the formatter Rule 7 boundary is in the right zone but the spec doesn't make the rule precise enough to avoid this.

**Recommendation**:
- Add an explicit policy line: "Whitespace in text-flow content between `{% ... %}` block boundaries must be preserved as authored; the formatter must not normalize it." This protects screen reader prosody.
- Document the rationale (accname 1.2 + screen reader implementation behavior) in the canonical policy file.
- Test fixture: a template like `<button>Open <span class="visually-hidden">accessibility menu</span></button>` should round-trip with the `<span>` and surrounding spaces intact.

### F9 — Fastblocks CI status unknown (Observation)
**Category**: Pre-flight verification
**Finding**: The spec assumes `fastblocks/` and `splashstand/` are receiving projects but does not audit their existing CI. If either repo already runs WCAG checks via axe-core / pa11y-ci / Lighthouse CI, the spec should *integrate*, not silently shadow. If they do not, that's a gap the spec creates (not a conflict). The reviewer cannot determine this from the spec alone.
**Recommendation**:
- Pre-flight grep: does `fastblocks/` or `splashstand/` (or their CI configs) reference axe, pa11y, lighthouse, or `@axe-core/cli`?
- If yes: spec must extend, not duplicate.
- If no: the Web adapter's a11y story becomes a net-new addition and should be priced accordingly in §Risks.

### F10 — Cross-package parity corpus should include a11y fixtures (Minor)
**Category**: Testing
**Finding**: §Testing strategy lists `tests/fixtures/jinja-corpus/` covering "default delimiters, fastblocks-style `[%`/`[[`/`[#`, edge cases." No mention of a11y-sensitive fixtures. Without them, F4/F8 regressions slip in silently.
**Recommendation**: Add a11y-tagged fixtures: `aria-label-with-expression`, `alt-fallback-conditional`, `label-wrapping-input`, `heading-in-conditional`, `live-region-passthrough`. Each must round-trip identically per Rule 4 invariant AND render to a string whose a11y-relevant attributes are byte-identical.

### F11 — Watch mode & a11y feedback loop (Observation)
**Category**: Future work
**Finding**: §Out of scope lists "Watch mode" as v0.83 future work. Watch mode has outsized value for a11y: live feedback during template edits lets developers catch `alt={{ foo }}` regressions where `foo` is empty. Worth noting as a future-work a11y angle, not blocking Phase 4.
**Recommendation**: Add to §Open questions / future work: "Watch mode for Web a11y hooks — gives per-keystroke feedback on alt-text / aria-label authoring."

### F12 — No mention of `axe-core` integration in MCP tools (Minor)
**Category**: MCP tools
**Finding**: §Phase 4 lists MCP tools `check_web_lint` and `format_jinja_templates`. No `check_web_a11y`. If the Web adapter adds axe-core/pa11y hooks, the MCP surface should mirror them so agents can invoke a11y checks individually (e.g., "check a11y on this fixture URL" vs. "run the whole hook pipeline").
**Recommendation**: Add `check_web_a11y` MCP tool parallel to `check_web_lint`. Schema should accept a URL or file path and return per-rule WCAG SC counts.

### F13 — Out-of-scope list silently defers the entire a11y surface (Minor)
**Category**: Scope boundary
**Finding**: §Out of scope says nothing about "accessibility testing." The implied decision (a11y is Phase 6+) is not documented. A reviewer reading the spec has no way to know whether a11y was considered-and-deferred or omitted-and-overlooked. This ambiguity is a process risk: when Phase 6 planning begins, there is no anchor for what was already considered.
**Recommendation**: Add an explicit bullet to §Out of scope: "Web a11y hooks (axe-core, pa11y, stylelint-a11y, eslint-plugin-jsx-a11y) — explicit Phase 6 follow-up; current design does not include them." Even better: do not defer; bring into Phase 4 (F1).

## Cross-cutting a11y architectural notes

### Universal design implications
The spec's "Approach A — Language Adapters as first-class packages" is a11y-positive: a hook-per-tool shape means a11y hooks slot in naturally alongside lint/format. The cost is that a11y is a *cross-language* concern (HTML semantics, JS interactivity, CSS visual focus, ARIA across both), and the per-language slicing risks leaving a11y as "nobody's adapter." Recommend a `crackerjack/adapters/web/a11y.py` (or a `crackerjack/a11y/` cross-cutting module) that the Web adapter imports, rather than scattering a11y checks across `css_hooks.py`, `js_hooks.py`, `html_hooks.py`.

### Crackerjack's MCP-first posture and a11y
The Crackerjack MCP server on port 8676 exposes tool results that downstream agents (Claude Code, Mahavishnu workers) consume. A passing `check_web_lint` with **no a11y dimension** is exactly the failure mode flagged in memory `mcp-surface-health-illusion.md`: surface signals look healthy, the underlying gap is invisible. Adding a11y hooks with explicit WCAG tiering in the MCP response schema closes this hole.

### Interaction with `crackerjack-p-minor-full-lifecycle.md`
The lifecycle phase (bump → commit → tag → push → publish) for Python currently does not consult hook results for *whether to tag*. If Web a11y hooks are added in Phase 4, the lifecycle must treat WCAG A/AA failures as version-bump blockers (per F2 recommendation). This requires either a config flag or a hardcoded default. The spec should call this out before Phase 2 ships, since Swift will inherit the policy.

This review covers the eight requested lenses:

1. **Web hooks scope — a11y gap?** — Covered (F1, F5, F6). Major gap confirmed; specific tools enumerated.
2. **HTML validation vs. a11y** — Covered (F3). Conflation flagged; semantic distinction documented.
3. **Jinja formatter and screen readers** — Covered (F4, F8). Multiple rules audited; a11y-unsafe edges identified.
4. **CSS hooks and a11y** — Covered (F5). Default-config absence and rule gaps identified.
5. **WCAG compliance gating** — Covered (F2). No current gate; AA-level default proposed.
7. **Universal design (formatter preserves a11y structure)** — Covered (F4, F8). Byte-level attribute preservation recommended.
8. **Reporting a11y violations** — Covered (F7). Tiered reporting by WCAG level proposed.

6. **Fastblocks CI status** — Partially covered (F9). Verification needed; cannot complete without external evidence.

Additional findings surfaced beyond the requested lens: F10 (test corpus), F11 (watch mode), F12 (MCP tool parity), F13 (scope-boundary documentation).

**Severity summary**: 2 Critical, 6 Major, 4 Minor, 1 Observation. The most load-bearing concern is F1 — the Web adapter ships without a11y tooling at all — combined with F2 (no WCAG gate) and F13 (the omission is not even documented). These three together mean the spec can be implemented exactly as written and still produce a Bodai web ecosystem where Python code quality is enforced but accessibility regressions are invisible to the same gate that blocks `crackerjack run -p minor`.
